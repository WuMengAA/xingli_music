**读表结论：**

1. **iOS 是唯一 100% 覆盖的新平台** —— 没有任何插件需要找替代。
2. **`just_audio` 缺 Linux** 是全表最致命的一格：`lib/services/audio/audio_service.dart:52` 硬持有 `final AudioPlayer _music`（just_audio 类型），`:37-40` 还注入了 `AudioPipeline` —— 整个播放状态机（`stateStream` / `playingStream` / `positionStream`）都建在 `_music.playerStateStream` 上。Linux 要么换 `just_audio_media_kit` 后端，要么抽播放引擎接口。

**Info.plist 权限声明（`ios/Runner/Info.plist` 现状）**

已有 ✅：
- `UIBackgroundModes = [audio]`（第 51-54 行）—— **后台播放的必要条件，已配好**
- `NSAppleMusicUsageDescription`（读取音乐库，`on_audio_query_ios` 需要）
- `NSMotionUsageDescription`（`sensors_plus` 摇一摇）
- `CFBundleDisplayName = 星璃音乐`、`CFBundleDevelopmentRegion = zh_CN`

需补 ⚠️：
- **`NSMicrophoneUsageDescription`** —— `lib/services/permission_service.dart:53,72` 会查询 `Permission.microphone`。只要 `permission_handler` 编译进了麦克风模块，Apple 静态扫描就会要求这条描述，否则**上传 App Store Connect 直接被 ITMS 打回**。
- **`PrivacyInfo.xcprivacy`**（隐私清单，2024 年起强制）。本工程会触发两类 Required Reason API：
  - `NSPrivacyAccessedAPICategoryUserDefaults` ← `shared_preferences`（`main.dart:25` 启动即调用），理由码 `CA92.1`
  - `NSPrivacyAccessedAPICategoryFileTimestamp` ← `path_provider` + `LogService`（`log_service.dart:31-39` 建日志文件）、`local_music_scanner` 目录遍历，理由码 `C617.1`
- `permission_handler` 的 **`PERMISSION_*` 宏裁剪**：默认全量编译会让二进制里出现「声明了但从未使用」的权限 API（通讯录/日历/相册…），是 App Store 审核 5.1.1 的常见拒因。需要在 Podfile 的 `post_install` 里只开 `PERMISSION_NOTIFICATIONS` / `PERMISSION_MEDIA_LIBRARY` / `PERMISSION_MICROPHONE`。
  - ⚠️ **这条与「无 Podfile / 走 SPM」冲突** —— SPM 模式下没有 `post_install` 钩子。**建议 iOS 线明确切回 CocoaPods**（`flutter config --no-enable-swift-package-manager`），理由：`audio_service` 0.18.19、`on_audio_query` 2.9.0 都是只提供 podspec 的老插件，SPM 兼容性未经验证，且失去权限宏裁剪能力。

**签名/上架**
- Apple Developer Program（99 美元/年）；Bundle ID 建议沿用 `com.stelarith.xingli-music`（注意 App Store 的 Bundle ID **不允许下划线**，Android 的 `com.stelarith.xingli_music` 不能直接复用）

### 2.3 macOS

**需先执行** `flutter create --platforms=macos .`（当前无 `macos/` 目录）。

- **App Sandbox entitlements** —— 默认模板是全封闭的，本工程必须补：
  - `com.apple.security.network.client` ← `http` 包（Subsonic / 电台 / `DemoSource` 网络流）

- **优势**：`audio_service` + `audio_session` + `sqflite_darwin` + `just_audio` 全都有 macOS 实现 → 音频与存储链路几乎零改动，是所有桌面平台里最省事的。
- 分发：Developer ID 签名 + **公证（notarization）**，或走 Mac App Store（则受 App Sandbox 更严限制）

### 2.4 Linux

**需先执行** `flutter create --platforms=linux .`。

这是唯一需要**动核心架构**的平台：

- **`just_audio` 无 Linux 实现**。两条路：
  - **路线 A（推荐）**：引入 `just_audio_media_kit`（media_kit 后端，依赖 `libmpv`）—— 保留 `just_audio` 的 API 面，`lib/services/audio/audio_service.dart` 几乎不用改。代价是引入 mpv 系统依赖。
  - **路线 B**：Linux 上整条切 `audioplayers_linux`（GStreamer）—— 但 `AudioService` 类深度耦合 just_audio：`_music.playerStateStream`（`:95`）、`_music.positionStream`（`:116`）、`_music.durationStream`（`:119`）、`AudioPipeline`（`:39`）。需要先抽播放引擎接口，改动面大得多。
- `audio_service` 无 Linux → 无 **MPRIS**（Linux 桌面的媒体控件标准，走 D-Bus）。需要自写 D-Bus 服务或引入 `mpris_service`。
- `sqflite` / `permission_handler` / `audio_session` 均无 Linux → 同 Windows 处置。
- 系统依赖：GTK3 + （路线 A）`libmpv` / （路线 B）GStreamer 插件集 → 发行版差异是长期维护成本。
- 分发：Flatpak / Snap / AppImage / deb —— **建议只选一个**（Flatpak 覆盖面最广），四个都做等于四套维护。

### 2.5 Android Auto（车载）

**需补的四件事**

1. **Manifest**：加 `<meta-data android:name="com.google.android.gms.car.application" android:resource="@xml/automotive_app_desc"/>` + 新建 `res/xml/automotive_app_desc.xml`（`<uses name="media"/>`）。
2. **媒体浏览树 —— 最大工作量。** `lib/services/audio/audio_handler.dart` 的 `StelarithAudioHandler` 目前只 override 了 `play` / `pause` / `seek` / `skipToNext` / `skipToPrevious` / `click` / `stop`（`:100-123`）。**完全没有 `getChildren(parentMediaId)`、`getMediaItem`、`search`、`playFromMediaId`、`playFromSearch`** → Auto 上打开就是空列表。
   - 建议树形：根 → `场景` / `曲库` / `最近播放` / `收藏`（Auto 根节点建议 ≤4 个），二级为曲目。数据直接复用 `activeSourcesProvider`（`audio_providers.dart:69`）与 `effectiveMusicLibraryProvider`（`:118`）。
3. **播放队列**：`BaseAudioHandler.queue` 从未 `add` 过 → Auto 的「下一首列表」为空。需要在切歌时同步发布。
4. **封面 URI 跨进程问题** ⚠️：`audio_handler.dart:85` 用的是 `Uri.file(t.coverPath!)`。Android Auto 是**独立进程**读 `MediaItem.artUri`，读不到本 App 私有目录的 `file://` → 封面全空。必须改成 `content://`（配 `FileProvider`）或走网络 URL。

**关键收益点**：Auto 的 UI 由系统模板渲染，**星璃的液态玻璃 / 无限画布 / 场景系统一律不出现**。所以这 11 人天全是数据层，零 UI 成本，且不会污染手机版布局 —— **投入产出比在所有平台里最高**。

**测试与上架**：Desktop Head Unit (DHU) 或真车机；Google Play 有独立的 Android Auto 质量审核清单（驾驶分心、必须支持语音 `playFromSearch`）。

### 2.6 CarPlay

- **前置**：必须先有可用的 iOS 版本。
- **最大风险是非技术的**：需向 Apple 单独申请 `com.apple.developer.carplay-audio` entitlement。Apple 会审核「你的 App 为什么需要 CarPlay」，个人/小众音乐 App 通过率不高，**审批周期以周~月计，且可能直接被拒**。这是全方案里唯一「钱和人天都解决不了」的风险项。

## 4. 平台特定代码隔离策略

**总原则：绝不为了新平台而修改 Android/Web 已跑通的代码路径。所有平台差异下沉到「能力查询」与「Provider 注入」两层，UI 层零感知。**

### 4.1 现状盘点

仓库已有的隔离手段是**运行时守卫**，共 11 处（`grep kIsWeb|Platform.is` 结果）：

| 范式 | 出现位置 | 评价 |
|---|---|---|
| `if (kIsWeb) return X; if (Platform.isY) {...}` | `ambient_soundscape_service.dart:32,34`、`minecraft_sfx_service.dart:132,133`、`sound_block_mixer.dart:96,112,113`、`local_dir_music_source.dart:32,33`、`minecraft_music_source.dart:37,38,44,45` | ✅ 正确，但**散落在 6 个文件里，无单一真源** |
| `if (kIsWeb \|\| !Platform.isAndroid) return null;` | `audio_providers.dart:40` | ✅ **最佳范式**（能力型 Provider） |
| `!kIsWeb && Platform.isAndroid` | `eq_engine.dart:147`、`sensor_service.dart:32` | ✅ 正确 |
| `if (!Platform.isAndroid && !Platform.isIOS)` | `local_music_scanner.dart:36` | ❌ **漏 `kIsWeb`**（见 §3.5） |
| 文件顶部直接 `import 'dart:io';` | 12 个文件 | ⚠️ 靠 dart2js 的 `dart:io` 桩勉强通过，脆弱 |

**问题**：平台判断散落，每加一个平台就要把这 11 处全部重读一遍并逐个改 —— 加 5 个平台就是 55 次判断修改，必然漏。

### 4.2 策略一：能力真源（Capability Registry）—— 推荐，改动最小

新增 `lib/core/platform/platform_caps.dart`，把「平台是什么」翻译成「平台能做什么」：

```
abstract final class Caps {
  // 平台身份（唯一允许出现 Platform.isX 的地方）
  static bool get isWeb / isAndroid / isIOS / isMacOS / isWindows / isLinux
  static bool get isMobile / isDesktop / isApple

  // 能力（业务代码只查这些，不查平台）
  static bool get hasMediaStore;          // on_audio_query   → android || ios
  static bool get hasSystemMediaControls; // audio_service    → android || ios || macos || web
  static bool get hasAudioFocus;          // audio_session    → android || ios || macos || web
  static bool get hasNativeEq;            // AndroidEqualizer → android
  static bool get hasSensors;             // sensors_plus     → android || ios || web
  static bool get hasNativeSqlite;        // sqflite          → android || ios || macos
  static bool get hasFileSystem;          // dart:io          → !web
  static bool get hasRuntimePermissions;  // permission_handler → !(macos || linux)
  static bool get prefersLiquidGlass;     // shader 白名单
}
```

**迁移方式（纯提取，零行为变更）**：把现有 11 处判断逐条替换为语义化查询。例如
`audio_providers.dart:40` 的 `if (kIsWeb || !Platform.isAndroid) return null;` → `if (!Caps.hasNativeEq) return null;`

**收益**：以后加平台只改 `platform_caps.dart` 一个文件。`local_music_scanner.dart:36` 那个漏守卫的 bug 在迁移过程中自然被消灭。

### 4.3 策略二：条件导入（仅用于必须触碰 `dart:io` 类型的地方）

`Caps` 解决不了「类型层面」的问题 —— 比如 `track_cover.dart:1` 用 `Image.file(File(...))`、`log_service.dart:22-23` 声明 `File? _file; IOSink? _sink;`。这些即使运行时不执行，类型也要在 Web 上存在。

对这类文件用条件导入：

```
import 'io_shim_stub.dart' if (dart.library.io) 'io_shim_real.dart';
```

**范围严格限定**：只对 `log_service.dart`、`track_cover.dart` 这两处做。其余 10 个 `import 'dart:io'` 的文件都只用 `Platform.isX`（已被 `Caps` 收编），不需要条件导入。

### 4.4 策略三：Riverpod 能力注入（核心手段）

沿用 `androidEqualizerProvider` 已验证的范式，把「平台实现选择」全部收敛到 provider 层，**UI 与业务代码一行不改**：

| 新增 Provider | Android | iOS | macOS | Windows | Linux | Web |

| `databaseFactoryProvider` | sqflite | sqflite | sqflite | **ffi** | **ffi** | **内存/Noop** |

### 4.5 策略四：UI 层隔离 —— 扩展而非改写 `ResponsiveLayout`

`lib/core/layout/responsive_layout.dart` 现有 API（`isCompact` / `isLandscape` / `isLarge` / `isTight` / `dockShowLabels` / `dockMaxWidth` / `playerCollapsedByDefault` / `cardScale`）**已被多处消费，签名一律保留不动**。


`cardScale` 现在是 `isCompact ? 0.85 : (isLarge ? 1.12 : 1.0)` —— TV 档只需在这条链上追加一个分支，不动前两档。

**TV 焦点体系同理走「包裹」而非「侵入」**：在 `AppShell`（`app_shell.dart:135`）外层包一个 `FocusTraversalGroup` + `Shortcuts`/`Actions`，媒体键与 D-pad 统一在这里映射；各页面不感知。只有 §2.7 列出的 8 个 `GestureDetector` 文件需要逐个换成可聚焦控件。

### 4.6 策略五：原生工程隔离

| 平台 | 手段 |
|---|---|
| **TV** | Android **product flavor** `tv`（`android/app/src/tv/AndroidManifest.xml`）—— leanback、banner、LEANBACK_LAUNCHER 只进 TV 包，手机版 Manifest 一字不改 |
| **Android Auto** | 无需 flavor（`automotive_app_desc.xml` 对手机无副作用）；Dart 侧的媒体浏览树是**纯新增 override**，不动已有 7 个 override |
| **CarPlay** | 独立 Swift 文件 + `#if canImport(CarPlay)` 编译隔离 |
| **桌面三平台** | CMake/Xcode 工程天然独立，互不影响 |

### 4.7 铁律（写进 CI 或 review 清单）

1. **禁止**在 `lib/app.dart`、`lib/app_shell.dart`、任何 `pages/` 下的文件里出现 `Platform.isX` —— 平台差异只能出现在 `platform_caps.dart` 与 provider 定义里。
2. 新增平台判断一律走 `Caps.hasXxx`（能力），不写 `Caps.isWindows`（身份）。
3. 任何平台的失败路径必须**可见**：现在 `app.dart:104` 只写日志，用户看不到。建议失败时同步写入 `recentNotificationsProvider`（`app_shell.dart:107` 已有此机制），让「后台播放在本平台不可用」变成用户可感知的信息。
4. `pubspec.yaml` 新增平台专属依赖时，必须用 `dependency_overrides` 之外的方式隔离（如 `just_audio_media_kit` 只在 Linux 需要，但 pub 无条件依赖机制 → 会被全平台拉取，需评估包体积影响）。

### 6.3 三个「看起来会很难、实际很省」的好消息
