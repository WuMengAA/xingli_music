## 0. 一句话结论

**分享码不用新造轮子**——`Scenes.encodePack` 已经是完整的分享载体，且它的解码器天然忽略未知顶层字段，所以社交元数据可以"挂在包外"零成本接入；**后端第一版不要做**——先"本地分享码 + 只读静态商店"两级火箭，把 UGC 后端推到第三阶段；**最大风险不是技术，是 `soundscapePath` 与 `bgmUri` 会随包外泄用户本地路径**，这是上线前必须堵的洞。

### 1.2 `encodePack` 的真实格式

```dart
// scene_api.dart:40-43 —— 原文
static String encodePack(Scene scene) => jsonEncode({
      'schema': packSchemaVersion,   // 1
      'scene': scene.toJson(),
    });
```

```dart
// scene_api.dart:46-59 —— 原文（关键：只校验 schema，只读 scene）
static Scene decodePack(String pack) {
  final root = jsonDecode(pack) as Map<String, dynamic>;
  final int schema = root['schema'] as int? ?? 0;
  if (schema != packSchemaVersion) throw FormatException(...);
  final dynamic raw = root['scene'];
  if (raw is! Map<String, dynamic>) throw const FormatException(...);
  return Scene.fromJson(raw);
}
```

**这一段代码有两个对本方案极其有利的性质：**

1. **顶层未知字段被静默忽略**。`decodePack` 只取 `schema` 和 `scene`，任何额外的顶层 key 都不影响解析。
   → **社交元数据（作者/标签/点赞数）可以作为 `meta` 兄弟键挂在包顶层，老版本 App 照样能导入这个包，只是看不到元数据。** 这是天然的前向兼容，零成本。
2. `ScenePacker.encode` 已经在实践这个性质——它多写了 `packedAtMs` / `packedBy` 两个顶层键，而 `Scenes.decodePack` 能正常解析它的输出。【已验证】

## 2. J-1 场景分享码设计

### 2.1 设计目标与分层

一个"分享码"要同时满足四种截然不同的使用场景，不可能用一种编码通吃：

| 载体 | 约束 | 选型 | 需后端 |
|---|---|---|---|
| **二维码**（当面分享，主路径） | 容量 ≤ 2953 B，越短越好扫 | QR byte 模式直塞紧凑 UTF-8 JSON | ❌ |
| **文本码**（微信/QQ 粘贴） | 必须 ASCII 安全、可选中 | `STL1.<base64url(gzip(紧凑JSON))>` | ❌ |
| **场景文件**（备份/邮件附件） | 可读、可版本管理 | `.stlscene`（= `encodePack` 原样 JSON，缩进美化） | ❌ |
| **短码**（口播/6 位码） | 人能记住、能手输 | `星璃-A7K2M9` → 服务端换包 | ✅ **必须有后端** |

> **必须向用户如实说明的一条**：真正意义上的"6 位短码"**不可能离线实现**。一个场景包最小也有 350 字节的信息熵，任何离线编码都压不进 6 个字符——6 位码本质是一张服务端的映射表。所以**第一阶段的"分享码"= 二维码 + 长文本码 + 文件**，短码留到有后端的第三阶段。

### 2.2 体积实测（本方案的定量依据）

以一个字段填满的自定义场景（含 bgm 三字段、粒子色、背景覆盖色、中文名与描述）实测：

| 编码方式 | 体积 | 备注 |
|---|---|---|
| `Scenes.encodePack` 原样输出 | **645 B** / 596 字符 | 当前实现，含所有 null 字段 |
| 紧凑线格式（短键 + 省 null + 颜色转 hex 串） | **350 B** | 相对原样 **−45.7%** |
| 紧凑格式 gzip 后 | 306 B | 仅省 12.6% |
| 紧凑格式 gzip + base64url | **408 字符** | **比不压缩的紧凑 JSON（350 B）还长** |
| 原样 gzip + base64url | 636 字符 | 比原样 JSON（596 字符）还长 |
| 叠加体素 `voxelCapture`（按体素方案 §5.3 字段）后原样输出 | 827 B | gzip+b64url 782 字符 |

**两条反直觉但重要的结论：**

1. **不要为了二维码去做 gzip+base64。** 这个数据量级下 gzip 省的字节被 base64 的 4/3 膨胀吃光还倒亏。二维码用 **byte 模式直接塞 UTF-8 JSON** 最短。
2. **真正有效的压缩是"改线格式"，不是"上压缩算法"**——短键 + 省略 null 一把砍掉 45.7%，因为 `Scene.toJson` 会无条件写出全部 22 个键（含 8 个常为 null 的可空字段）。

按 350 B 估算，QR byte 模式约需版本 14~16、M 级纠错（73~81 模块），屏幕显示与拍摄识别都很轻松，距 v40 上限（2953 B / L 级）有 8 倍余量。【需实测】具体版本号以 `qr_flutter` 实际编码结果为准。

### 2.3 建议的分享编解码层

**不改动 `Scenes.encodePack` / `decodePack`**（它们是已上线的存档格式，改了会破坏用户已复制出去的包），而是**新增一层旁路编解码器**：

```
lib/scenes/
├─ scene_api.dart        （不动，仍是存档/内部格式的真源）
├─ scene_packer.dart     （修 D-1/D-2 两个 bug）
├─ scene_deploy.dart     （不动）
├─ share_codec.dart      ★新增：紧凑线格式 ⇄ Scene
├─ share_meta.dart       ★新增：ShareMeta 数据类（见 §5）
└─ share_sanitizer.dart  ★新增：导出脱敏 + 导入净化（见 §7）
```

`share_codec.dart` 的职责边界（建议 API 形态，非最终签名）：

| 方法 | 输入 → 输出 | 说明 |
|---|---|---|
| `encodeCompact(Scene, {ShareMeta?})` | → `String` | 紧凑 JSON，二维码用 |
| `decodeCompact(String)` | → `(Scene, ShareMeta?)` | 容错解析 |
| `encodeText(Scene, {ShareMeta?})` | → `String` | `STL1.<base64url(gzip(compact))>` |
| `decodeText(String)` | → `(Scene, ShareMeta?)` | 校验前缀 + CRC |
| `sniff(String)` | → `ShareFormat` | 自动识别：紧凑/文本码/原样 encodePack/`.stlscene` |

**`sniff` 是关键的体验设计**：用户从任何地方粘贴任何一种格式，导入入口都能认出来。判定顺序：`STL1.` 前缀 → 以 `{` 开头且有 `"schema"` → 以 `{` 开头且有 `"s"` 键 → 否则报"无法识别的分享码"。

**文本码前缀 `STL1.` 的作用**：一是让 `sniff` 零歧义；二是未来线格式升级为 `STL2.` 时，老 App 能给出"请升级星璃"而不是"格式错误"。前缀里的版本号是**线格式版本，与 `packSchemaVersion` 正交**——不要复用同一个数字，否则两条演进线会互相绑架。

### 2.6 schema 兼容策略

**与 `docs/体素世界技术方案.md` §5.3 保持完全一致，不另起炉灶。** 该文档已裁决把严格相等改为区间兼容：

```dart
static const int packSchemaVersion = 2;   // 体素落地时 1 → 2
static const int minSupportedSchema = 1;  // 新增
// schema < min || schema > current → FormatException（错误信息必须可读）
```

本方案在此之上补三条**社交场景特有**的要求：

1. **`ScenePacker.decode` 必须补同样的校验并修 D-1**（`packedAtMs` 改为 `as int?` + 默认值）。分享链路可能走到这条路径，两条路径行为不一致就是线上事故。
2. **"未来包"要给出可操作的提示**，不能只抛异常。用户扫到一个 `schema=3` 的码，应看到「这个场景来自更新版本的星璃，请升级后再导入」而不是 `FormatException`。
3. **线格式版本（`STL1.`）与 pack schema 解耦**：
   - `packSchemaVersion` 变化 = **Scene 结构**变了（如新增 `voxelCapture`）
   - `STLn` 变化 = **压缩/编码方式**变了（如改用 CBOR）
   两者可以独立演进。跨版本兼容矩阵：

| 包 schema | v1 App | v2 App（体素落地后） | 说明 |
|---|---|---|---|
| 1 | ✅ | ✅ `voxelCapture=null` → 渐变背景 | 老包永远能读 |
| 2 无 capture | ❌ FormatException | ✅ | 提示升级 |
| 2 有 capture | ❌ FormatException | ✅ 3D 背景 | 提示升级 |
| 3（未来） | ❌ | ❌ 但提示可读 | 见上条第 2 点 |

> 体素方案已明确 `VoxelSceneCapture` 用 `tryFromJson`（不认识的 `"v":2` 返回 null 而非抛错），这个"**字段级降级、包级不失败**"的原则应推广到所有未来新增的可空复合字段——这是分享场景下跨版本存活的核心保命机制。

## 3. J-2 场景 / 拍照背景导出

### 3.1 导出什么：三档产物

| 档位 | 产物 | 技术路径 | 平台 | 依赖 |
|---|---|---|---|---|
| **A. 静态图** | PNG（1080×1920 / 1080×1350 / 1080×1080） | `RenderRepaintBoundary.toImage()` | 全平台 | 0 新依赖 |
| **B. 动图** | GIF / WebP（3~5 s，15 fps，720p） | 离屏确定性逐帧 + 纯 Dart 编码 | 全平台（含 Web） | `image` 包 |
| **C. 视频** | MP4 H.264（5~15 s，30 fps，1080p） | 离屏确定性逐帧 + 平台原生编码器 | Android 先行 / iOS 后补 | MethodChannel |

**核心判断：C 档不走"录屏"，走"离屏重渲"。** 理由见 §3.3。

### 3.2 A 档 · 静态 PNG 快照

工程里已有现成范式，直接复用即可：

```dart
// lib/providers/shell/liquid_glass_capture_provider.dart:44-53 —— 原文
Future<void> _capture() async {
  final RenderObject? ro = _boundaryKey.currentContext?.findRenderObject();
  if (ro is! RenderRepaintBoundary) return;
  try {
    final ui.Image img = await ro.toImage();
    if (mounted) setState(() => _image = img);
  } catch (_) { /* 捕获失败（测试环境等）静默降级 */ }
}
```

导出版在此基础上改三处：
1. `toImage(pixelRatio: 3.0)` —— 屏幕是 1x/2x，出图要 3x 才够社交平台清晰度
2. `img.toByteData(format: ui.ImageByteFormat.png)` → 字节流
3. `path_provider` 取目录后落盘（`path_provider ^2.1.5` 已有 ✅）

**不要截当前屏**，而是**离屏构造一棵专用的导出 widget 树**：

```
ExportCanvas（离屏，固定 1080×1920 逻辑尺寸）
├─ 背景层：场景渐变 / voxelCapture 实时渲染（同 §3.3）
├─ 内容层：场景名 + mood + 一句 desc（排版为导出优化，不是照搬 UI）
└─ 品牌层：右下角小 logo + 二维码角标（见 §3.4）
```

**理由**：屏幕上的 UI 有 Dock、播放条、状态栏、安全区——截屏出来是"一张 App 截图"，不是"一张作品"。而离屏树可以固定构图、固定比例、去掉一切控件，且**不受设备分辨率影响**（手表 412×502 和平板出的图一样大）。这对 `A-1 手表 412×502` 适配档尤其重要。

**已知坑（源自现有代码注释）**：
- `toImage()` 在测试环境会失败 → 单测里必须走 mock 或跳过（现有代码 line 50-52 已是这个处理方式）
- Web 端 `toImage` 依赖 CanvasKit（项目 Web 版正是 CanvasKit，✅ 兼容），但跨域图片会污染画布 → 导出树里不要放网络图
- `LiquidGlass` 的 shader 在离屏树里需要背景快照才生效（`LiquidGlassCapture.maybeOf(context) == null` 时退回纯内容）→ **导出树里干脆不用 LiquidGlass**，避免出图缺玻璃效果

### 3.3 B/C 档 · 离屏确定性逐帧渲染（本方案的技术核心）

#### 为什么不录屏

`docs/体素世界技术方案.md` §5.1 定下的原则是"**存机位不存像素**"：

> `VoxelSceneCapture` 不存像素，只存"能复现这一画面的参数"：世界 seed + 世界尺寸 + 相机位姿 + fov + 画幅 + 时间相位。

这条原则在导出场景下的直接推论是：**画面是纯函数 `frame = render(capture, phase)`，所以可以脱离实时播放、脱离屏幕、脱离设备性能，离线渲染任意分辨率任意帧率的序列帧。**

确定性已经在代码里成立【已验证】：
- `lib/widgets/voxel/voxel_world.dart:14-23` —— `VoxelWorld({..., int seed = 20260810, ...}) { _generate(seed); }`，构造函数吃 seed；体素方案 §5.3 已确认生成算法是纯整数位运算 + LCG，无 `DateTime`、无无种子 `Random()`
- `lib/widgets/noise_texture.dart:29` —— `final Random rng = Random(seed);` 背景噪点也是种子驱动的
- 渐变背景（`card_stack.dart:239`）本身是静态的，无随机性

> ⚠️ **F2 前置依赖**：体素方案 §5.3 明确指出 `VoxelWorld` 目前**没有把 seed 存成字段**（`_generate(seed)` 后即丢弃）。逐帧导出要能复现同一世界，必须先按体素方案补 `final int seed;`。**这是 C 档的硬前置，不做 = 导不出体素背景视频。**

#### 录屏 vs 离屏重渲 对比

| 维度 | 录屏（MediaProjection / ReplayKit） | 离屏重渲（推荐） |
|---|---|---|
| 分辨率 | 受限于屏幕（手表 412×502 出不了 1080p） | 任意，1080p/4K 均可 |
| 帧率 | 受限于实时性能（体素背景实时只跑 18 fps） | 任意，30/60 fps 均可 |
| 画面纯净度 | 会录进状态栏、Dock、手势条、来电横幅 | 只有导出树内容 |
| 权限 | 每次弹系统授权框（Android 每次、iOS 需 ReplayKit） | 无需任何权限 |
| 时长精度 | 手动起止，不精确 | 帧数精确可控 |
| 后台/息屏 | 中断即毁 | 不受影响，可后台跑 |
| Web/Windows | 不可用 | 可用（B 档） |
| 隐私风险 | 高（可能录到通知内容） | 无 |

**裁决：录屏 API 不作为主路径**，只在未来"录制我的操作过程"这类需求出现时再考虑。

#### 渲染管线

```
导出请求（scene, 时长 T, 帧率 F, 分辨率 WxH）
   │
   ├─ 帧数 N = T × F（如 5s × 30fps = 150 帧）
   ▼
for k in 0..N-1:
   ├─ phase = k / F × speed        ← 唯一的时间输入，纯函数
   ├─ PictureRecorder + Canvas
   ├─ 绘制导出树（背景 render(capture, phase) + 内容层 + 品牌层）
   ├─ picture.toImage(W, H)
   ├─ image.toByteData(rawRgba)    ← B/C 档都要原始像素，不要每帧 PNG
   └─ 交给编码器 / 写入临时帧缓存
   ▼
编码 → 落盘 → 分享
```

**性能与内存约束（必须设计进去）**：
- 1080×1920 RGBA 单帧 = **7.9 MB**。150 帧全内存 = 1.2 GB → **必然 OOM**。
- 对策一：**流式编码**，编一帧丢一帧，内存常驻 ≤ 3 帧（约 24 MB）。
- 对策二：**分辨率分档**，GIF 档强制降到 720×1280（3.7 MB/帧）甚至 540×960。
- 对策三：**渲染放 Isolate**——但 `ui.Picture.toImage()` 需要 GPU 上下文，在后台 Isolate 中受限【需实测】。保守方案是主 Isolate 渲染 + 后台 Isolate 编码，中间用 `TransferableTypedData` 传字节，避免拷贝。
- 对策四：**必须有进度条 + 可取消**。150 帧 × (渲染 5ms + 编码 15ms) ≈ 3 s，看着不长，但低端机可能到 15 s，无进度反馈用户会以为卡死。
- 对策五：**导出期间暂停实时背景 timer**（体素方案 §5.4 的 `Timer.periodic`），避免与导出渲染抢 GPU。

#### 编码器选型

| 方案 | 产物 | 体积影响 | 平台覆盖 | 评价 |
|---|---|---|---|---|
| **`image` 包纯 Dart 编码 GIF/动画 WebP** | GIF/WebP | +0（纯 Dart） | 全平台含 Web | ✅ **B 档采纳**。GIF 只有 256 色、渐变会有色带，但社交平台兼容性最好；动画 WebP 画质好得多但部分平台不认 |
| **Android `MediaCodec` + `MediaMuxer`（MethodChannel）** | MP4 H.264 | +0（系统 API） | 仅 Android | ✅ **C 档 Android 采纳**。工程已有自写 MethodChannel 先例（`SensorChannel.kt` 读 TYPE_LIGHT/TYPE_HEART_RATE） |
| **iOS `AVAssetWriter`（MethodChannel）** | MP4 H.264 | +0 | 仅 iOS | ✅ C 档 iOS 采纳（**但项目当前无 iOS 工程**，排在 H 域跨平台之后） |
| **`ffmpeg_kit_flutter`** | 全格式 | **+20~40 MB/ABI** | 全平台 | ❌ **不采纳**。体积与项目"APK 精简"目标（G-1，debug 157MB 已是痛点）正面冲突；LGPL 需动态链接合规；且该项目上游已停止维护【需核实】 |
| **屏幕录制 API** | MP4 | +0 | 移动端 | ❌ 不采纳，见上表对比 |

**建议实施顺序：B 档（GIF，全平台、零原生）→ C 档 Android MP4 → C 档 iOS MP4。** B 档能覆盖"发朋友圈/发群"的绝大多数需求，且是 Web 端唯一可行的动图方案。

#### 音频：默认不混

导出视频要不要带 BGM？**默认不带，且这是合规裁决不是技术取舍。**

- `bgmUri` 指向的是用户本地音乐或第三方音源（网易云/QQ，见 I 域），把它混进视频并分享 = **传播受版权保护的录音制品**，风险直接落在 App 上。
- 唯一可安全混入的是**本工程自研的程序合成音景**——`services/audio/spatial/spatial_synth.dart` 合成的 water/fireplace/furnace/rain/wind/cave PCM WAV 是自研算法产物，无第三方版权。
- 因此：导出面板的音频选项为 `[无声（默认）] / [仅场景音景（自研合成）]`，**BGM 选项不提供**，并在 UI 上说明原因。

### 3.4 导出图即分享码（低成本高价值）

在导出图右下角画一枚小尺寸二维码（约 120×120 px），内容就是 §2.2 的紧凑分享码。

**收益**：图片本身成为分享载体。用户发一张好看的场景图到群里，别人扫图角落的码就能一键复刻这个场景——**不需要任何后端就实现了"病毒式传播"**，这是零成本的增长杠杆。

实现上，`qr_flutter` 提供 `QrPainter`，可直接 `paint(canvas, size)` 画进导出树的 Canvas，不需要先生成图片再合成。

> 备选方案是把分享码写进 PNG 的 `tEXt` chunk，但 Flutter 的 `toByteData(png)` 不暴露 chunk 接口，需手工拼字节；且社交平台转发时普遍会重编码图片、剥离元数据 → **不可靠，不采纳**。可见的二维码角标反而是最鲁棒的。

### 3.5 分享到其他 App

| 平台 | 方式 | 依赖 |
|---|---|---|
| Android/iOS | 系统分享面板（`ACTION_SEND` / `UIActivityViewController`） | `share_plus` ❌需新增；或自写 MethodChannel（有 `SensorChannel.kt` 先例） |
| Windows/Web | 无系统分享 → 「保存到…」+「复制到剪贴板」 | 0 新依赖 |

建议：**第一版全平台统一用「保存到相册/文件夹 + 复制分享码到剪贴板」**，零新依赖即可闭环；`share_plus` 作为体验优化排在后面。理由是 `share_plus` 只优化了"少点两下"，而它带来的是一个覆盖 6 个平台的插件依赖。

## 4. J-3 社区场景商店

### 4.1 后端选型对比

| 维度 | 纯本地 P2P | 只读静态商店 | 国内 BaaS | 海外 BaaS | 自建后端 |
|---|---|---|---|---|---|
| 形态 | 二维码/文件/剪贴板/局域网 | 对象存储 + CDN 上的静态 JSON 索引 | 腾讯云开发 CloudBase / LeanCloud | Supabase / Firebase | 服务器 + DB + OSS |
| 上传 UGC | ❌ | ❌（官方精选，随版本或 CDN 更新） | ✅ | ✅ | ✅ |
| 账号体系 | 无 | 无 | 内置（匿名/手机号/第三方） | 内置 | 自己写 |
| 月成本 | **¥0** | **≈¥5~30**（存储+流量） | ¥0 起，按量 | 免费额度 + 超量计费 | ≥¥100 + 运维人力 |
| ICP 备案 | 不需要 | 需要（若用国内域名/OSS 公网访问） | 需要 | 不需要但**不适用** | 需要 |
| 内容审核义务 | 无 | 无（内容由官方产出） | **有** | **有** | **有** |
| 中国大陆可用性 | ✅ | ✅ | ✅ | **Firebase ❌ 不可直连；Supabase ⚠️ 延迟高/不稳** | ✅ |
| 数据出境合规 | 无 | 无 | 无 | ⚠️ 用户数据存境外，触发出境合规义务 | 无 |
| 实施工作量 | 已在 J-1 覆盖 | **1~2 人日** | 5~8 人日 | 5~8 人日 | 15~25 人日 |

**几条决定性事实：**

1. **Firebase 直接出局** —— GCP 相关域名在中国大陆无法直连，而本项目是中文产品（内置场景名/文案全中文，音源规划为网易云/QQ 音乐）。用 Firebase 等于对主力用户群不可用。
2. **Supabase 也不推荐** —— 虽可访问，但延迟不稳；更关键的是 UGC + 用户标识存境外，会触发个人信息出境的合规义务，为一个 P3 功能背这个包袱不划算。自托管 Supabase 又等价于"自建后端"的成本。
3. **国内 BaaS（腾讯云开发 CloudBase / LeanCloud）是做 UGC 时的正确选择** —— 备案链路完整，鉴权/存储/云函数开箱即用，并可直接对接腾讯云内容安全（T-Sec 天御）做文本图片机审，把 §4.4 的审核义务落地成本压到最低。

### 4.2 推荐路线：两级火箭，UGC 推到第三级

```
Phase A  纯本地（无后端）
   二维码 / 文本码 / .stlscene 文件 / 导出图带码角标
   成本 ¥0 · 合规负担 0 · 覆盖"我发给朋友"这个 80% 场景
        ↓ 只有当用户开始抱怨"没地方发现新场景"才进入 B
Phase B  只读静态商店（无账号、无上传）
   官方 + 精选投稿场景，打包成一份静态 index.json 挂 CDN
   App 只 GET，永不 POST
   成本 ≈¥10/月 · 合规负担 0（内容由官方产出并负责）
        ↓ 只有当 DAU 与投稿量证明"用户真的想上架"才进入 C
Phase C  真 UGC 商店（账号 + 上传 + 审核）
   国内 BaaS + 机审 + 人审 + 举报 + 封禁
   成本 = 服务费 + 审核人力（这才是大头）
```

**为什么强烈建议卡在 Phase B**：

- 一旦允许用户上传，产品性质从"工具"变成"内容平台"，随之而来的是实名、审核、举报、未成年人保护、日志留存等一整套义务——**这些义务的成本远高于服务器费用，且是持续性的**。
- 而 Phase B 用**≈1~2 人日 + 每月几块钱**就能给用户"有个地方能逛新场景"的完整体验感知。投入产出比相差两个数量级。
- Phase B 的"投稿"可以走**站外收口**：用户在 App 里点"投稿我的场景" → 复制分享码 → 引导到官方社群/问卷提交 → 官方人工挑选后并入下一版 index.json。**零后端实现了 UGC 的内容供给，且天然带人工审核。**

### 4.3 Phase B 技术形态（推荐首发）

```
CDN / 对象存储
└─ /store/v1/
   ├─ index.json          （场景列表 + 元数据，含每项 contentHash）
   ├─ packs/<hash>.json   （单个场景包，格式 = §5 的带 meta 完整包）
   └─ manifest.json       （store schema 版本 + 最后更新时间 + 总数）
```

`index.json` 单条目约 200 B，1000 个场景 = 200 KB，**一次 GET 全量拉取即可，不需要分页 API**。客户端做本地筛选/搜索/排序，零后端计算。

**关键设计：缩略图不上传，客户端本地重渲。**

商店列表里每个场景要显示预览图。常规做法是服务端存缩略图（每张 50~200 KB × 1000 = 50~200 MB，且要 CDN 流量）。但本项目的场景**本身就是"参数即画面"**：

- 渐变背景 = `gradientColors` + `stops` 两个数组，客户端直接画
- 体素背景 = `voxelCapture` 参数确定性重渲（体素方案 §5.1 的核心性质）

→ **商店永远不传图片，只传参数，客户端拿到参数当场渲染缩略图。** 存储成本从 200 MB 降到 200 KB（**1000 倍**），流量成本同比例下降，且缩略图分辨率自适应设备。这是本项目相较通用 UGC 平台的结构性成本优势，必须吃满。

**客户端缓存策略**：`index.json` 带 `ETag`，用 `http ^1.2.2`（✅已有）做条件请求；本地缓存写 `sqflite ^2.4.1`（✅已有）或直接 `shared_preferences`。Phase B **零新依赖**。

### 4.4 Phase C 若启动：账号与合规最小集

**账号体系分层（按需最小化收集）**：

| 阶段 | 标识 | 收集的个人信息 | 合规负担 |
|---|---|---|---|
| Phase A/B | 无 | 无 | 无 |
| Phase C 起步 | 匿名设备 ID（本地生成 UUID，存 `shared_preferences`） | **无** | 低 |
| Phase C 成熟 | 手机号 / 第三方登录 | 手机号 | **高**：实名、隐私政策、注销、导出 |

> 建议 Phase C 起步就用**匿名 ID + 昵称**：能实现"作者归属、我的上架、举报封禁"三件事，但不收集任何个人信息。只有当需要"跨设备找回我的上架内容"时才引入手机号——而这个需求可以用"导出恢复码"绕过。

**UGC 上架流程（必须的四道闸）**：

```
用户点"上架" → ①客户端预检（字段长度/敏感词本地词表/必填项）
             → ②服务端机审（文本：name/desc/tags 送内容安全 API）
             → ③人工复审队列（机审存疑 + 抽检）
             → ④上架，附举报入口
                  ↓ 被举报 N 次自动下架进复审
```

**合规要点（Phase C 才涉及）**：
- ICP 备案（域名）+ 隐私政策与用户协议（上架前置）
- 内容审核机制：UGC 平台须落实审核责任，`name`/`desc`/`tags`/昵称四个自由文本字段是风险面
- 举报入口 + 处置时限 + 违规内容留存日志
- 未成年人保护相关要求
- 应用商店上架时通常需说明 UGC 审核机制

> 上述为方向性提示，**Phase C 立项前须由法务/合规角色出具正式清单**，本文档不构成合规意见。

### 4.5 纯本地 P2P 的补充能力（Phase A 加分项）

不需要任何服务器也能做的"社交感"：
- **局域网直传**：同 WiFi 下用 `http ^1.2.2`（✅已有）起一个临时 HTTP server（`dart:io HttpServer`，无需新依赖），对方扫码即取。适合面对面分享多个场景。
- **场景合集文件**：`.stlpack` = 多个场景包的 JSON 数组，一次导入一整套（如"睡眠合集 5 场景"）。这让"民间自制合集"成为可能——用户在社群里传合集文件，等价于一个去中心化的商店。

## 5. 数据模型扩展

### 5.1 核心原则：分享元数据挂在包层，绝不进 `Scene`

这条原则有**代码先例**支撑。`lib/providers/scene/voxel_scene_providers.dart:11-13` 的注释记录了同类裁决：

> A2 已裁决：2.5D 音效保存为**独立音效层**（不入 `Scene.soundscapePath`，避免污染既有场景数据）。

同理，作者/标签/点赞/下载量这些**与场景本体无关的社交属性**，一个字段都不应加进 `Scene`。理由：

1. `Scene` 是渲染与播放的输入，加社交字段会让 `copyWith` 参数表继续膨胀（现已 22 字段 + 5 个 clear 标志）
2. 点赞/下载量是**服务端权威数据**，放进本地持久化的 `Scene` 里必然产生脏数据
3. **最关键**：`Scenes.decodePack` 只读 `schema` 和 `scene` 两个键（`scene_api.dart:47-58`【已验证】），**顶层新增 `meta` 键对老版本完全无感**——挂在包层是零成本的前向兼容，塞进 `Scene` 则会污染每一条本地场景记录

### 5.2 完整分享包结构

```json
{
  "schema": 1,
  "scene": { "...": "Scene.toJson() 原样（已脱敏）" },
  "meta": {
    "v": 1,
    "cid": "a7k2m9f3e1b8",
    "author": { "aid": "anon_9f2c...", "nick": "夜航船" },
    "tags": ["助眠", "雨天", "低饱和"],
    "createdAt": 1754800000000,
    "appVer": "0.26.8+9",
    "license": "cc-by-nc",
    "origin": "user",
    "stats": { "likes": 0, "downloads": 0, "favs": 0 }
  }
}
```

### 5.3 `ShareMeta` 字段定义

| 字段 | 类型 | 权威方 | 说明 |
|---|---|---|---|
| `v` | int | 客户端 | meta 自身版本，独立于 `schema`。未知版本 → 整个 meta 降级为 null，**不影响 scene 解析** |
| `cid` | String | 客户端（可复算） | 内容指纹：`sha256(规范化 scene JSON)` 取前 12 位十六进制。用 `crypto ^3.0.6`（✅已有） |
| `author.aid` | String | 客户端 | 匿名 ID，本地 UUID，**不含任何个人信息** |
| `author.nick` | String | 客户端 | 昵称，≤16 字符，属审核风险面 |
| `tags` | List\<String\> | 客户端 | **枚举白名单**，非自由文本（见下） |
| `createdAt` | int | 客户端 | 毫秒时间戳 |
| `appVer` | String | 客户端 | 产出版本，排障用（对应 `core/app_version.dart`） |
| `license` | String | 客户端 | 授权声明，见 §7 R-2 |
| `origin` | String | 客户端 | `builtin` / `user` / `official` |
| `stats` | Object | **服务端** | 客户端只读缓存，本地永不自增；无后端阶段恒为 0 且**不展示** |

#### `cid` 内容指纹的三个用途

1. **去重**：同一个场景被多人分享，`cid` 相同 → 商店合并、导入时提示"你已有这个场景"
2. **短码基础**：Phase C 的 `星璃-A7K2M9` 就是 `cid` 前 6 位的展示形式，无需另建 ID 空间
3. **完整性校验**：导入时重算 `cid` 比对，不符即包被篡改或损坏

> **规范化（canonicalization）是 `cid` 正确性的前提**：必须按固定规则序列化后再哈希——键名字典序排序、浮点数固定小数位、剔除所有 null 值、UTF-8 无 BOM。否则同一场景在不同 Dart 版本 / 不同字段顺序下算出不同哈希，去重全盘失效。这一段必须配单测（同一 Scene 构造两次、字段赋值顺序打乱，`cid` 必须相等）。

#### `tags` 必须是枚举白名单，不是自由文本

自由文本标签是**内容审核的最大风险面**（用户可写任意违规词），且会造成"助眠/助眠/睡眠/睡覺"这类语义重复导致筛选失效。

建议白名单按现有 `Scene` 的情绪坐标体系组织，与 `valence`/`energy` 呼应：
- **场景类**：雨天 · 雪 · 森林 · 海洋 · 星空 · 壁炉 · 城市 · 咖啡馆
- **用途类**：助眠 · 专注 · 冥想 · 阅读 · 通勤 · 运动
- **氛围类**：低饱和 · 高对比 · 暖色 · 冷色 · 极简 · 复古

每个场景至多选 3 个。白名单变更随 App 版本走，老版本遇到未知 tag **原样保留但不参与筛选**（前向兼容）。

### 5.4 与体素 `voxelCapture` 的关系

体素方案 §5.3 将新增 `Scene.voxelCapture`（schema 1→2）。对本方案的影响：

- 分享包体积从 645 B → 827 B（原样）/ 350 B → 约 480 B（紧凑），**二维码仍绰绰有余**
- 紧凑线格式加一个 `vx` 短键即可，`VoxelSceneCapture` 的 JSON 本身已是短键设计，无需二次压缩
- `tryFromJson` 的容错语义（不认识的版本返回 null 而非抛错）**正是为跨版本分享设计的**，体素方案 §5.3 原文已明确："场景包可能来自更高版本的 App（分享场景），遇到不认识的 `"v": 2` 直接返回 null 退化成渐变背景，**不能让整个场景解析失败**"
- **商店的缩略图零成本重渲**（§4.3）完全依赖体素的确定性重建能力

→ **J 域与 E 域强耦合**。建议 J-1（分享码）可独立先行，但 J-2 的 C 档（视频）与 J-3 的体素场景商店必须排在 E 域 G-1/G-3 落地之后。

## 7. 风险登记

### R-1 · 本地绝对路径随分享包外泄 —— **最高风险，且当前已存在**

**等级：高｜类型：隐私 + 功能｜状态：现存缺陷**

`Scene.toJson()`（`scene.dart:180-203`）**无条件写出**两个含本地信息的字段：

```dart
'soundscapePath': soundscapePath,   // scene.dart:194
'bgmUri': bgmUri,                   // scene.dart:200
```

而 `Scenes.encodePack` 直接调 `scene.toJson()`（`scene_api.dart:42`），当前 UI 又已经把这个结果**复制到剪贴板**（`custom_scene_list_page.dart:180`）。

**两重危害：**

| 危害 | 说明 |
|---|---|
| **隐私外泄** | `soundscapePath` 是用户选择音频文件时留下的**绝对路径**，在 Windows 上形如 `C:\Users\<真实用户名>\Music\...` —— **用户名、目录结构、甚至音乐品味都随包泄露**。用户完全不知道自己复制给别人的那段 JSON 里有这些。 |
| **功能失效** | 这些路径在对方设备上必然无效。`bgmUri` 若是 Android `content://media/external/audio/media/1234`，到对端会指向一首完全无关的歌，或直接播放失败。 |

**缓解（J-A0 必做，不可延期）：**

```
导出侧 sanitizeOut(scene)：
  soundscapePath → 一律剔除（音频文件不随包走，这是 scene_packer.dart:6-7 已声明的边界）
  bgmUri         → 一律剔除
  bgmTitle/bgmArtist → 保留（纯文本，作为"推荐曲目"线索，导入侧尝试在本地曲库匹配）
  id             → 见 R-3
```

> `scene_packer.dart` 文件头注释原文已经写明了正确边界：「不嵌入媒体资产（封面/音频文件）—— 场景包只存引用（musicSourceId / soundscapePath）」。**但"存引用"在跨设备分享的语境下就是错的**——引用在对端不可解析。设计意图（备份/同步）与实际用法（分享）在这里发生了偏移，必须显式修正。

导入侧对应地在预览页给出提示：「该场景推荐曲目《X》，你的曲库中未找到」/「该场景使用了自定义音景，分享包不含音频文件，将回落为程序合成音景」。

### R-2 · 版权

**等级：高｜类型：法律**

| 风险点 | 说明 | 缓解 |
|---|---|---|
| 视频/动图混入受版权音乐 | 用户导出带 BGM 的视频发到公开平台 = 传播录音制品 | §3.3 已裁决：**默认无声**，可选仅自研合成音景，**不提供 BGM 混音选项** |
| `bgmTitle`/`bgmArtist` 随包传播 | 纯文本曲目名，**不构成侵权**（仅为推荐线索，不含音频内容） | 保留，但导入侧只做本地匹配，不触发任何下载 |
| Minecraft 素材外传 | 项目使用了 Minecraft 音源管线（`docs/TODO_分派方案.md` §四），这些素材有其自身授权约束 | 分享包**不含任何音频字节**（§R-1 已剔除路径），只传参数，天然规避 |
| 用户上架他人作品 | Phase C 才涉及 | `meta.license` 字段 + 上架时勾选原创声明 + 举报下架 |
| 商店场景的授权 | Phase B/C | 官方场景标 `origin:"official"`；用户投稿默认 `cc-by-nc`，上架页明示 |

### R-3 · 场景 id 冲突与覆盖攻击

**等级：中｜类型：数据完整性｜状态：现存缺陷**

`CustomScenesNotifier.save()`（`scene_custom_providers.dart:51-55`）的语义是 **upsert**：

```dart
final List<Scene> rest = state.where((s) => s.id != scene.id).toList();
state = [...rest, scene];
```

同时 `scenesProvider`（`scene_providers.dart:151-165`）规定：**非 `custom_` 前缀的自定义场景会覆盖同 id 的内置场景**。

→ **一个精心构造的分享包，若 `id == "starnight"`，导入后会静默覆盖用户的内置「星夜」场景**，且内置场景不支持删除（`scene_custom_providers.dart:57` 注释），用户很难恢复。

**缓解（J-A0）**：导入时**一律重写 id**为 `custom_<timestamp>_<cid前6位>`，绝不信任包内 id。分享包中的 `id` 仅作为 `cid` 计算的输入，不用于写入。这条同时解决了"同一个场景导入两次互相覆盖"的问题。

### R-4 · 恶意 / 损坏包导致渲染异常

**等级：中｜类型：稳定性**

`Scene.fromJson`（`scene.dart:205-234`）做了**类型兜底**（`as String? ?? ''`、`as num?)?.toDouble() ?? 0.5`），但**没有做值域校验**。已核查的边界：

| 输入 | 现有防护 | 结论 |
|---|---|---|
| `gradientColors: []` | `card_stack.dart:248` 有 `colors.isNotEmpty` 判断 → 回落中性深色渐变 | ✅ 已防护 |
| `stops` 长度 ≠ `colors` 长度 | `card_stack.dart:254` `stops.length == colors.length ? stops : null` | ✅ 已防护 |
| `gradientColors` 仅 1 个颜色 | `isNotEmpty` 为真 → 进入 `LinearGradient(colors: [c])` 分支 | ⚠️ **单色渐变在 dart:ui 层不被支持【需实测】** |
| `valence`/`energy` = 1e9 | 无校验 | ⚠️ 污染 `SceneOrderService.emotionalDistance`（`scene_order_service.dart:22-26` 欧氏距离），可能导致排序逻辑异常 |
| `stops` 含 NaN / 超出 [0,1] / 非递增 | 无校验 | ⚠️ 渐变绘制异常【需实测】 |
| `name`/`desc` 超长（10 万字符） | 无校验 | ⚠️ 布局撑爆 + `shared_preferences` 膨胀 |
| `visualWeight` = -5 | 无校验 | ⚠️ 视觉参数异常 |

**缓解（J-A0，`share_sanitizer.sanitizeIn`）**：

```
gradientColors : 长度 < 2 → 补足为 2（复制首色或填默认）；长度 > 8 → 截断
stops          : 长度≠colors 或含 NaN/越界/非递增 → 整体丢弃（置 null，走等分）
valence/energy : clamp(0.0, 1.0)
visualWeight   : clamp(0.0, 1.0)
name           : 截断 ≤ 24 字符，且非空（空则填「未命名场景」）
mood/desc/track/artist/soundscape : 截断 ≤ 64 / 120 字符
glyph          : 截断 ≤ 2 字符
icon           : 不在已知 AppIcon 白名单内 → 回落 'star'
particleMotion : 不在 {rain,snow,fireplace,ocean,starnight,dust} 内 → 置 null
tags           : 不在白名单内的丢弃，至多保留 3 个
整包            : 原始字符串 > 64 KB 直接拒收（防 DoS）
```

**净化在解析之后、写入之前**，且导入预览页展示的就是净化后的结果——用户看到什么就存什么。

### R-5 · 存储与流量成本

**等级：低（Phase B）/ 中（Phase C）**

| 阶段 | 存储 | 流量 | 说明 |
|---|---|---|---|
| Phase A | 0 | 0 | 无服务器 |
| Phase B | 1000 场景 ≈ 850 KB（含 index） | index 200 KB × DAU（ETag 后趋近 0） | **因缩略图本地重渲，成本近乎为零**（§4.3） |
| Phase C | 同上 + 用户上传 | 同上 | 若将来允许上传自定义音频/图片，成本会跳变 2~3 个数量级 |

**关键成本闸门**：**永远不要允许用户上传音频文件或图片到商店。** 一旦开这个口子，存储从 KB 级跳到 GB 级、CDN 流量指数上升，同时引入音频版权审核（比文本审核难得多）。场景商店只交易**参数**——这既是成本控制，也是版权隔离。

### R-6 · UGC 内容合规（Phase C）

**等级：高（一旦启动）｜类型：法律 + 运营**

风险面是四个自由文本字段：`scene.name` / `scene.desc` / `meta.author.nick` / 自定义 tag（若开放）。

| 义务 | 说明 |
|---|---|
| 内容审核 | 机审（内容安全 API）+ 人工复审 + 抽检 |
| 举报处置 | 举报入口、处置时限、结果反馈 |
| 违规留存 | 违规内容与处置记录留存 |
| 实名相关 | 平台侧账号实名要求 |
| 未成年人保护 | 相关保护机制 |
| 备案与协议 | ICP 备案、隐私政策、用户协议 |

**这是本方案建议卡在 Phase B 的核心原因**：审核是持续性人力投入，对一个 P3 优先级的功能而言，投入产出严重失衡。

**降级缓解**：`tags` 用枚举白名单（§5.3）、`name`/`desc` 长度受限、投稿走站外人工收口（§4.2）—— 三招合起来可以在**不建 UGC 后端**的前提下获得社区内容供给。

### R-7 · 跨版本兼容断裂

**等级：中｜类型：兼容性**

分享码一旦流入互联网就**永久存在**——两年后的 App 仍可能被要求解析今天生成的码。

| 缓解 | 说明 |
|---|---|
| `minSupportedSchema` 区间兼容 | 永不上调下限；旧包必须永远能读（§2.6） |
| 字段级降级 | 新增可空复合字段一律用 `tryFromJson` 语义（体素方案 §5.3 先例） |
| 线格式与 schema 解耦 | `STLn` 与 `packSchemaVersion` 独立演进（§2.3） |
| 未来包可读提示 | 不抛裸 `FormatException`，提示"请升级星璃"（§2.6） |
| 往返一致性单测 | 每次改 `Scene` 字段必须跑（防止 `toJson`/`fromJson` 漂移） |
| **黄金样本测试** | 在 `test/fixtures/` 固化若干**历史版本**的真实分享包字符串，每次 CI 必须能解析成功。这是防止兼容性静默断裂的唯一可靠手段 |

### R-8 · 导出性能与内存

**等级：中｜类型：稳定性**

1080p RGBA 单帧 7.9 MB，150 帧全内存 = 1.2 GB → **必然 OOM**。缓解见 §3.3（流式编码、分辨率分档、≤3 帧常驻、进度可取消、导出期暂停实时背景 timer）。

另需注意工程已知坑（`PROJECT_STATE.md` §四-2）：**磁盘满会导致 Flutter 工具链异常**。导出前应检查可用空间，落盘失败要给出明确提示而非静默失败。

### R-9 · 商店内容质量与冷启动

**等级：中｜类型：产品**

一个空荡荡或全是低质内容的商店比没有商店更伤体验。

缓解：Phase B 全部是**官方精选**，从源头保证质量；首发至少 20~30 个高质量场景；Phase C 上线后仍保留"官方精选"分区置顶，并用 `origin` 字段区分 `official` / `user`。
