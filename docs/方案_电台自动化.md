# 电台自动化能力 · 方案（无人值守自动电台）

> 需求来源（2026-08-31 用户规格，7 条）：
> **① 电台容忍 3 秒延时　② 由服务器中转　③ 可无人主持　④ 重连自动归主　⑤ 音源自搜索　⑥ 歌单定时式排歌　⑦ 房主排歌**
>
> 模块定位：`xingli_music` 社交模块「电台房」体系的自动化升级（在既有 PRD_电台核心 底座上扩展，不推翻现有一起听/点歌/世界联机）。
> 关联文档：[PRD_电台核心](./social/PRD_电台核心.md) · [一起听 PRD](./social/PRD_一起听系统.md) · [校园点歌 PRD](./social/PRD_校园点歌系统.md) · [README_社交模块](./social/README_社交模块.md)
> 状态：方案稿 v0.1，待评审（实施前需用户确认里程碑与隐私边界）。

## 1. 需求 ↔ 现状映射

| # | 需求 | 现状 | 判定 |
|---|---|---|---|
| ① | 容忍 3 秒延时 | NF-1 稳态 <1.5s（弱网放宽 3s） | **已具备**，明确定义为「3s 同步窗口」即可 |
| ② | 由服务器中转 | relay-server 跨公网中转（OQ-2 已决） | **已具备**（沿用 wss://relay.245959623.xyz） |
| ③ | 可无人主持 | 无：房主（DJ）离线 → 房间清空即下线 | **新增**：服务端托管「虚拟 DJ」 |
| ④ | 重连自动归主 | 无：房主断线无归主逻辑（重连仅客户端侧） | **新增**：房主凭 hostId 自动恢复 DJ |
| ⑤ | 音源自搜索 | 聚合搜索已有（`aggregate_search_sheet`）；`listenState` 已同步 uri | **新增**：自动 DJ 按规则选源 |
| ⑥ | 歌单定时式排歌 | 无时间表概念；点歌队列为「人审」模式 | **新增**：编排队列 + 定时自动切歌 |
| ⑦ | 房主排歌 | DJ 独占控制权 + 点歌审核 | **扩展**：房主可编辑「播放编排队列」 |

**一句话**：把现有「有人主持的点歌电台」升级为「**房主离线也能自动播出的无人值守电台**」，延时窗口 3s、跨公网中转。

## 2. 总体设计

### 2.1 拓扑演进（服务端托管 + 各端跟随）

```
现状：  [房主/DJ] ──(listenState)──> relay  ──(扇出)──> [听众…]
升级：  [虚拟 DJ（relay 内嵌调度器）] ──(listenState/schedule)──> [房主 + 听众…]
        ↑ 房主在线时以房主为准；离线时虚拟 DJ 接管，房主回归自动恢复
```

- **播放真值源两级**：房主在线 → 房主 `AudioService` 为真值（现有逻辑不变）；房主离线（或「自动模式」开启）→ 服务端调度器按编排队列 + 时间表定时广播 `listenState`。
- **relay 服务端角色扩展**：从「纯路由转发」升级为「可选的房间编排托管」（房间配置时声明 `autoDJ=true` 才启用；否则保持纯转发，隐私/行为零回归）。

### 2.2 三条新机制

| 机制 | 说明 | 承载端 |
|---|---|---|
| 房主保活 | 房主断线后房间**不销毁**，保留 TTL（如 10 min）；房主重连凭原 hostId 自动恢复 DJ | relay |
| 虚拟 DJ 调度 | 编排队列（曲目 uri + 顺序/权重）+ 时间表（可选定时档），到点自动广播下一曲 | relay |
| 归主协商 | 房主回归 → 服务端把控制权交还房主，停止虚拟广播 | relay + session_provider |

## 3. 服务端扩展（tools/relay_server/relay_server.dart）

### 3.1 房间生命周期（核心改动）
- 创建时新增可选字段：`autoDJ`（是否无人值守）、`ttl`（房主离线保活秒数，默认 0 = 不保活，保持现状）、`schedule`（编排队列 JSON，首版可选）。
- 房主断线：`_removeClient` 不再立即清房——若 `autoDJ` 且 TTL>0，房间转入「托管态」：保留 `_RoomMeta`，记录 `hostId`，启动 TTL 倒计时（到点无房主回归才销毁）。
- 房主回归：relay `join` 时带 `hostId`，若与托管房记录匹配 → 恢复 host 元数据，广播 `peerHostBack`，虚拟调度器停。

### 3.2 虚拟 DJ 调度器
- 每房一个轻量调度器（`Timer`）：按编排队列顺序播放，曲目之间间隔 = 当前曲目时长（未知时长用默认档位）。
- 广播 `listenState`（沿用现有消息结构与字段：uri/title/artist/sourceId/playing/pos），听众端**无需改动**即可跟随。
- 队列耗尽：按策略循环（首版：重复队列；或静音等待房主回归）。
- **边界（隐私）**：relay 只存编排元数据（uri 列表/时间表），**不缓存音频流**——沿用 NF-4「relay 不存储内容」，仅放宽为「可存房间编排元数据」。见 §6 待确认。

### 3.3 音源自搜索（服务端侧）
- 服务端不做搜索（避免放大 relay 职责与合规风险）；**音源自搜索落到客户端自动 DJ**（见 §4.3）：房主端/虚拟 DJ 端用现有聚合搜索按规则自动取歌进编排队列。
- 若首版不做客户端自动 DJ，则「音源自搜索」退化为「房主用聚合搜索手动加歌 + 队列循环」——两种口径在 §6 待确认。

## 4. 客户端扩展（lib/）

### 4.1 协议（net_message.dart）
新增 `NetMsgType`（追加在枚举尾部，不重排既有索引）：
```
roomMetaUpdate   // 服务端→房内成员：托管态/编排队列变更（title/autoDJ/ttl）
peerHostBack     // 服务端→房内成员：房主回归，虚拟广播结束
scheduleSet      // 房主→服务端：设置编排队列/时间表
scheduleSnapshot // 服务端→新成员/房主：当前编排队列快照
```
复用既有：`listenState`（播放跟随）、`orderQueue/orderDecision`（点歌审核）、`chat`。

### 4.2 归主（session_provider.dart）
- `host()` 在 relay 模式记录并携带 `hostId`（房间创建即持久化；本地可存 SharedPreferences 以便重连带回）。
- 新增重连归主路径：房主断线后不 `leave`（用户主动离开仍正常退房），触发 `_beginReconnect` 的 **host 版**——以原 hostId 重连 join，relay 识别后自动恢复 DJ（`role=host, dj=true`），世界/房间状态保留。
- 客户端断线：沿用现有重连逻辑；重连成功后服务端若有 `peerHostBack` 缓存则回放。

### 4.3 音源自搜索 + 自动 DJ（客户端）
- 新增「自动播」开关（房主侧）：开启后房主端用现有聚合搜索自动取歌（按关键词/曲库随机/歌单），写入编排队列并 `scheduleSet` 上传。
- 房主离线后，服务端虚拟 DJ 按该编排队列继续广播（满足「可无人主持」）。
- 房主端在线时也可随时手动接管（⑦ 房主排歌）。

### 4.4 UI（station_room_page / station_lobby_page）
- 创建电台新增：**无人值守（自动播）开关** + TTL 提示。
- 房内新增：编排队列面板（房主可增删/排序/设置定时档 → ⑦）；托管态角标（「无人值守播出中」）；房主回归 toast。
- 大厅公开房间列表展示 `autoDJ` 标记（无人值守电台）。

## 5. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| M1 | relay 房主保活 + 归主协议（roomMetaUpdate/peerHostBack）+ 客户端 host 版重连归主 | 房主拔线重连自动恢复 DJ；房间 TTL 内不销毁 |
| M2 | 虚拟 DJ 调度器（编排队列 + listenState 广播）+ scheduleSet/scheduleSnapshot | 房主离线后听众仍跟随自动播出 |
| M3 | 客户端自动选源（聚合搜索接入）+ 房主排歌 UI + 大厅 autoDJ 标记 | 无人值守电台全链路：开台→自动播→房主回归接管 |
| M4 | 定时式排歌（时间表档：如整点/每日固定节目）+ 音源自搜索策略可选 | 定时排歌生效 |

> 各阶段独立可交付、向后兼容；未开 `autoDJ` 的房间行为与现状完全一致（回归面受控）。

## 6. 待确认（评审点）

1. **隐私边界**：relay 允许存储「房间编排元数据」（uri 列表/时间表）是否可接受？（音频流仍不缓存；现状 NF-4「relay 不存储内容」需放宽为「不存音频」）
2. **音源自搜索口径**：A）客户端自动 DJ 用聚合搜索自动选源（推荐，符合「音源自搜索」）　B）仅房主手动加歌 + 队列循环（更保守）。
3. **自动 DJ 版权/来源**：自动选源仅限已配置音源（本地/Subsonic/公开电台/已授权网络源），不做第三方代理源——对齐白皮书铁律。
4. **里程碑顺序**：是否按 M1→M4 逐步实施，还是先做 M1+M2（无人值守最小闭环）验证？
