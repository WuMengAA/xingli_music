### 1. 是否授权重编译并重启 relay？

**现状**：计划任务 `XingliRelayAutostart`（运行中）指向 `tools/relay_server/relay_server.exe`，
但该文件时间戳为 **8/28 03:03**，早于 cl10/cl11/cl12 全部能力层工作。
实测 `127.0.0.1:8092/api/capabilities` 与公网同名路径均返回 **HTTP 200 + 0 字节**。
→ 客户端拉不到能力清单，cl10～cl12 的能力层、内容来源页、搜索开关在真机上均不生效
（解析层走「清单里没有 → 放行」兜底，功能不崩但也用不上新东西）。

**选项**
- A. 授权执行：`dart compile exe relay_server.dart -o relay_server.exe` 后重启服务
- B. 暂缓，等我先确认影响面（域名上已有注册用户，重启会短暂中断中继与多设备同步）
- C. 换个端口先起新版验证，确认无误再切

**结论（2026-08-29）**：**C** —— 先在新端口起重编后的 relay，验证 `/api/capabilities` 返回完整清单，确认无误再切公网。已建任务 T1 跟进。

**已落地（2026-08-29 15:53）**：新版 `relay_server_new.exe` 在端口 18092 验证通过（完整 8 项能力、全部 `enabled`，仅 `netease.playlist` 为 `planned`）。
关键反直觉发现：**旧 exe 返回「0 字节」并非能力层代码 bug，而是旧 exe（8/28 03:03）本身过期**——同份源码重编译后 18092 完全正常。
故走最短路径：停 `XingliRelayAutostart` → 备份旧 exe（`relay_server_old.exe`）→ 替换 `relay_server.exe` → 重启任务（仍 8092）→ 验证公网路径 `127.0.0.1:8092/api/capabilities` 已返回完整清单。**已切换公网，cl10–cl12 能力层对用户正式可见。**

## 二、产品定位 —— 决定后续所有方向，越晚定代价越大

### 3. 产品重心：本地优先，还是聚合多源？

**现状**：白皮书 1.1 原文——「不做『私有云版酷狗』，要做『**本地文件的智能策展人**』」。
但代码实际已明显偏向多源聚合：能力清单 8 项里本地曲库只占 1 项，
近三版新增的全是服务端下发内容与第三方源。

**选项**
- A. 维持白皮书定位：本地优先，服务端内容与第三方源是补充
- B. 承认演进：产品重心已转向聚合多源，反过来修订白皮书
- C. 双轨但明确主次：本地曲库是主场，其余是「可选内容源」

**结论（2026-08-29）**：**B（按用户补充界定）** —— **不搞第三方代理源（不稳定、不安全）**。
产品路线回到「本地优先 + 自建后端 + 自有内容 + 用户自登录获取音源」：
netease / bilibili 走**用户凭据**（credentialOwner=client），服务端**不**做第三方内容代理，
只下发自有内容（scenes/playlists/notices/random）。白皮书据此修订。已建任务 T3。

### 4. `content.random` 是否违反「不做云端推荐」？

我们却做了 `content.random`（服务端下发随机内容）。同时白皮书指定的替代方案
「本地语义随机」在代码里**查不到**。

**选项**
- A. 保留 `content.random`，视为「编辑精选」而非「算法推荐」，白皮书相应放宽表述
- B. 改名（如 `content.daily`）并弱化推荐语义
- C. 移除，改为实现本地语义随机
- D. 保留服务端随机 + 补做本地语义随机（两者并存）

**结论（2026-08-29）**：**D** —— 服务端随机（编辑精选，运营可控）与**本地语义随机**（离线可用、数据主权）并存。
已建任务 T4，本地语义随机必须真做，否则白皮书差异化决策落空。

## 三、架构分歧 —— 与并行会话直接冲突

### 5. `netease.recommend` 到底服务端实现还是客户端执行？

**现状**：我（本会话）在 cl11 判定走**客户端执行**，理由有二：
1. 客户端 8/15 起已有完整实现（weapi 加密 + `recommendSongs()` + webview 登录），服务端再写一遍 = 同一套逻辑维护两份
2. 服务端代理意味着用户 cookie 必须出网，与「服务端不持账号资产」直接冲突

但记忆文件里**另一会话留下的计划**明确写着「服务端实现 netease.recommend
（需把客户端 `netease_crypto.dart` 的 weapi 加密在服务端重写一份）」——结论相反。

**选项**
- A. 客户端执行（我的判断）
- B. 服务端实现（另一会话的计划）
- C. 客户端执行为主，服务端仅做无状态转发

**结论（2026-08-29）**：**C（用户补充）** —— 客户端执行为主，服务端仅做**无状态转发**；
仅「部分特殊」场景才需要服务端代理。与第 6 条协同：weapi 仍只在客户端，服务端不重写加密。
已建任务 T5。

## 四、产品细节

### 7. B 站搜索的登录门槛要不要解耦？

**现状**：实测 B 站 WBI 搜索**免登录即可返回数据**（code=0、20 条结果、无 -412 风控）。
但 UI 里 `_buildBilibili()` 强制要求登录才搜索。推测原因：无 cookie 只能拿到低码率音频流，
登录影响的是**播放音质**而非搜索能力。能力清单已按事实标为「不需要凭据」。

于是出现不一致：清单说不用登录，界面却拦着。

**选项**
- A. 解耦：允许免登录搜索，仅在播放时提示「登录后可播更高音质」
- B. 维持现状：搜索仍需登录（保证播放体验一致）
- C. 免登录搜索，但结果行标注音质提示

**结论（2026-08-29）**：**C** —— 免登录搜索，结果行标注音质提示（如「登录后更高音质」）。
已建任务 T7。

**现状**：C 盘 120G 用满（**仅剩 252K**），构成 Users 41G / Windows 37G / Program Files 32G

另注：构建脚本里批量删文件会被安全护栏拦下（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`），
改用 mtime 新鲜度校验后已解决——但 C 盘问题本身没解决。

**选项**
- A. 磁盘清理「清理系统文件」+ `DISM /Online /Cleanup-Image /StartComponentCleanup`
- B. 只清 `C:\dumps`（3.1G，崩溃转储，通常安全）
- C. 暂时不处理，继续用 TEMP 迁 D 盘的方案

**结论（2026-08-29）**：先**查多余 flutter 缓存**释放空间，**严禁触碰敏感内容**（密钥、用户数据、源码）。
仅分析报告，不擅自删除系统/敏感文件。已建任务 T9。
