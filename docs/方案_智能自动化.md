# 星璃音乐 · 智能与自动化 技术方案

> 版本：v1.0 · 日期：2026-08-10 · 基线：`0.26.8+9`（Flutter 3.44.8 / flutter_riverpod ^2.6.1）
> 范围：AI 歌单推荐 · 睡眠定时器 · 自动切场景（时间/天气/心率）· 语音控制
> 性质：**技术方案文档，不含代码实现**。所有类名 / Provider 名均引自当前 `lib/` 真实代码，新增命名以 `【新增】` 标注。
> 关联：`docs/PROJECT_STATE.md`（状态快照）、`docs/API_CONTRACT_FROZEN.md`（命名冻结契约）、`docs/ARCHITECTURE_V2_增量.md`（v2 架构）

## 0. 结论先行

### 0.1 优先级排序（推荐落地顺序）

| 序 | 功能 | 优先级 | 理由 | 预估 |
|---|---|---|---|---|
| **1** | **睡眠定时器** | **P0** | 依赖最少、闭环最短、用户价值即时；只需 1 个 Notifier + 已有 `AudioService` 淡出能力；顺带补齐引擎缺失的 `stop()` | **2.5 人日** |
| **2** | **AI 歌单推荐（本地规则引擎）** | **P0** | `Scene.valence/energy` 已存在但**当前 `RecommendPage` 根本没用**（只做文本重合度）；补齐即见效，零新依赖、零隐私风险 | **6 人日** |
| **3** | **自动切场景 · 时间触发** | **P1** | 无需权限、无需网络、100% 可靠；先把规则引擎骨架立起来，后续触发源都是插件式接入 | **4 人日** |
| **4** | **自动切场景 · 天气触发** | **P1** | 需联网 + 定位权限 + 外部 API 依赖；但降级路径清晰（失败即不触发） | **3.5 人日** |
| **5** | **自动切场景 · 心率/光线触发** | **P2** | **原生侧必须改造**（现为单次读取，非持续流）；且多数手机无心率传感器，覆盖面极小 | **5 人日**（含原生改造） |
| **6** | **语音控制** | **P2** | 成本最高、准确率风险最大、需 `RECORD_AUDIO` 权限；建议走系统 STT，**明确不做 on-device Whisper** | **8 人日** |

**总计约 29 人日**（单人，含自测；不含 QA 与真机回归）。

### 0.2 三个关键判断

1. **推荐不需要云端 LLM/embedding。** 曲库是本地/自建源，规模在 10² ~ 10³ 量级，`Scene` 已有 `valence/energy` 二维情感坐标，`SceneOrderService.emotionalDistance()` 已有现成的欧氏距离算法。**本地规则引擎 + 元数据启发式打标**足以覆盖 80% 场景，云端方案的收益/成本比在本项目为负（见 §2.5）。
2. **自动切场景的最大工程量不在规则引擎，而在传感器数据源的可靠性。** 现有 `SensorService.lightLux()` / `heartRate()` 走 `MethodChannel.invokeMethod().asStream()`，原生 `MainActivity.readSensor()` **读一次即 `unregisterListener`** —— 它是**一次性 Future 伪装成的 Stream**，不能作为持续触发源。这是必须先解决的前置改造（见 §4.4）。
3. **语音控制走系统 STT（Android `SpeechRecognizer`）而非 on-device Whisper。** Whisper 最小可用量化模型 ~40MB+，而当前 debug APK 已 157MB、目标平台含 Wear OS / 低端机（项目已有 `PerformanceMode.powerSave` 专门应对发热），引入端侧 ASR 推理与本项目「省电优先」的既定取向直接冲突（见 §5.1）。

## 1. 现状盘点（基于真实代码）

### 1.1 Scene 情感模型 —— 可直接复用的资产

`lib/models/scene.dart` 的 `Scene` 已具备完整的情感维度：

| 字段 | 类型 | 说明 | 智能化用途 |
|---|---|---|---|
| `valence` | `double` 0~1 | 情绪效价（低沉 ↔ 明亮） | **推荐匹配主维度 / 自动切场景目标坐标** |
| `energy` | `double` 0~1 | 能量强度（静 ↔ 动） | **推荐匹配主维度 / 心率映射目标** |
| `mood` | `String` | 氛围词（'静默' '湿润' '呼吸' '温暖' '余晖' '寂静' '深邃'） | 文本匹配辅助 / 语音指令别名 |
| `desc` | `String` | 场景描述文案 | 文本匹配辅助 |
| `track` / `artist` | `String` | 场景默认曲目名 | 已被 `PlaybackActions._sceneDefaultTrack()` 使用（R6） |
| `musicSourceId` | `String?` | 专属音源（`snow`/`ocean` → `'minecraft'`） | **推荐时的硬过滤条件** |
| `bgmUri`/`bgmTitle`/`bgmArtist` | `String?` | 场景默认 BGM | 自动切场景后的选曲兜底 |
| `visible` | `bool` | 是否在列表显示 | **自动切场景时必须过滤 `visible == false`** |

7 个内置场景（`builtInScenes`）的情感坐标分布：

| 场景 id | 名称 | valence | energy | 象限特征 |
|---|---|---|---|---|
| `starnight` | 星夜 | 0.45 | 0.12 | 中性 · 极静 |
| `rain` | 雨 | 0.35 | 0.25 | 偏低沉 · 静 |
| `forest` | 森林 | 0.60 | 0.35 | 偏明亮 · 偏静 |
| `fireplace` | 壁炉 | 0.75 | 0.50 | 明亮 · 中 |
| `dusk` | 黄昏 | 0.55 | 0.40 | 中性偏亮 · 中 |
| `snow` | 雪 | 0.40 | 0.10 | 偏低沉 · 极静 |
| `ocean` | 海底 | 0.30 | 0.20 | 低沉 · 静 |

> ⚠️ **分布观察**：7 个场景 `energy` 全部 ≤ 0.5、`valence` 全部在 0.30~0.75。这是一个「安静/氛围向」的产品定位，**自动切场景的目标坐标计算不能假设 0~1 全域均匀分布**，映射函数必须做区间压缩（见 §4.6），否则任何高能量输入都会被吸附到 `fireplace`。

现成算法资产 —— `lib/services/scene_order_service.dart`：
- `SceneOrderService.emotionalDistance(Scene a, Scene b)`：`(valence, energy)` 二维欧氏距离，**推荐与自动匹配可直接复用同一距离度量**，保证全局一致性。
- `SceneOrderService.isBright(Scene s)`：`valence >= 0.5`。
- 常量 `minAdjacentDistance = 0.10` / `maxAdjacentDistance = 0.55`：已定义「情绪距离过近＝没区别」「过远＝跳变」的经验阈值，**自动切场景的迟滞阈值应与之对齐**，不要另立一套。

### 1.2 Track 模型 —— 核心缺口

`lib/models/track.dart` 的 `Track` **没有任何情感/声学维度字段**：

```
title / artist / uri / source(TrackSource) / sourceId / isLiveStream
coverUrl / album / duration / coverPath / extras(Map<String,dynamic>?)
```

**这是 AI 推荐的第一性障碍**：场景侧有 `(valence, energy)`，曲目侧没有，无法做同空间匹配。§2.3 给出三条打标路线。

> 🟢 **有利条件**：`Track.extras` 是 `Map<String, dynamic>?` 且已在注释中定位为「数据源私有字段」。特征可挂在 `extras` 上做**渐进式增强**，无需修改 `Track` 构造签名，向后兼容成本为零。

### 1.3 传感器现状 —— 「伪 Stream」问题

| 层 | 文件 | 事实 |
|---|---|---|
| 原生 | `android/app/src/main/java/com/stelarith/xingli_music/MainActivity.java` | `MethodChannel("com.stelarith.xingli_music/sensors")`，方法 `lightLux` / `heartRate`；`readSensor()` 在 `onSensorChanged` 首次回调后**立即 `unregisterListener`** —— 单次读取语义 |
| 服务 | `lib/services/sensor/sensor_service.dart` | `lightLux()` / `heartRate()` = `invokeMethod().asStream()` → **只发一个值就结束**；`gyroscope()` 走 `sensors_plus`（真流）；`shakeDetected()` 走 `accelerometerEventStream()`（真流，含 2.2 阈值 + 800ms 冷却） |
| Provider | `lib/providers/explore/sensor_providers.dart` | `sensorServiceProvider` / `lightLuxProvider` / `gyroscopeProvider` / `heartRateProvider` / `shakeDetectedProvider` / `sceneBrightnessMaskProvider` / `shakeSceneLinkProvider` / `shakeSceneEnabledProvider` / `shakeSceneMessageProvider` / `sceneShakeNotifierProvider` |
| 联动 | 同上 · `SceneShakeNotifier.nextScene()` | **唯一已实现的传感器→场景联动**：切下一个场景 + `audioServiceProvider.switchSoundscape()` + 写 `shakeSceneMessageProvider` 文案 |

**结论**：
- ✅ 摇一摇 → 切场景**已跑通**，`SceneShakeNotifier` 是自动切场景执行器的**现成范式**，直接沿用其结构。
- ❌ 光线 / 心率**不能用于持续触发**（只有冷启动那一个值）。必须改造为 `EventChannel` 持续流（§4.4）。
- ❌ **手表适配未做**：`SensorService` 的 `_isAndroid` 判断不区分 Wear OS；Wear OS 才是心率传感器的真实载体（手机侧 `TYPE_HEART_RATE` 命中率接近 0）。
- ⚠️ `AndroidManifest.xml` **已声明** `BODY_SENSORS`，但 `PermissionService` 的 `requestAll()` / `overview()` **未包含它** —— 心率读取在 Android 6+ 会静默失败（返回 null，被 `handleError` 吞掉）。这是现存缺陷。

### 1.4 Provider 架构模式（必须遵循的既有范式）

从 `lib/providers/settings/`、`lib/providers/explore/` 归纳出的三层模式：

```
Service（纯 Dart，无 Riverpod 依赖）
  ↓  由 Provider 包一层，ref.onDispose 注册清理
Provider（状态暴露 / 派生）
  ↓  StateProvider 存原子状态；Provider 存派生值；StreamProvider 存流
Repository（SharedPreferences 收口持久化）
  ↓  restoreSettings() 冷启动灌入 + settingsSyncProvider 运行期写回
```

关键约定（**违反即引入既有坑**，见 `PROJECT_STATE.md` §四）：

| # | 约定 | 出处 |
|---|---|---|
| C1 | **Provider 初始化期禁止修改其它 Provider**。冷启动恢复做成普通函数 `restoreSettings(WidgetRef)`，由 `AppShell.initState` 帧后回调调用 | `settings_persistence_providers.dart:27` |
| C2 | **默认值内置、不读 prefs**。如 `performanceModeProvider` 注释所述：纯组件/测试环境无 prefs 注入也能 watch | `performance_providers.dart:33` |
| C3 | **所有持久化收口 `SettingsRepository`**，禁止散落调用 SP；键名统一 `settings.*` 前缀 | `settings_repository.dart:9` |
| C4 | **副作用 Provider 靠 `AppShell.build` 顶层 `ref.watch` 保活**（如 `settingsSyncProvider` / `eqReapplyOnPlayProvider`） | `app_shell.dart:131` |
| C5 | **所有 Stream 订阅必须在 `dispose` 取消**，防泄漏/耗电 | `sensor_service.dart:22` |
| C6 | **UI 只调意图**，不直接操作引擎；播放动作统一走 `playbackActionsProvider` | `playback_notifier.dart:14` |
| C7 | 服务层异常**一律捕获降级、不向上抛**（Wear OS/低端机 `PlatformException` 会闪退） | `audio_service.dart:_safe` |

复杂状态则用 `StateNotifierProvider` + JSON 持久化，范式见 `ExperimentConsentNotifier`（key `experiment_consent_v1`，`_load()` / `_persist()` 成对）。

### 1.6 现有「智能」实验的真实完成度

| 实验 id | 页面 | 声称 | **实际** |
|---|---|---|---|
| `recommend` | `RecommendPage` | 「按当前场景情绪推荐曲目」，注释写「优先推荐与场景情绪距离近的曲目」 | ❌ **名不副实**：`_recommend()` / `_score()` 只做 `scene.name+mood+desc` 与 `track.title/artist` 的**字符串包含判断**（命中 +3 / +1），`valence`/`energy` **一次都没读**。且 `sceneText.contains(title)` 方向反了（场景描述包含曲名，几乎恒为 false）—— 实际等价于**原序返回全库** |
| `mood` | `MoodAnalysisPage` | 问卷 → 心情匹配 | ✅ **真实可用**：5 题 → `valence = (a0+a2+a4)/9`、`energy = (a1+a3)/6` → 遍历 `sceneOrderProvider` 取**曼哈顿距离**最小场景 → 写 `currentSceneIndexProvider` + `switchSoundscape()`。**这就是自动切场景的最小可用原型** |
| `sensor` | `SensorPage` | 光线/加速度 → 场景联动 | ⚠️ 仅摇一摇联动可用；光线仅用于 `sceneBrightnessMaskProvider`（视觉遮罩），未接场景切换 |

> 📌 **重要发现**：`MoodAnalysisPage._analyzeAndSwitch()` 用的是**曼哈顿距离** `|Δv| + |Δe|`，而 `SceneOrderService.emotionalDistance()` 用的是**欧氏距离**。同一产品内两套度量，应在本次统一为欧氏（§2.4 / §4.7）。

## 2. AI 歌单推荐

### 2.1 目标与非目标

**目标**
- 给定当前 `activeSceneProvider`，从 `effectiveMusicLibraryProvider` 中排出一份「与场景意境相符」的播放序列（歌单）。
- 推荐结果**可解释**（能告诉用户「为什么推这首」），符合 README「意境优先」「习惯性交互」的产品调性。
- 全本地计算，零网络、零上传，与 `ConsentGate.privacyNote` 的承诺一致。

**非目标（本期明确不做）**
- 不做协同过滤（单机应用，无跨用户数据）。
- 不做云端音频指纹 / 声学分析服务。
- 不做「猜你喜欢」式的全局个性化排序（曲库规模不足以支撑）。

### 2.2 核心难点与三条打标路线

`Track` 无情感维度（§1.2）。要与 `Scene.(valence, energy)` 同空间匹配，必须给曲目打标。三条路线：

| 路线 | 做法 | 精度 | 成本 | 离线 | 结论 |
|---|---|---|---|---|---|
| **A · 元数据启发式** | 从 `title` / `artist` / `album` / `duration` / `sourceId` / 文件夹名，用关键词词典 + 时长/流派先验推断 `(valence, energy)` | 低~中 | **极低** | ✅ | ✅ **本期采用（默认）** |
| **B · 端侧音频特征** | 解码 PCM → 算 RMS 能量、过零率、频谱质心、估计 BPM → 映射到 `(valence, energy)` | 中~高 | 高（需解码器 + 后台任务 + 首次全库扫描耗时/耗电） | ✅ | ⏸ **P3 后置**（可复用 `spatial_synth.dart` 的 PCM 处理经验） |
| **C · 云端 LLM / embedding** | 曲目元数据 → LLM 打标 或 文本 embedding 检索 | 中~高 | 高（API Key、费用、隐私授权、离线不可用） | ❌ | ❌ **本期不做**，理由见 §2.5 |
| **D · 用户显式反馈** | 用户长按曲目打标「更安静 / 更明亮」，或收藏行为反推 | 高（但稀疏） | 低 | ✅ | ✅ **作为 A 的修正项**（阶段 S2b） |

**采用组合：A（冷启动基线）+ D（在线修正）**，B 留接口。

### 2.3 数据模型设计

**【新增】`lib/models/track_feature.dart` · `TrackFeature`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `uri` | `String` | 主键，对齐 `Track.uri`（全项目已用 `uri` 做曲目同一性判断，见 `nextTrackInLibrary`） |
| `valence` | `double` 0~1 | 情绪效价 |
| `energy` | `double` 0~1 | 能量强度 |
| `confidence` | `double` 0~1 | 置信度：启发式命中关键词多则高；用户显式修正则置 1.0 |
| `source` | `enum FeatureSource` | `heuristic` / `userTagged` / `audioAnalysis`（预留 B 路线） |
| `updatedAt` | `DateTime` | 用于后续重算失效判断 |

**存储**：`usage_events` 表（`type = 'track_feature'`，`payload` 存 JSON），**复用 `UsageRepository`，不新建表**。理由：
- 曲库规模 10²~10³，全量读入内存做排序完全可行，无需索引查询能力。
- 避免引入 sqflite migration（当前 `UsageRepository.open()` 是 `version: 1` 且 `onCreate` 无 `onUpgrade` 分支，加表要动 migration，风险外溢到既有功能）。
- 若后期特征量增长，再独立建表并写 migration。

> ⚠️ **注意**：`UsageRepository.recent()` 按 `ts DESC` 返回同 `type` 全部行，同一 `uri` 可能有多条历史。读取时需**按 `uri` 去重取最新**。这是复用现有表的代价，需在 `【新增】TrackFeatureRepository` 内部封装掉。

### 2.4 本地规则引擎设计

**【新增】`lib/services/intelligence/recommendation_engine.dart` · `RecommendationEngine`**（纯 Dart，无 Riverpod 依赖，符合 §1.4 分层）

#### 2.4.1 打标阶段（A 路线启发式）

输入 `Track` → 输出 `TrackFeature`。评分维度与建议权重：

| 信号 | 提取方式 | 影响维度 | 权重 |
|---|---|---|---|
| **关键词词典** | `title`/`album` 命中中英词表：`{雨/rain/storm}`→低 v 低 e；`{夜/night/lunar/moon}`→低 e；`{火/fire/ember/warm}`→高 v 中 e；`{海/ocean/deep/abyss}`→低 v 低 e；`{雪/snow/winter}`→低 e；`{森林/forest/moss/light}`→高 v 中 e；`{钢琴/piano/solo/acoustic}`→低 e；`{rock/dance/beat/remix}`→高 e | v, e | 0.45 |
| **艺术家先验** | 同一 `artist` 已有 ≥3 首带特征 → 取其均值作为该艺人基线 | v, e | 0.20 |
| **时长** | `Track.duration`：>8min → e −0.15（长曲多为氛围）；<2min → e +0.10 | e | 0.10 |
| **音源** | `sourceId == 'minecraft'` → 低 e（游戏环境音）；`isLiveStream == true` → 中性 0.5/0.5 且 `confidence` 置 0.2 | v, e | 0.15 |
| **文件夹路径** | 本地源 `uri` 路径段命中词表（用户常按氛围建目录） | v, e | 0.10 |

无任何命中 → `(0.5, 0.5)`，`confidence = 0.1`（中性兜底，靠后但不排除）。

#### 2.4.2 打分阶段

对候选曲目 `t`、当前场景 `s`：

```
情感距离    d = sqrt((t.valence - s.valence)² + (t.energy - s.energy)²)     ← 复用 SceneOrderService 的欧氏度量
情感得分    S_emotion = 1 - clamp(d / √2, 0, 1)
文本得分    S_text    = 关键词重合度（修正 RecommendPage 现有反向 contains 的 bug）
行为得分    S_history = f(该曲在本场景下的历史播放次数 / 跳过次数)        ← 来自 usage_events
收藏加成    S_fav     = favoriteProvider.contains(t.uri) ? 1 : 0
置信惩罚    P_conf    = feature.confidence

总分 = 0.50·S_emotion·P_conf + 0.15·S_text + 0.25·S_history + 0.10·S_fav
```

#### 2.4.3 硬过滤（先于打分）

1. `scene.musicSourceId != null` → 只保留该音源曲目。**注意**：`effectiveMusicLibraryProvider` **已经做了这层过滤**（`snow`/`ocean` → `MinecraftMusicSource`），推荐引擎消费它即可，**不要重复实现**。
2. `Track.isLiveStream == true` → 电台无「歌单」语义（`Track` 注释明确「无时长、无进度、无下一首单首语义」），从歌单排除，但保留在「电台」分组。
3. 排除当前 `nowPlayingProvider` 曲目（避免推荐正在播的）。

#### 2.4.4 多样性重排（避免「同一个艺人刷屏」）

采用简化 **MMR（Maximal Marginal Relevance）**：

```
每轮从候选中选 argmax [ λ·总分 − (1−λ)·max(与已选集合的相似度) ]
相似度 = 同 artist 记 1.0 / 同 album 记 0.7 / 情感距离 < 0.1 记 0.5 / 否则 0
λ = 0.75（偏相关性，兼顾多样）
```

同时施加**软约束**（借鉴 `SceneOrderService._score()` 的违规计数思路）：相邻两首情感距离建议落在 `[0.05, 0.40]`，避免歌单内部忽静忽动。

#### 2.4.5 输出

`【新增】RecommendedPlaylist { List<Track> tracks; Map<String,String> reasons; }`
`reasons[uri]` 形如「与「雨」场景情绪接近（距离 0.08）」「你在这个场景听过 6 次」—— 满足**可解释性**要求，直接渲染成 `InfoRow` 副标题。

### 2.5 云端 LLM / embedding 评估

| 维度 | 本地规则引擎 | 云端 LLM/embedding |
|---|---|---|
| 精度 | 中（元数据依赖强，无 tag 的曲库退化明显） | 中高（LLM 认识大量曲名/艺人） |
| 延迟 | < 50ms（10³ 曲目全量排序） | 300ms~2s + 网络抖动 |
| 离线 | ✅ 完全可用 | ❌ 不可用；本项目核心场景是本地曲库 + 睡前离线使用 |
| 隐私 | ✅ 零上传，符合 `ConsentGate.privacyNote` | ❌ 需上传曲名/艺人，**必须新增二次授权流程** |
| 成本 | 0 | API Key 管理 + 调用费；项目 `.env` 目前仅 66 字节，无密钥体系 |

## 3. 睡眠定时器

### 3.1 交互形态

- **入口**：`SettingsSection.playback`（设置①播放）新增「睡眠定时器」条目 + `UnifiedPlayer` 全屏播放层新增快捷入口（沿用其已有的 `PlaybackButtonFabric` 按钮体系）。
- **预设**：15 / 30 / 45 / 60 / 90 分钟 + 「播放完当前曲目」+ 自定义。
- **运行中**：入口处显示剩余时间（`mm:ss`）；提供「+10 分钟」「取消」。
- **到点行为**（可配）：`渐隐后暂停`（默认）/ `渐隐后停止并释放` / `仅停止音景`。
- **渐隐时长**（可配）：默认 **60 秒**，可选 0（立即）/ 30s / 60s / 180s。

### 3.2 状态模型

**【新增】`lib/models/sleep_timer_state.dart`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | `enum SleepTimerStatus { idle, running, fading, finished }` | 显式状态机，对齐 `AudioService.PlaybackState` 的设计取向（"用单一权威模型替代零散 flag 拼凑"） |
| `endAt` | `DateTime?` | **绝对结束时间戳**（非剩余秒数计数器）—— 关键设计，见 §3.5 |
| `totalDuration` | `Duration` | 本次设定总时长（用于进度环） |
| `fadeDuration` | `Duration` | 渐隐时长 |
| `action` | `enum SleepTimerAction { pause, stopAndRelease, soundscapeOnly }` | 到点动作 |
| `waitCurrentTrack` | `bool` | 「播完当前曲目再停」模式 |

派生：`remaining => endAt.difference(DateTime.now())`（**每次读都重算，不累加**）。

### 3.3 引擎缺口与改造

| 缺口 | 影响 | 改造方案 |
|---|---|---|
| **无 `stop()`** | `stopAndRelease` 动作无法实现；`pauseOnly()` 只暂停不释放，长时间后台占资源 | 在 `AudioService` 新增 `【新增】Future<void> stop()`：`_music.stop()` + `_activeSc.stop()` + `_sfx.stop()` + `_state = PlaybackState.idle` + `_currentTrack = null` + `_trackCtrl.add(null)`，全程包 `_safe()`（C7） |
| **`_fadeMusic` 不可打断** | 60s 渐隐中用户手动调音量 → 两个循环互相覆盖，音量抖动 | 新增 `【新增】Future<void> fadeOutAll(Duration d, {String token})`：内部维护 `int _fadeSeq`（**复用 `switchSoundscape` 的 `_scSeq` 竞态保护范式**），每次进入 `++_fadeSeq`，循环内每步校验 `seq == _fadeSeq`，不等则立即退出。同时 `setMusicVolume()` 也 `++_fadeSeq` 以抢占正在进行的渐隐 |
| **渐隐需同时作用音乐+音景** | 只淡音乐会留下音景孤零零响着 | `fadeOutAll` 内部 `Future.wait([_fadeMusic(...), _fadeSoundscape(_activeSc, ...)])`，与 `switchSoundscape` 的并行淡入淡出写法一致 |
| **渐隐后音量必须可恢复** | 淡到 0 后若不恢复，用户下次手动播放没声音 | 到点动作执行完毕后，**把引擎音量恢复到 `musicVolumeProvider` / `soundscapeVolumeProvider` 的记忆值**（引擎已在暂停态，恢复音量不发声）。这一步是最容易漏的 bug |

> 💡 **可复用参考**：`setDuck(bool)` 已有「临时改音量但不改记忆值」的语义模型，`fadeOutAll` 应遵循同样约定——**只动输出音量，绝不写 `_musicVol`**。

### 3.4 Notifier 与计时设计

**【新增】`lib/providers/intelligence/sleep_timer_providers.dart`**

| Provider | 类型 | 说明 |
|---|---|---|
| `sleepTimerProvider` | `StateNotifierProvider<SleepTimerNotifier, SleepTimerState>` | 主状态 |
| `sleepTimerRemainingProvider` | `Provider<Duration?>` | 派生剩余时间（供 UI watch） |
| `sleepTimerDefaultsProvider` | `StateProvider<...>` | 默认时长/淡出时长/到点动作偏好，走 `SettingsRepository` 持久化 |

`SleepTimerNotifier` 内部：
- 单个 `Timer.periodic(Duration(seconds: 1))` 作为**心跳**，每 tick 用 `DateTime.now()` 与 `endAt` 比对（**不做倒计数累加**）。
- 剩余 ≤ `fadeDuration` 时置 `status = fading` 并**一次性**调用 `audio.fadeOutAll(remaining)`（不是每 tick 调）。
- 剩余 ≤ 0 → 执行 `action` → `status = finished` → 恢复记忆音量 → `_timer.cancel()`。
- `ref.onDispose` 中 `cancel()` 定时器（C5）。
- 「播完当前曲目」模式：不用心跳，改为 `ref.listen(playbackStateProvider)`，等 `PlaybackState` 从 `playing` 转 `idle/paused` 且 `musicPositionProvider ≈ musicDurationProvider` 时触发。

### 3.5 后台存活（关键风险）

Dart `Timer` 在应用进入后台后**不保证按时触发**（Android Doze / 进程冻结；息屏睡前场景恰恰是最常见用法）。

**缓解设计（三重）**：
1. **绝对时间戳 `endAt`**：即使 Timer 被节流、漏 tick，恢复前台或下次 tick 时用 `DateTime.now()` 比对，**误差不累积**，最多是「晚停」而非「不停」。
2. **借力已有前台服务**：项目已集成 `audio_service: ^0.18.19` + Manifest `FOREGROUND_SERVICE_MEDIA_PLAYBACK` + `AudioServiceConfig(ongoing: true)`（R14）。**只要在播放，进程即有前台服务，Timer 存活性远高于普通后台**。这是本项目的天然优势。
3. **持久化 `endAt`**：写入 `SettingsRepository`。冷启动 `restoreSettings()` 时读取：若 `endAt` 已过期 → 直接执行到点动作并清空；未过期 → 重建定时器。这样进程被杀重启也不会「定时器消失但音乐还在响」。

> ⚠️ **明确不做**：不引入 `WorkManager` / `AlarmManager` 精确闹钟。Android 12+ `SCHEDULE_EXACT_ALARM` 需特殊权限申请，对「音乐晚停 30 秒」这种低危场景属于过度设计。

### 3.6 边界与交互裁决

| 场景 | 处理 |
|---|---|
| 定时器运行中用户手动切歌 | **不取消**（用户只是换歌，不是不想睡） |
| 定时器运行中用户手动暂停 | **不取消**，继续倒计时；到点后仍执行 `action`（幂等） |
| 渐隐中用户手动拖音量 | **取消渐隐**（`++_fadeSeq` 抢占），定时器继续；到点直接执行动作（跳过渐隐）。视为「用户想继续听」的信号，同时弹一次「睡眠定时器仍在运行，剩余 X 分钟」提示 |
| 到点时音乐本就没在播 | 只执行音景关闭 + `setWhiteNoise(false)`，不报错 |
| 来电 / 音频焦点被抢 | 交给既有 `audio_session` 焦点逻辑（`setDuck`）；定时器不感知，行为不变 |
| 用户设置新定时器 | 覆盖旧的（`endAt` 重算），不叠加 |

### 3.7 通知联动

到点时调用 `recentNotificationsProvider.notifier.append('睡眠定时器', '已在 30 分钟后停止播放')`，与 `AppShell` 中既有的场景切换 / 曲目切换事件记录方式一致。

### 4.2 规则引擎数据模型

**【新增】`lib/models/auto_scene_rule.dart`**

```
AutoSceneRule {
  String   id;              // 'builtin_night' / 'custom_xxx'（沿用 Scene.isCustom 的前缀约定）
  String   name;            // '深夜自动进入星夜'
  bool     enabled;         // 单规则开关
  int      priority;        // 数值越大越优先，同优先级取先命中
  TriggerCondition trigger; // 条件（见下）
  SceneTarget target;       // 动作目标（见下）
  Duration cooldown;        // 命中后冷却，默认 30 分钟
  DateTime? lastFiredAt;    // 上次触发时间（持久化，用于冷却判定）
}
```

**`TriggerCondition`（sealed class，四个子类）**

| 子类 | 字段 | 语义 |
|---|---|---|
| `TimeRangeTrigger` | `startMinuteOfDay`, `endMinuteOfDay`（支持跨零点） | 「22:30 ~ 06:00」 |
| `WeatherTrigger` | `Set<WeatherKind>`（`clear/cloudy/rain/snow/thunder/fog`） | 「下雨或雷阵雨时」 |
| `HeartRateTrigger` | `min`, `max`（bpm） | 「心率 > 100」 |
| `LightTrigger` | `minLux`, `maxLux` | 「环境光 < 10 lux」 |

**`SceneTarget`（两种）**

| 类型 | 语义 | 实现 |
|---|---|---|
| `FixedSceneTarget(sceneId)` | 切到指定场景 | 按 id 在 `sceneOrderProvider` 中查索引 |
| `EmotionTarget(valence, energy)` | 切到情感坐标最近的场景 | 复用 `SceneOrderService.emotionalDistance()` 取 argmin |

> `EmotionTarget` 是心率/天气这类**连续量**触发源的正确表达方式——它们不该硬绑某个场景 id（用户可能已隐藏或删除该场景），而应表达「我想要更安静一点」。

### 4.3 内置规则（默认随包，用户可改可关）

| id | 条件 | 目标 | 优先级 | 默认 |
|---|---|---|---|---|
| `builtin_night` | 时间 22:30–06:00 | `FixedSceneTarget('starnight')` | 60 | 关 |
| `builtin_dusk` | 时间 17:30–19:30 | `FixedSceneTarget('dusk')` | 50 | 关 |
| `builtin_rain` | 天气 = rain/thunder | `FixedSceneTarget('rain')` | 70 | 关 |

### 4.4 传感器改造：单次读 → 持续流

这是 P2 阶段的**前置硬依赖**。

**原生侧（`MainActivity.java`）**
- 新增 `EventChannel("com.stelarith.xingli_music/sensors_stream")`。
- `onListen(args, sink)`：按 `args['type']`（`light` / `heartRate`）`registerListener`，持续 `sink.success(value)`。
- `onCancel`：`unregisterListener`，**必须彻底注销**（否则息屏持续采样 → 耗电投诉）。
- 采样率：光线用 `SENSOR_DELAY_NORMAL`（200ms 级即可，不用 `SENSOR_DELAY_UI`）；心率用 `SENSOR_DELAY_NORMAL`。
- 保留现有 `MethodChannel` 单次读接口不动（`SensorPage` 的一次性展示仍在用），**新旧并存，零回归风险**。

**Dart 侧（`SensorService`）**
- 新增 `【新增】Stream<double?> lightLuxStream()` / `【新增】Stream<double?> heartRateStream()`，走 `EventChannel.receiveBroadcastStream(args)`。
- 现有 `lightLux()` / `heartRate()` **保持不变**（`sensor_providers.dart` 的 `lightLuxProvider` / `heartRateProvider` / `sceneBrightnessMaskProvider` 全部不受影响）。
- 新增流的订阅同样注册进 `_subs`，由 `dispose()` 统一取消（C5）。

**权限补齐**
- `PermissionService.requestAll()` 与 `overview()` 加入 `Permission.sensors`（对应 `BODY_SENSORS`，Manifest 已声明）。
- 心率规则启用时才申请，不在启动时申请（避免无谓权限弹窗）。

**Wear OS 适配**
- `SensorService` 新增 `【新增】bool get isWearOs`（原生侧 `PackageManager.hasSystemFeature("android.hardware.type.watch")` 经 MethodChannel 回传）。
- 手机上 `TYPE_HEART_RATE` 命中率极低 → UI 显式提示「当前设备无心率传感器」（`SensorPage` 已有该降级文案模式，直接复用）。

### 4.5 天气 API 设计

**选型原则**：免费额度够用、无需信用卡、返回结构简单、可无 Key 或 Key 可内置。候选（按推荐序）：
1. **Open-Meteo**（无需 API Key、免费、无商用限制、返回 WMO weather code）—— **首选**，与「不引入密钥体系」的现状最契合。
2. 和风天气 / 彩云天气（国内节点快，但需注册 Key + `.env` 管理）—— 备选。

**【新增】`lib/services/intelligence/weather_service.dart` · `WeatherService`**
- 依赖：仅 `http: ^1.2.2`（**不引入新包**）。
- 方法：`Future<WeatherSnapshot?> fetch({required double lat, required double lon})`。
- `【新增】WeatherSnapshot { WeatherKind kind; double? tempC; DateTime fetchedAt; }`。
- **缓存**：结果缓存 **30 分钟**（`SettingsRepository` 存 JSON）。天气变化慢，高频拉取纯属浪费流量与电量。
- **轮询**：`Timer.periodic(30min)` + 应用回前台时补一次；**仅当存在已启用的 `WeatherTrigger` 规则时才启动轮询**（无规则 = 零网络请求）。
- **失败降级**：任何异常 → 返回 `null` → 天气类规则**全部视为不命中**（不猜、不用陈旧数据超过 3 小时），`LogService.instance.w('weather', ...)` 记录。

**定位方案裁决 —— 不引入 `geolocator`**：
- 理由：定位权限是最敏感权限之一，为「切个背景场景」申请位置权限，收益/信任成本比很差；且 Android 12+ 精确定位需额外交互。
- **采用**：设置页让用户**手动选择/搜索城市**（存 `settings.weatherCityName` + `lat/lon`），一次设定长期有效。
- 备选（P3）：用 IP 粗定位（Open-Meteo 配套的 geocoding 接口），精度到城市级，无需任何权限。

### 4.6 心率 / 光线 → 情感坐标映射

**心率**（需先建立个人基线，否则运动员和老人不能用同一套阈值）：
- 基线 `HR_rest`：取近 7 天 `usage_events(type='hr_sample')` 的**第 20 百分位**；样本不足 50 条时用 `70 bpm` 兜底。
- 相对激活度 `a = clamp((HR − HR_rest) / 40, 0, 1)`。
- 映射：`energy_target = 0.10 + 0.35·(1 − a)` —— **注意是反向**：心率高 → 推荐低能量场景（安抚），符合「壁炉/星夜」这类产品定位。
- `valence_target` 不由心率推断（心率无法区分「兴奋」与「焦虑」，强行映射会出错），固定取当前场景 `valence`，只调 `energy`。

> ⚠️ **区间压缩**：§1.1 已指出 7 个场景 `energy ∈ [0.10, 0.50]`。映射输出必须落在这个区间内，否则 argmin 永远吸附到端点场景。上式的 `[0.10, 0.45]` 输出区间即为此设计。

**环境光**：
- `lux < 10` → 夜间/暗室 → `energy_target = 0.12`。
- `10 ≤ lux < 300` → 室内 → 不触发（信息量不足）。
- `lux ≥ 300` → 明亮 → `energy_target = 0.40`。
- 复用 `sceneBrightnessMaskProvider` 已确立的 `10 / 300` 分档阈值，**保持全项目一致**。

### 4.7 去抖、迟滞与冷却（防「场景疯狂横跳」）

这是自动切场景**最容易翻车的地方**。四道闸门：

| 闸门 | 设计 | 参数 |
|---|---|---|
| **① 持续确认** | 连续 N 次采样均满足条件才算命中 | 心率 3 分钟 / 光线 2 分钟 / 天气 1 次（已是 30 分钟粒度） |
| **② 迟滞（Hysteresis）** | 进入阈值与退出阈值分离，避免临界抖动 | 如 lux 进入 `<10`、退出 `>20` |
| **③ 情绪距离门槛** | 目标场景与当前场景距离 **< 0.10** 时**不切**（`SceneOrderService.minAdjacentDistance` 的现成语义：「太近＝两个场景没区别」） | 0.10 |
| **④ 冷却** | 任一规则命中后进入全局冷却，期间不再自动切 | 默认 30 分钟，可配 |

**额外的用户意图保护**：
- 用户在**过去 10 分钟内手动切过场景** → 暂停自动切换（尊重显式操作）。判定依据：`currentSceneIndexProvider` 的变更来源标记。
- **【新增】`sceneChangeSourceProvider`**（`StateProvider<SceneChangeSource>`，枚举 `user / shake / automation / restore`）—— 现有代码里 `currentSceneIndexProvider` 被 `MoodAnalysisPage`、`SceneShakeNotifier`、`restoreSettings` 三处直接写，无法区分来源。**这个 Provider 是自动化的必要前置**。

### 4.8 执行器设计

**【新增】`lib/services/intelligence/scene_automation_engine.dart` · `SceneAutomationEngine`**（纯规则求值，无副作用）
- `AutoSceneRule? evaluate(List<AutoSceneRule> rules, AutomationContext ctx)`
- `【新增】AutomationContext { DateTime now; WeatherKind? weather; double? heartRate; double? lux; Scene currentScene; }`
- 求值顺序：过滤 `enabled` → 过滤冷却中 → 逐条判条件 → 按 `priority` 降序取首个 → 应用闸门③ → 返回。
- **纯函数，100% 可单测**（给定 context 与规则集，输出确定）。

**【新增】`SceneAutomationNotifier`**（副作用执行，**完全沿用 `SceneShakeNotifier` 的结构**）：

```
现有 SceneShakeNotifier.nextScene() 的三步：
```

## 5. 语音控制

### 5.1 STT 方案对比与选型

| 方案 | 包体增量 | 离线 | 中文准确率 | 首字延迟 | 隐私 | 低端机/Wear | 结论 |
|---|---|---|---|---|---|---|---|
| **系统 STT**（Android `SpeechRecognizer`，经 `speech_to_text` 插件） | ~0.3MB | 取决系统（多数机型联网） | **高**（厂商中文模型成熟） | 低 | 音频经系统服务，可能上传厂商服务器 | ✅ 无额外负担 | ✅ **本期采用** |
| **on-device Whisper**（`whisper.cpp` + FFI） | **+40~150MB**（tiny~base 量化模型） | ✅ 完全离线 | tiny 中文差 / base 中等 | **高**（低端机数秒） | ✅ 最佳 | ❌ CPU 密集，发热严重 | ❌ **不采用** |
| **云端 ASR**（自建/第三方 API） | ~0 | ❌ | 高 | 中 | ❌ 需上传音频 + 二次授权 | ✅ | ❌ 违反 README「不做云端」边界 |

**选型结论：`speech_to_text` 插件（封装 Android `SpeechRecognizer` / iOS `SFSpeechRecognizer`）。**

否决 on-device Whisper 的核心理由（三条，均基于本项目实际约束）：
1. **包体**：debug APK 已 157MB，release 目标 25~40MB（`PROJECT_STATE.md` §三）。加 40MB+ 模型直接让 release 目标失守。
2. **算力**：项目专门做了 `PerformanceMode.powerSave`（关噪点、关模糊、0.5× 动画）来应对「长时间高负载导致发热」，同一产品里塞一个 CPU 密集的 ASR 推理，自相矛盾。
3. **平台矩阵**：需支持 Windows / Web，Whisper FFI 的多平台构建（含 Web WASM）工作量远超语音控制本身的价值。

**降级链**：`speech_to_text` 不可用（Web / Windows / 无 Google 语音服务的国内 ROM）→ **功能整体隐藏**，不显示入口，不报错。

### 5.2 唤醒方式（明确不做常驻唤醒词）

- **不做**「小星小星」式常驻唤醒词监听：需常开麦克风 → 耗电 + 严重隐私顾虑 + 需引入 Porcupine 之类的额外引擎。
- **采用按压说话（Push-to-Talk）**：
  - `UnifiedPlayer` 全屏播放层的麦克风按钮，**按住说话、松手识别**。
  - 长按 Dock 的一处热区（可选）。
  - 识别过程有明确的视觉反馈（波形/呼吸圈）与「正在聆听」文案 —— 让用户随时知道麦克风何时开启，这是隐私设计的基本要求。

### 5.4 意图解析：本地规则，不用 LLM

- **方案**：正则 + 关键词槽位抽取 + 编辑距离容错。指令集只有 13 个意图、槽位类型 4 种，规则法完全够用。
- **不用 LLM 的理由**：需联网、有延迟（语音场景对延迟极敏感）、有成本、且会把「已经识别出的文本」再上传一次（隐私二次暴露）。
- **纯函数设计**：`VoiceIntentParser.parse(String text, {required List<Scene> scenes, required List<Track> library}) → ParsedIntent`。无副作用，**100% 可单测**（这是本功能唯一能有效保障质量的手段——真实语音识别无法自动化测试，但「文本 → 意图」可以覆盖上百条用例）。
- **数字解析**：需处理中文数字（「三十分钟」「一小时」「五十」）与阿拉伯数字混合。

### 5.5 与播放器联动的执行契约

**【新增】`lib/providers/intelligence/voice_control_providers.dart` · `VoiceCommandExecutor`**

必须遵守的两条铁律（否则会产生状态不一致 bug）：

1. **音量类指令必须同时写 Provider 与引擎。**
   参考 `UnifiedPlayer` 现有写法（`unified_player.dart:408-413`）：先 `ref.read(musicVolumeProvider.notifier).state = v`，再 `ref.read(audioServiceProvider).setMusicVolume(v)`。只写 Provider → 引擎不生效；只写引擎 → UI 与持久化不同步。
   **例外**：`whiteNoiseEnabledProvider` / `balanceModeProvider` 已由 `settingsSyncProvider` 监听并自动同步引擎，**只写 Provider**，重复写会导致双重调用。

2. **播放类指令一律走 `playbackActionsProvider`（C6），不直接碰 `AudioService`。**
   它已处理空曲库提示、场景默认曲目（R6）、播放失败兜底，并返回 `String` 提示消息 —— 语音层直接把这个消息念/显示出来即可，无需自己造错误文案。

**执行结果反馈**：
- 成功 → SnackBar「已切换到「雨」」+ 可选 TTS 回读（P3，`flutter_tts`，本期不做）。
- 失败/未识别 → SnackBar 提示 + 展示 3 条可用指令示例。
- 全程写 `recentNotificationsProvider.append('语音控制', ...)`。

### 9.3 建议的第一步

**先做 S1（睡眠定时器）**，理由：
- 2.5 人日即可闭环，是最快能让用户感知到「这个应用变智能了」的改动。
- 它顺带补齐的 `AudioService.stop()` 与**可抢占淡出** `fadeOutAll()`，是后续自动切场景（切场景时的平滑过渡）与语音控制（"停止播放"指令）的**共同基础设施**——早做早复用。
- 零新依赖、零新权限、零隐私风险，不需要任何合规评审。

紧接着做 **S2（推荐）**，因为 `Scene.valence/energy` 这套情感模型已经躺在代码里两个版本没被真正用起来（`RecommendPage` 徒有其名），这是**投入产出比最高的一笔**。
