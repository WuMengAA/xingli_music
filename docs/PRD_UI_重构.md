## 0. 设计输入说明（重要，请先读）

本 PRD 使用**两个同源但保真度不同**的设计输入：

| 来源 | 内容 | 权威性 |
|---|---|---|
| **A. PDF 设计稿**（主理人解读） | 颜色、选中态、文案 | **配色与状态的唯一权威** |
| **B. `figma_export/*.svg`**（仓库内，5 个文件） | 精确几何：坐标、尺寸、圆角、层级、阴影参数 | **尺寸与布局的唯一权威** |

**关键发现：两者是同一 Figma 文件的不同导出。**
- 画布比例完全一致：1400/1080 = 2489/1920 = 1.296
- 文件名与 PDF 页序一一对应：`场景.svg` / `探索.svg` / `曲库.svg` / `首页.svg` / `设定.svg`
- SVG 是**灰度线框版**（只含 `#D9D9D9` / `#9A9A9A` 两种灰），不含紫色 → 所以颜色必须取自 PDF
- SVG 含完整坐标与滤镜参数 → 所以尺寸必须取自 SVG

> **纠正一处解读**：主理人将 PDF 第 4 页描述为「默认态（无 Tab 选中）」。
> 实际该页文件名为 **`首页.svg`**，是一个**独立的首页设计**——它没有搜索栏，且因为首页不在 4 Tab 之列，所以 Dock 上自然无 Tab 高亮。
> 这正好印证了「home 保留但不进主导航」的决策：设计稿本身就是这么设计的。

**SVG 中发现、但与 PDF 解读不一致的 4 处**，已全部登记在 §7 待确认问题（Q1–Q4），**开发前必须裁决**。

### 0.1 设计稿 → Flutter 换算基准

SVG 手机框内屏尺寸 = **972 × 1818 px**。

取 **缩放系数 = 2.5**（设计 px ÷ 2.5 = Flutter 逻辑 dp）：
- 972 ÷ 2.5 = **388.8 dp** ≈ 390 dp（现代手机主流逻辑宽度）
- 验算：曲库卡片 = (812 − 92) ÷ 2 ÷ 2.5 = **144 dp**；在 390dp 屏上按同样内外边距计算得 144.6 dp ✅ 完全吻合

结论：**本设计稿以 390dp 宽为基准绘制，缩放系数固定为 2.5。**

垂直方向设计稿总高 1818 ÷ 2.5 = 727.2 dp，而 390×844 真机可用高约 763 dp（扣状态栏与手势条）→ **多出约 36 dp**。
处理原则：**固定高度 = 搜索栏 / 迷你播放器 / Dock；弹性高度 = 内容容器（Expanded 吸收差值）**。

## 1. 背景与目标

### 1.1 背景

星璃音乐空间当前功能完整（音频播放、曲库聚合、场景切换、后台播放、锁屏控件均可用），但视觉体系是**深色沉浸式玻璃拟态**：深紫底 `#1A103C`、粒子层、噪点纹理、由用户主色 HSL 实时派生的动态配色（`DerivedPalette` / `DesignTokens`）。

这套体系带来三个问题：
1. **配色不可预期** —— 颜色由 HSL 运行时派生，同一控件在不同场景/心情下颜色不同，无法做设计走查，也无法保证对比度
2. **信息密度低** —— 中央舞台卡 + 脉动光球占据主视野，曲库/设置等功能性内容被挤压
3. **导航过载** —— 8 个页面、5 个 Tab，加上心情入口、调色盘入口、ControlBar、MorePanel、VolumeSlider 五层浮层，操作路径不清晰

设计稿给出的答案是**极简浅色扁平化**：固定色板、4 Tab、常驻迷你播放器、内容优先。

### 1.2 产品目标

| # | 目标 | 衡量方式 |
|---|---|---|
| **G1** | **建立可预期的固定设计系统** —— 用一套硬编码浅色 Token 取代运行时 HSL 派生，让每个像素可被设计走查 | 主 Shell 与 4 个主 Tab 页中，对 `DerivedPalette` / 深色 `DesignTokens` 的引用数 = 0；所有颜色可追溯到 §6 Token 表 |
| **G2** | **收敛导航到 4 Tab + 常驻迷你播放器** —— 任意功能 ≤ 2 次点击可达，播放控制永远在手边 | Dock Tab 数 = 4；迷你播放器在全部 5 个 Shell 页面持续可见；核心功能（播放/曲库/音源设置/场景）点击深度 ≤ 2 |
| **G3** | **视觉重构零功能倒退** —— 换皮不换里，音频与数据能力 100% 保留 | §8 回归清单全项通过；`flutter analyze` 无 error |

> 三个目标正交：G1 管「怎么看」，G2 管「怎么用」，G3 管「别弄坏」。

### 1.3 非目标（本次不做）

- 不新增音乐源、不改动 `lib/services/` 下任何音频/数据逻辑
- 不做深色模式（列入 P2）
- 不做国际化
- 不重写场景引擎（`lib/scenes/`）与场景数据模型

## 2. 用户故事

### 2.1 应用外壳（贯穿全局）

- **US-01** 作为用户，我希望**底部始终有一条迷你播放器**，这样我在浏览曲库或改设置时也能随时暂停/切歌，不必返回播放页。
- **US-02** 作为用户，我希望**底部导航只有 4 个清晰的入口**，这样我一眼就知道 App 能做什么，不用在 8 个页面里迷路。
- **US-03** 作为用户，我希望**当前所在页在导航栏上有明确的紫色高亮**，这样我永远知道自己在哪。
- **US-04** 作为用户，我希望**切 Tab 时页面状态被保留**（曲库滚到哪还在哪），这样来回切换不丢上下文。

### 2.2 场景页（Tab 1，默认启动页）

- **US-10** 作为用户，我打开 App 就进入场景页，这样我能立刻选一个氛围开始听。
- **US-11** 作为老用户，我希望**仍能进入原来的首页和沉浸画布**，这样我熟悉的沉浸体验没有被删掉，只是收进了二级入口。

### 2.3 探索页（Tab 2）

- **US-20** 作为用户，我希望在探索页发现新内容/新场景，这样我不用每次都听同样的东西。

### 2.4 曲库页（Tab 3）

- **US-30** 作为用户，我希望曲库以**双列专辑卡片网格**展示，这样我靠封面就能快速认出想听的专辑，比纯文字列表快得多。
- **US-31** 作为用户，我点一下卡片就直接播放，并且迷你播放器立刻显示这首歌。
- **US-32** 作为用户，当曲库还在扫描/加载时我希望看到加载提示，失败时能重试，空的时候告诉我为什么空。

### 2.5 设置页（Tab 4）

- **US-40** 作为用户，我希望设置项按类别分组，这样我能快速找到要改的东西。
- **US-41** 作为用户，我**必须仍能配置音乐服务器 / 本地目录**，否则 App 拿不到歌就是个空壳。
- **US-42** 作为用户，我希望**场景编辑器仍然可达**，我之前做的自定义场景不能变成孤儿数据。

### 2.6 搜索（全局组件）

- **US-50** 作为用户，我希望每页顶部都有搜索栏，且它搜的是**当前页的东西**（曲库页搜歌，设置页搜设置项），这样我不用猜它到底在搜什么。

### 5.2 Tab 索引与页面索引的映射

Dock 只有 4 个 Tab，但 `IndexedStack` 有 5 个子页面，因此需要两个独立状态：

| 状态 | 类型 | 说明 |
|---|---|---|
| `shellPageIndex` | `0..4` | 当前展示的页面索引，驱动 `IndexedStack.index` |

## 6. 配色方案 Token 定义

### 6.1 色值溯源方法

线框 SVG 用 `#D9D9D9` / `#9A9A9A` 两种灰配合不同 alpha 表达层级。将其按 alpha 合成到白底，即可**反解出设计稿的真实中性色**：

```
合成值 = 255 − (255 − 灰阶值) × alpha
```

| 元素 | SVG 原始值 | 叠加底色 | 反解结果 | 与 PDF 解读对比 |
|---|---|---|---|---|
| 内容容器 | `#D9D9D9` @25% | `#FFFFFF` | **`#F5F5F5`** | ✅ 与 PDF 完全一致 |
| Dock 容器 | `#9A9A9A` @25% | `#FFFFFF` | **`#E6E6E6`** | PDF 未给具体值 |
| 设置卡片 | `#D9D9D9` @25% | `#F5F5F5` | **`#EEEEEE`** | PDF 未给具体值 |
| 设置左分类栏 | `#D9D9D9` @20% | `#EEEEEE` | **`#EAEAEA`** | PDF 未给具体值 |
| 设置分类 tile | `#D9D9D9` @20% | `#EAEAEA` | **`#E7E7E7`** | PDF 未给具体值 |
| 搜索栏 | `#D9D9D9` 实色 | — | **`#D9D9D9`** | ⚠️ PDF 解读为 `#E8E8E8`，见 Q3 |
| 控制按钮底 | `#D9D9D9` @25% | `#FFFFFF` | **`#F5F5F5`** | PDF 未给具体值 |

> **内容容器反解出 `#F5F5F5`、与 PDF 解读完全吻合**，这是两个设计源同源的有力交叉验证，也说明本反解方法可靠。

### 6.5 阴影 Token（SVG 滤镜实测）

SVG `filter12_d` / `filter13_d` 实测参数：`feOffset` = 0,0；`feGaussianBlur stdDeviation` = 2~2.5；`feMorphology dilate radius` = 1；颜色矩阵 alpha = **0.25 纯黑**。

换算到 dp（÷2.5）：偏移 0、模糊半径约 1.6~2.0、扩散约 0.4。

| Token | Flutter 值 | 说明 |
|---|---|---|
| `shadowCard`（**忠实还原**） | `BoxShadow(color: Color(0x40000000), blurRadius: 2, spreadRadius: 0.5, offset: Offset.zero)` | 与设计稿完全一致 |
| `shadowCardSoft`（**工程推荐**） | `BoxShadow(color: Color(0x14000000), blurRadius: 8, offset: Offset(0, 2))` | 25% 黑 + 2dp 模糊在真机上视觉接近「深色描边」而非阴影；此变体更符合「微阴影」的观感 |

> 建议：**先按 `shadowCard` 实现，在真机上与 PDF 比对后再决定是否切换到 `shadowCardSoft`**（见 Q11）。

## 8. 实现可行性与技术挑战（Flutter）

供架构师评估用。按风险从高到低排列。

### 8.1 🔴 主题系统迁移（最大改造面）

**现状**：`buildAppTheme(primary)` 用 `ColorScheme.fromSeed` 由用户主色生成；`DerivedPalette.from(primary)` 用 HSL 派生 6 个角色色；`DesignTokens` 混合情绪色。整套体系在 66 个 Dart 文件中被广泛引用，且 `themeMode` 硬编码为 `dark`。

**挑战**：
- 新设计是**固定色板**，与「运行时派生」的架构假设根本冲突
- `PalettePanel`（308 行）提供的「6 组预设主色 + 自定义主色」功能，在固定色板下**失去意义**
- 大量 `theme.colorScheme.onSurface.withValues(alpha: ...)` 式取色需要逐处替换

**建议策略**：
1. 新增 `lib/core/theme/light_tokens.dart`，承载 §6 全部固定 Token（不改动现有文件）
2. `buildAppTheme` 增加 `buildLightTheme()`，用显式 `ColorScheme.light(...)`

### 8.2 🔴 Dock：药丸容器 + 内部圆形选中态

**挑战**：Material 3 的 `NavigationBar` 无法满足——它的 indicator 是**水平胶囊**（`StadiumBorder`，宽 64 × 高 32），且容器是矩形，无法做成满宽药丸。强行改 `NavigationBarThemeData` 只能改 indicator 颜色和形状，改不了「圆形 + 容器药丸化」的组合。

**建议**：**放弃 `NavigationBar`，自定义 `AppDock` 组件**：

```
Container(                      // 药丸容器: h=76, #E6E6E6, StadiumBorder, 白色 1px 描边
  child: Row(
    children: List.generate(4, (i) => Expanded(
      child: InkWell(           // 热区铺满 Expanded
        child: Column(
          AnimatedContainer(    // 44dp 圆, 200ms, 选中=#7C6BFF / 未选中=transparent
            child: Icon(26dp, 选中=白 / 未选中=#999)
          ),
          Text(10dp, 选中=#7C6BFF / 未选中=#999)
        )
      )
    ))
  )
)
```

难度：**中低**。注意 `InkWell` 的水波纹要裁剪到 `StadiumBorder` 内，否则会溢出药丸边界。

### 8.3 🟡 迷你播放器在窄屏溢出（已量化）

右控制胶囊需容纳 4 个 36dp 按钮 + 3 个 6dp 间距 = **162dp**。

| 屏宽 | 单胶囊可用宽 | 是否溢出 |
|---|---|---|
| 390dp | (390 − 28 − 5) ÷ 2 = **178.5** | ✅ 安全 |
| 375dp | (375 − 28 − 5) ÷ 2 = **171** | ✅ 安全 |
| 360dp | (360 − 28 − 5) ÷ 2 = **163.5** | ⚠️ 余量仅 1.5dp |
| 320dp | (320 − 28 − 5) ÷ 2 = **143.5** | ❌ **溢出 18.5dp** |

**建议**：控制按钮宽度改用 `Expanded` 均分而非固定 36dp；或在 `width < 360` 时把间距降到 4dp、按钮降到 32dp（对应 P1-10）。**必须加 `Flexible` / `FittedBox` 兜底，避免 RenderFlex overflow 黄条。**

### 8.4 🟡 设计稿高宽比与真机不符

设计稿内屏 972×1818（比例 0.535），真机 390×844（比例 0.462）——设计稿**更"矮胖"**。

**建议**：严格按「固定 + 弹性」拆分（§4.3）。**禁止**对整屏做等比缩放（`FittedBox` / `Transform.scale`），那会让字号在不同机型上漂移。

### 8.5 🟡 嵌套圆角的同心问题

内容容器圆角 36dp，内部搜索栏（pill）、设置卡片（24dp）、专辑卡（24dp）都是子级圆角。
标准同心公式为 `内圆角 = 外圆角 − 内边距 = 36 − 18 = 18`，但设计稿实际用 24。
**结论**：以设计稿为准（24），不套用公式。这会让内外圆角略不同心，属设计选择。

### 8.6 🟡 清理旧 Shell 的连带影响

`app_shell.dart`（327 行）几乎全部要重写：背景渐变、噪点、粒子、心情入口、调色盘入口、`ControlBar`、`MorePanel`、`VolumeSlider` 全部移除。
连带影响：`app_shell.dart` 引用的 8 个 provider（`moodKindProvider` / `paletteOpenProvider` / `volumeSliderOpenProvider` / `showParticlesProvider` / `sessionSeedProvider` / `derivedPaletteProvider` 等）在主 Shell 不再被消费。
**注意**：不要直接删除这些 provider——`CanvasPage` 仍需要它们（见 8.1 策略 3）。
