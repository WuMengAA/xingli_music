## 〇、结论先行（给决策者的 5 分钟版）

**1. 六个音源的可行性排序（能否真正落进星璃的播放链路）**

| 排序 | 音源 | 结论 | 一句话理由 |
|---|---|---|---|
| ① | **本地网络 SMB** | ✅ 强烈推荐，最先做的"确定性收益" | 无版权风险、无第三方 API 依赖、产物是真实音频字节，完美复用现有 `just_audio` + EQ + 音景 |
| ② | **网易云音乐** | ⚠️ 可行但高风险（用户已拍板做） | 无官方开放 API，靠社区逆向协议；能拿到真实音频 URL，可完整走星璃播放链路；版权与反爬风险由用户自担 |
| ③ | **DLNA 投送** | ✅ 技术可行，但**语义是"出口"不是"音源"** | 投出去后音频在电视/音箱解码，星璃的 EQ / 音景 / 空间音效**全部失效**，需当独立"输出模式"设计 |
| ④ | **Spotify** | ⚠️ 合规可行、体验割裂 | 官方 Web API 只给 30 秒 `preview_url`；完整播放必须走 App Remote SDK 远程控制官方客户端，**音频不经过我们的引擎** |
| ⑤ | **Apple Music** | ⚠️ 门槛最高 | 需 Apple Developer Program 年费 + 自签 Developer Token + 用户订阅；Flutter 无官方插件需自写 Platform Channel；音频同样不过我们的引擎 |
| ⑥ | **QQ音乐** | ❌ 不建议排期 | 与网易云同为逆向路线，但社区实现更少、加密更新更频繁、封禁更激进，投入产出比最差 |

**2. 现有抽象够不够用？** —— **架子对了，但有 3 个硬伤必须先修**，否则任何云音源都接不进来：

- **硬伤 A（致命）**：`Track.uri` 被当成全局唯一身份用（去重 `audio_service.dart:144`、切歌 `playback_controller.dart:74`、收藏 `audio_providers.dart:183`、续播 `settings_repository.dart:42`、锁屏 `audio_handler.dart:91`）。而云音源的播放 URL **是带时效签名的**，每次解析都变 → 收藏失效、续播失效、切歌错乱。
- **硬伤 B**：`MusicSource.resolveStreamUrl()` 接口定义了却**全项目零调用**（10 处命中全是定义与实现，无调用点）——"按需解析播放 URL"这条路**接口有、链路没接**。
- **硬伤 C**：`AudioService._prepareMusic()`（`audio_service.dart:183-198`）只会 `setUrl(track.uri)`，**不支持自定义请求头**。网易云 CDN 常需 `Referer` / `User-Agent` / `Cookie`，SMB 代理需 `Range` 透传，都无处安放。

**3. 网易云 cookie 加密落盘（用户已拍板 AES-256）核心设计**：
**AES-256-GCM（AEAD）+ 主密钥托管到系统安全区（Android Keystore / iOS Keychain / Windows DPAPI）+ 独立密文文件（不进 SharedPreferences）+ 日志脱敏**。
其中**日志脱敏是当前代码里真实存在的泄露点**：`audio_service.dart:150` 会把完整 `uri` 打进日志，而 `LogService` 明文落盘到 `<appSupport>/logs/app.log`（`log_service.dart:36`）并保留 7 天（`log_service.dart:20`）——网易云带鉴权参数的播放 URL 会被原样写进磁盘。**加密做得再好，这一行不改等于白做。**

**4. 最大风险**：**不是技术，是"逆向协议音源的不可控性"**——网易云/QQ 的接口随时可能变更或封禁，属于**外部不可抗力**，且法律上属灰色地带。缓解手段只有"降级不崩"：任一云源失败必须静默退回本地曲库（现有 `musicLibraryProvider` 已具备 catch 兜底骨架，`audio_providers.dart:96-103`）。

**5. 实施顺序建议**：`P0 地基改造(硬伤 ABC) → 网易云 → SMB → DLNA → Spotify → Apple Music → QQ(不排期)`。
总量约 **44~59 人天**（不含 QQ音乐）。详见 §七。

## 一、现状盘点（实读代码，作为一切设计的地基）

### 1.1 音源抽象层：`MusicSource`

`lib/services/music_sources/music_source.dart:8-21` 定义了统一接口，只有 4 个成员：

| 成员 | 签名 | 现状评价 |
|---|---|---|
| `sourceId` | `String get sourceId` | ✅ 够用，但**无类型区分**（云源/本地源/直播流混在一个字符串空间） |
| `enabled` | `bool get enabled` | ✅ 够用 |
| `getTracks()` | `Future<List<Track>>` | ⚠️ **一次性全量拉取**，无分页、无游标、无增量 |
| `resolveStreamUrl()` | `Future<String>` | ❌ **接口存在但零调用**，见 §1.4 |

现有 6 个实现：

| 实现类 | 文件 | 类型 | 备注 |
|---|---|---|---|
| `LocalMusicSource` | `local_music_source.dart` | 本地 | 包装 `LocalMusicScanner` |
| `LocalDirMusicSource` | `local_dir_music_source.dart` | 本地 | 用户自选目录，递归扫描，同名优先 `.mp3`（`:54-58`） |
| `MinecraftMusicSource` | `minecraft_music_source.dart` | 本地 | 场景专属音源 |
| `SubsonicSource` | `subsonic_source.dart` | 远端 | **最接近云音源的现有范本**，见 §1.5 |
| `RadioSource` | `radio_source.dart` | 远端直播流 | 多镜像 fallback（`:14-19`），`isLiveStream: true` |
| `DemoSource` | `demo_source.dart` | 远端 | 3 首 SoundHelix 兜底曲 |

**接口注释自称**（`music_source.dart:5-7`）：
> "现有 AudioService 只认 Track（isRemote → setUrl / setFilePath），因此新增任何源都不必改动播放层，差异全部收敛在 resolveStreamUrl。"

**这句话对本地源与 Subsonic 成立，对云音源不成立**——因为它假设"一个 URL 走天下"，而云音源的 URL 是**临时的、需鉴权头的、会过期的**。见 §三硬伤分析。

### 1.2 数据模型：`Track`

`lib/models/track.dart`：

```
enum TrackSource { local, stream, soundscape }   // :2
title / artist / uri / source / sourceId
isLiveStream / coverUrl / album / duration / coverPath
extras: Map<String, dynamic>?                     // :33 源私有字段逃生舱
bool get isRemote => uri.startsWith('http');      // :50 播放分流的唯一依据
```

- ✅ **`extras` 是最重要的设计遗产**：本地源已用它存 `androidId`/`albumId`（`local_music_scanner.dart:97-100`），云音源可无侵入地塞 `songId`/`vip`/`br`/`expireAt`。
- ❌ **无稳定 id 字段**：全靠 `uri` 当身份。
- ❌ **无请求头字段**：`Track` 不携带 `headers`，播放层也不消费。
- ⚠️ `isRemote` 用 `startsWith('http')` 判定：SMB 若走 `smb://` 前缀会被误判为本地文件路径 → `setFilePath` 必然失败。

### 1.3 播放链路（真实调用顺序）

```
UI / 系统媒体键
   ↓
PlaybackController.play() / skip(dir)          playback_controller.dart:30,49
   ↓  （选曲：nextTrackInLibrary，按 title 排序 + uri 定位）  :59-95
AudioService.playMusic(track)                  audio_service.dart:142
   ├─ 同 uri → 直接续播（去重）                 :144
   ├─ 状态机 → loading                          :154
   ├─ _prepareMusic(track)                      :155 → :183
   │     isRemote ? _music.setUrl(uri)          :186
   │              : _music.setFilePath(uri)     :188
   ├─ setVolume(0) → play() → 状态机 playing    :175-177
   └─ 后台淡入 _fadeMusic                        :180
   ↓
StelarithAudioHandler 订阅状态流 → 发布锁屏 MediaItem   audio_handler.dart:25-49,78-97
```

**关键观察**：
- 整条链路**没有任何一处调用 `MusicSource`**。`AudioService` 只认 `Track`，`PlaybackController` 只认 `Track` 列表。也就是说 **Track 一旦生成，就与它的"娘家源"彻底断联**。
- `_safe()` 兜底（`:129-136`）把所有引擎异常吞掉记日志——这对云音源是**双刃剑**：不会闪退，但"播不出来"会静默失败，用户只看到进度条不动。云音源必须**在 Source 层给出可见的失败原因**（复用现有 `SourceHealth`，见 §1.6）。

### 1.4 `resolveStreamUrl` 是一条断头路（实证）

全库检索 `resolveStreamUrl` 共 10 处命中：1 处接口定义（`music_source.dart:20`）、1 处接口注释（`:7`）、6 处实现（全部是 `async => track.uri` 直接透传）、**0 处调用**。

结论：**"按需重解析播放地址"这个能力在链路上根本没通电**。云音源接入的第一件事就是把这条路接上（§四）。

### 1.5 现有远端源范本：`SubsonicSource`

`subsonic_source.dart` 是目前最有参考价值的远端实现：

- 鉴权：`t = md5(password + salt)`，salt 每次实例化随机（`:31-38`），密码不进 URL。
- 关键设计：**token 长期有效，所以 `getTracks()` 时就把可播放 URL 与封面 URL 预解析好塞进 `Track`**（`:94-101`），播放层零感知。
- `testConnection()`（`:64-74`）供设置页"测试连接"调用。

**它能这么干，是因为 Subsonic 的 stream URL 不过期。网易云不行。**——这正是云音源必须走 `resolveStreamUrl` 懒解析的原因。

### 1.6 曲库聚合与配置层

- `activeSourcesProvider`（`audio_providers.dart:69-88`）：**硬编码组装**——固定 `LocalMusicSource` + 遍历 `localDirConfigsProvider` + 遍历 `serverConfigsProvider` 并按 `SourceType` 二选一（`subsonic` / 否则 `radio`）。**新增源类型必须改这里**。
- `musicLibraryProvider`（`:93-112`）：`Future.wait` 并发拉全部源，单源异常 → 空列表（`:99-101`），全空 → `DemoSource` 兜底（`:107-110`）。**没有超时控制**——一个慢云源会拖住整个曲库首屏。
- `effectiveMusicLibraryProvider`（`:118-134`）：场景专属音源，但**硬编码只认 `MinecraftMusicSource`**（`:124`）。
- `ServerConfig`（`models/server_config.dart`）：`SourceType { subsonic, radio }` 仅两种；字段是 `baseUrl/user/password` 这种**账密模型**，**无法表达 OAuth token / cookie / 刷新令牌**。
- **凭证存储现状（重要）**：
  - `server_config.dart:7` 注释声称"密码等敏感字段存于 flutter_secure_storage"——**与事实不符**。
  - `server_config_provider.dart:11-12` 才是真相："密码随配置一起存于本地 SharedPreferences……若日后需要系统级加密存储，可换 flutter_secure_storage（需 VS 安装 ATL 组件）"。
  - 实测 `pubspec.yaml` 与 `pubspec.lock` 均**无** `flutter_secure_storage`。当前 Subsonic 密码是 **SharedPreferences 明文**（`server_config_provider.dart:44-48` 的 `jsonEncode` 全量写入）。
  - ⚠️ 顺带修正：`ServerConfig.toJson()`（`server_config.dart:60-69`）**没有序列化 `password`**，但 `fromJson` 会读它（`:81`）→ 现状是密码**重启即丢**。这是既有 bug，不属本方案范围，但云音源凭证方案必须避开同类错误。
- **健康状态基建可复用**：`SourceHealth` / `sourceHealthProvider` / `StateChip`（`server_settings_page.dart:69-81, 436-463`）已提供"连接中 / 正常 / 失败 + 上次测试时间"的完整 UI 与状态机，**新音源直接复用，零额外成本**。

### 1.7 设置页（音源管理入口）

`lib/pages/settings/server_settings_page.dart`：三张硬编码 `_GroupCard`——本地目录（`:108`）/ 自建服务器（`:122`）/ 公开电台（`:136`）。
新增音源需**新增卡片 + 新增配置 Sheet**。其中"本地目录"已内置系统文件选择器与 Android SAF `content://` → 真实路径解码（`:211-243`），**SMB 挂载点的 UI 可直接照抄这套交互范式**。

### 1.8 依赖与平台现状（决定新依赖成本）

- `pubspec.yaml` 已有：`http ^1.2.2`、`crypto ^3.0.6`（**只有哈希，没有对称加密**）、`just_audio ^0.9.42`(+`just_audio_windows`)、`audioplayers ^6.1.0`、`audio_service ^0.18.19`、`shared_preferences`、`sqflite ^2.4.1`、`path_provider`、`permission_handler`、`file_picker ^11.0.3`。
- **实测 `pubspec.lock` 中没有**：`dio` / `cookie_jar` / `webview_flutter` / `flutter_inappwebview` / `flutter_secure_storage` / `pointycastle` / `encrypt` / `cryptography`。（仅 `ffi`、`win32` 命中，为其它插件的传递依赖。）
  → **AES-256 与 cookie 抓取所需的能力，目前一个都没有，全是新增依赖。**
- `AndroidManifest.xml` 已声明 `INTERNET` + `ACCESS_NETWORK_STATE`（`:13-14`），✅ 云音源无需新权限。
- **未配置 `networkSecurityConfig` / `usesCleartextTraffic`** → Android 9+ 默认禁明文 HTTP。SMB 本地 HTTP 代理（`http://127.0.0.1:port`）与 DLNA 局域网 HTTP 都会被拦，**必须新增网络安全配置**。
- `minSdkVersion = flutter.minSdkVersion`（`android/app/build.gradle:37`），按 `PROJECT_STATE.md` 为 **API 21**；`abiFilters` 仅 `arm64-v8a` + `armeabi-v7a`（`:44`）。**新增含原生代码的插件必须核对 minSdk 21 与这两个 ABI**（历史教训：`light` 插件因 minSdk 被移除，见 `build.gradle:36`）。
- 当前实际运行平台：Android + Web（`PROJECT_STATE.md` §一）。**Web 平台对本方案几乎全线不可用**（CORS 挡云 API、无 SMB、无 UDP 组播做 SSDP），需在实现中以 `kIsWeb` 全部降级关闭。

## 二、音源全景与目标

### 2.0 先分清三种"音源"，否则方案会打架

星璃现有心智是"音源 = 一批可播放的 Track"。但本次六个目标里，实际上混了三种**本质不同**的东西：

| 类别 | 定义 | 本次目标里的成员 | 能否复用现有 `MusicSource` |
|---|---|---|---|
| **A 类·字节可得** | 我们能拿到真实音频字节流，交给 `just_audio` 解码 | 网易云、QQ音乐、SMB | ✅ 完全复用，EQ / 音景 / 淡入淡出 / 空间音效**全部保留** |
| **B 类·仅可遥控** | 音频由第三方 App / SDK 解码播放，我们只发指令 | Spotify(App Remote)、Apple Music(MusicKit) | ❌ 不能复用。星璃引擎全程旁路 |
| **C 类·输出端** | 不是"进来的源"，是"出去的口" | DLNA 投送 | ❌ 反向链路，需独立"输出设备"概念 |

**这个分类是整份方案的骨架**：A 类接 `MusicSource`，B 类需要新的 `RemotePlaybackAdapter` 抽象，C 类需要新的 `AudioOutputTarget` 抽象。
**强烈建议：一期只做 A 类 + C 类，B 类推迟到有明确用户诉求时再评估**——因为 B 类会撕裂"星璃是一个沉浸式音频引擎"这个产品内核（用户开着 EQ 和雨声音景，切到 Spotify 曲目突然全失效，是极差的体验断层）。

### 2.1 逐源可行性评估

#### ① 本地网络 SMB —— A 类，推荐指数 ★★★★★

| 维度 | 结论 |
|---|---|
| 可行性 | **高**。SMB2/3 是稳定的公开协议，不存在"接口哪天变了"的问题 |
| 授权方式 | 用户自填 `主机 / 共享名 / 用户名 / 密码 / 域`（可选匿名 guest） |
| 版权风险 | **无**。用户播放自己 NAS 上的文件，与现有"本地目录"性质完全一致 |
| 与星璃契合度 | **完美**。产物是真实音频文件流，`just_audio` 直接解码 |
| 主要技术障碍 | `just_audio` **不认 `smb://`**，必须做"SMB → 本地 HTTP 代理"桥接（§六.3） |
| 平台覆盖 | Android / Windows / iOS 均可（纯 Dart 协议栈时）；Web 不可 |

> 这是六个源里**唯一没有外部不可控因素**的一个。建议作为"网易云之后立刻做"的第二顺位，用来对冲云音源被封的风险。

#### ② 网易云音乐 —— A 类，推荐指数 ★★★☆☆（用户已拍板做）

| 维度 | 结论 |
|---|---|
| 可行性 | **中**。**没有面向第三方 App 的官方开放 API**。业界通行做法是复用社区逆向出的 weapi / eapi 协议（如 `NeteaseCloudMusicApi` 类项目的接口定义） |
| 授权方式 | **用户自己的账号 cookie**。三条路径：<br>① 内嵌 WebView 打开官方登录页，登录成功后从 CookieManager 抓 `MUSIC_U`（**推荐**，兼容扫码/短信/密码全部登录方式，且我们不接触用户密码）<br>② 手机号+密码/验证码 直连登录接口（需实现请求体加密，且我们会经手用户密码，**不推荐**）<br>③ 让用户手工粘贴 `MUSIC_U`（**兜底**，零依赖，给高级用户与 WebView 不可用平台） |
| 关键凭证 | `MUSIC_U`（登录态主凭证）+ `__csrf`（部分接口需要）。有效期通常以月计，但**会因异地/风控提前失效**，必须设计失效重登流程 |
| 版权风险 | **高**。仅供个人账号自用；灰色曲/试听曲/无版权曲会返回空 URL 或 试听片段。**必须在 UI 明示"使用你自己的账号，播放能力受账号权益限制"** |
| 反爬风险 | **高**。频率过高会触发风控（返回 -460 / 8810 类错误码）。必须做请求节流 + 指数退避 + 失败静默降级 |
| 播放 URL 特性 | **带签名、有时效**（通常几十分钟到数小时级）。**这是引出全部架构改造的根本原因** |
| 与星璃契合度 | **高**。拿到 URL 后就是普通 HTTP 音频流，EQ / 音景 / 空间音效全部可用 |
| 附加价值 | **歌词**（对应 `TODO_分派方案.md` F-1）。网易云歌词接口返回 LRC 文本，可与本地 `.lrc` 解析共用一套渲染层 |

**必须落到文档里的诚实声明**：本路线依赖**非官方接口**，属于逆向协议调用。接口随时可能变更、被封或需要更新加密算法；本功能**不承诺可用性 SLA**，且**仅限用户本人账号自用，不得用于分发**。

#### ③ DLNA 投送 —— C 类，推荐指数 ★★★★☆

| 维度 | 结论 |
|---|---|
| 可行性 | **高**。UPnP/DLNA 是成熟公开标准：SSDP（UDP 组播 239.255.255.250:1900）发现设备 → 拉 device description XML → 调 AVTransport 服务的 `SetAVTransportURI` / `Play` / `Pause` / `Seek` / `SetVolume` |
| 授权方式 | 无需授权，同一局域网即可 |
| 版权风险 | **无** |
| **关键限制** | 投送时音频由**渲染设备**解码 → 星璃的 EQ（`eq_engine.dart`）、场景音景（`switchSoundscape`）、空间音效（`spatial/`）、音量均衡（`BalanceMode`）**全部失效**。这是协议决定的，无解 |
| 附加要求 | 投送**本地文件**时，必须在手机上起一个 HTTP 服务把文件暴露给电视拉取（局域网 IP，非 127.0.0.1）；投送**网络 URL**（如网易云已解析的 URL）则可直接把 URL 给设备，但带签名的 URL 可能因设备 UA/Referer 不符而失败 |
| 平台覆盖 | Android / Windows / iOS（iOS 需 `NSLocalNetworkUsageDescription` 与 Bonjour 声明）；Web 不可 |

> **产品建议**：DLNA 不要放在"音源"设置里，应放在播放页的"输出到设备"入口（类似系统投屏按钮）。进入投送态时，UI 必须明确降级提示：EQ / 音景 / 空间音效已暂停。

#### ④ Spotify —— B 类，推荐指数 ★★☆☆☆

| 维度 | 结论 |
|---|---|
| 可行性 | 元数据**高**，播放**受限** |

## 三、现有音源抽象评估：能统一，但要先补三个洞

**总结论：`MusicSource` 抽象的方向是对的，不需要推倒重来；但它是按"URL 永久有效的静态曲库"假设设计的，而云音源是"URL 临时、需鉴权头、需分页、会失效"的动态曲库。**
**改造策略：不改接口语义，只做"加法"——补 3 个洞 + 加 1 个可选扩展接口。目标是"老源零改动，新源能落地"。**

### 3.1 硬伤 A：`uri` 被当成全局主键（致命，必须先修）

**证据链（5 处真实依赖）**：

| # | 位置 | 代码含义 | 云音源下会怎样 |
|---|---|---|---|
| 1 | `audio_service.dart:144` | `if (_currentTrack?.uri == track.uri)` → 同曲续播 | URL 每次解析都变 → 判定为"不同曲" → 重新加载，正在播的歌被打断 |
| 2 | `playback_controller.dart:74` | `sorted.indexWhere((t) => t.uri == current.uri)` → 定位当前曲 | 定位失败（`idx < 0`）→ 走 `:76` 分支跳回第一首/最后一首 → **下一首功能错乱** |
| 3 | `audio_providers.dart:183` | `favoriteProvider` 是 `Set<String>` 存 uri | 重启后 URL 变了 → **收藏全部失效** |
| 4 | `settings_repository.dart:42` | `kLastTrackUri` 持久化上次曲目 | 冷启动按 URL 恢复 → **URL 已过期，续播必失败** |
| 5 | `audio_handler.dart:91` | `MediaItem(id: t.uri, ...)` | 锁屏媒体项 id 漂移，系统侧去重/历史紊乱 |

**方案（最小侵入，向后兼容）**：
给 `Track` 增加**稳定身份**，而不是替换 `uri`：

```
// models/track.dart 增补（示意，不在本方案中实现）
final String? id;                       // 源内稳定 id，如网易云 songId
String get key => id != null && id!.isNotEmpty
    ? '$sourceId::$id'                  // 云源：源内 id 拼源前缀
    : uri;                              // 本地源/旧源：退化为 uri，行为完全不变
```

- 上述 5 处逐一从 `uri` 改判 `key`。**本地源 `id == null` → `key == uri` → 行为逐字节等价**，零回归风险。
- `favoriteProvider` / `kLastTrackUri` 存的是历史 uri：加一次性迁移（旧值直接当 key 用即可，因为本地源 key 就是 uri）。
- `MediaItem.id` 换成 `key`。

**这一步是所有云音源的前置条件，不做则后面全是沙上建塔。**

### 3.2 硬伤 B：`resolveStreamUrl` 没接线

**现状**：接口有（`music_source.dart:20`），实现有 6 个，**调用 0 次**（§1.4 实证）。

**方案**：在 `AudioService.playMusic()` **之前**插入解析层。**不要把解析塞进 `AudioService`**——它当前不依赖任何 Source，保持这份干净很值钱。正确落点是 `PlaybackController` 与 Riverpod 层之间：

```
新增 providers/audio/source_registry_provider.dart（示意）
  musicSourceRegistryProvider : Provider<Map<String, MusicSource>>
      由 activeSourcesProvider 派生：{ s.sourceId : s }

新增 services/music_sources/stream_resolver.dart（示意）
  Future<PlayableSource> resolve(Track t):
     1. registry[t.sourceId] 取不到 → 直接用 t.uri（老行为）
     2. 取到且 t 未过期（extras['expireAt'] 未到）→ 用 t.uri（走缓存）
     3. 否则 await source.resolveStreamUrl(t) → 得到新 URL
     4. 失败 → 抛 SourceResolveException（带可读原因，供 UI 展示）
```

`PlaybackController.play()/skip()` 在调 `audio.playMusic(t)` 前先过 resolver，把解析后的 `Track`（uri 已刷新，key 不变）交给引擎。
**注意**：`PlaybackController` 现在刻意不依赖 Riverpod（`playback_controller.dart:10-11` 注释），所以 resolver 应该像 `setResolvers()`（`:21-27`）一样**注入进去**，保持这个设计不被破坏。

### 3.3 硬伤 C：播放层不支持请求头（也不认非 http 协议）

**现状**：`_prepareMusic()`（`audio_service.dart:183-198`）只有二选一：`setUrl(uri)` / `setFilePath(uri)`，判据是 `uri.startsWith('http')`（`track.dart:50`）。

**问题**：
- 网易云 CDN 部分资源需要 `Referer` / `User-Agent`，甚至 `Cookie`。
- SMB 代理需要透传 `Range`（拖动进度条必需）。
- `smb://` 前缀会被 `isRemote` 判为 false → 走 `setFilePath` → 必然失败。

**方案**：引入播放源描述对象，取代裸字符串：

```
// 示意
class PlayableSource {
  final String uri;
  final Map<String, String>? headers;   // 新增
  final PlayableKind kind;              // file / http / hls
  final DateTime? expireAt;             // 供 resolver 判缓存
}
```

`_prepareMusic` 改为：
- `kind == file` → `setFilePath`
- 否则 → `setAudioSource(AudioSource.uri(Uri.parse(uri), headers: headers))`
（`just_audio` 的 `AudioSource.uri` 支持 headers；项目已在 `audio_service.dart:261` 用过 `setAudioSource(AudioSource.file(...))`，用法一致）
- ⚠️ **平台注意**：headers 在部分平台（尤其 Web / 某些 Windows 后端）支持不完整，需在实现阶段实测 `just_audio_windows`；不支持时的降级策略是"把必要参数拼进 query"或"经本地代理注入头"。

**协议兜底**：`smb://` 等非 http 协议**永远不直接交给 `just_audio`**，一律由对应 Source 在 `resolveStreamUrl` 里转换成 `http://127.0.0.1:<port>/...` 代理地址（§六.3）。这样 `AudioService` 的认知边界维持在"file 或 http"，不被污染。

### 3.4 需要"加法"的第 4 处：大曲库分页

`musicLibraryProvider`（`audio_providers.dart:93-112`）一次 `Future.wait` 拉全部源全量曲目。网易云一个账号的收藏+歌单轻松几千首，全量拉取会：首屏卡死、内存膨胀、触发风控。

**方案（不改老接口）**：新增可选能力接口，老源不实现即自动走老路径：

```
// 示意
abstract class PagedMusicSource implements MusicSource {
  Future<List<MusicCollection>> getCollections();          // 歌单/收藏/专辑列表（轻量）
  Future<TrackPage> getCollectionTracks(String id, {int offset, int limit});
}
```

聚合层策略调整为：
- 云源的 `getTracks()` **只返回"用户已固定/已同步"的小集合**（如"我喜欢的音乐"前 N 首），保证首屏快；
- 完整歌单走曲库页按需分页加载。
- 同时给 `Future.wait` **加超时**（建议 8s），超时源按空处理，避免一个慢源拖垮首屏。

### 3.5 配置模型：`ServerConfig` 撑不住云音源

`SourceType { subsonic, radio }` 与 `baseUrl/user/password` 账密模型（`server_config.dart:9-28`）无法表达"OAuth token + refresh token + 过期时间"或"cookie 串"。

**方案**：**不要硬塞进 `ServerConfig`**（会污染现有 Subsonic/Radio 逻辑并牵动 `activeSourcesProvider:79-86` 的 if/else）。改为**并列新增**：

```
models/cloud_account.dart（示意）
  enum CloudProvider { netease, qq, spotify, appleMusic }
  class CloudAccount {
    provider / displayName / uid / avatarUrl
    enabled / boundAt / expireAt
    // ⚠️ 凭证本身不在这里，只存一个引用键，密文另存（§五）
    credentialRef: String
  }

models/smb_share_config.dart（示意）
  host / port / shareName / subPath / username / domain / anonymous / enabled
  // password 同样只存引用键，密文另存
```

`activeSourcesProvider` 相应扩展为"本地源 + 目录源 + ServerConfig 源 + CloudAccount 源 + SMB 源"的组装。

### 3.6 评估结论

| 问题 | 是否需要改现有代码 | 侵入性 | 回归风险 |
|---|---|---|---|
| A. Track 稳定 id (`key`) | 是，6 个文件 | 中 | **低**（本地源退化为原行为） |
| B. resolveStreamUrl 接线 | 是，`PlaybackController` + 新 provider | 中 | 低（无 Source 匹配时走老路） |
| C. headers + 协议分流 | 是，`AudioService._prepareMusic` | 中 | 中（需回归本地/Subsonic/电台三类播放） |
| D. 分页扩展接口 | 否（纯新增） | 低 | 无 |
| E. 云账号/SMB 配置模型 | 否（纯新增）+ `activeSourcesProvider` 扩展 | 低 | 低 |

**答案是"统一接入点"而非"逐源适配"**：补完 A/B/C/D/E 后，网易云、QQ、SMB 都是标准 `MusicSource` 实现；Spotify L1（30s 试听）也能塞进来；只有 Spotify L2 / Apple Music（B 类）和 DLNA（C 类）需要各自独立的抽象。

## 四、网易云音乐接入详细设计

> 用户已拍板：**cookie 用 AES-256 企业级加密持久化**。本章是全文最重点章节。

### 4.1 分层结构（建议落点）

```
lib/services/music_sources/netease/
├── netease_source.dart          # 实现 MusicSource + PagedMusicSource（对外唯一门面）
├── netease_client.dart          # HTTP 客户端：签名/加密请求体、cookie 注入、节流、重试
├── netease_crypto.dart          # 协议层加密（weapi/eapi 的 AES+RSA），⚠️ 与凭证加密是两回事
├── netease_models.dart          # 歌单/歌曲/歌词 DTO ↔ Track 映射
└── netease_auth.dart            # 登录编排：WebView 抓 cookie / 手工粘贴 / 校验 / 登出

lib/services/security/           # ★ 通用安全层，不属于网易云，SMB/Spotify 共用
├── secure_vault.dart            # AES-256-GCM 加解密 + 主密钥托管（本章 §4.4）
├── master_key_provider.dart     # 主密钥获取/生成/降级 KDF
└── credential_store.dart        # credentialRef → 密文文件 的读写与擦除

lib/providers/audio/netease_providers.dart   # 登录态 / 歌单列表 / 分页曲目
lib/pages/settings/netease_login_page.dart   # WebView 登录页
```

**必须强调**：`netease_crypto.dart`（**协议加密**，为了让网易云服务器认我们的请求）与 `secure_vault.dart`（**凭证加密**，为了保护落盘的用户 cookie）是**两个完全独立的东西**，不要混在一个文件里，否则后续维护必然出错。用户拍板的 AES-256 指的是**后者**。

### 4.2 端到端流程

```
① 用户在「设置 → 音源 → 网易云音乐 → 登录」
        ↓
② NeteaseLoginPage 内嵌 WebView 打开官方登录页
   （支持扫码 / 短信 / 密码，全部由官方页面处理，我们不接触密码）
        ↓
③ 监听页面导航；登录成功后从 WebView CookieManager 读取 cookie
   关键字段：MUSIC_U（登录态主凭证）、__csrf（部分接口需要）
        ↓
④ 立即调「获取账号信息」接口验证 cookie 有效性
   有效 → 拿到 uid / 昵称 / 头像；无效 → 提示重试，不落盘
        ↓
⑤ ★ 加密落盘（§4.4）：
   明文 JSON { cookies, uid, nickname, savedAt, expireHint }
   → AES-256-GCM 加密 → 写 <appSupport>/secure/cred_netease.bin
   → CloudAccount{credentialRef:'netease'} 写 SharedPreferences（不含任何凭证）
        ↓
⑥ NeteaseSource 上线：注册进 activeSourcesProvider
        ↓
⑦ 曲库拉取：
   getCollections() → 「我喜欢的音乐」+ 用户歌单列表（轻量，只有名称/封面/数量）
   getTracks()      → 只返回「我喜欢的音乐」前 N 首（默认 200），保首屏
   getCollectionTracks(id, offset, limit) → 曲库页按需分页
   → 映射成 Track（uri 此时留空或填占位，真正的播放 URL 不在这里解析）
        ↓
⑧ 播放：PlaybackController → StreamResolver → NeteaseSource.resolveStreamUrl(track)
   → 调「歌曲播放 URL」接口（带 songId + 音质档位 br）
   → 返回带签名的临时 URL + 过期时间 → 写入 Track.uri / extras['expireAt']
   → AudioService 用 AudioSource.uri(url, headers:{Referer, User-Agent}) 播放
        ↓
⑨ 歌词：按 songId 拉 LRC 文本 → 与本地 .lrc 走同一解析/渲染层（对接 F-1）
        ↓
⑩ 失效处理：任一接口返回未登录/风控 → 标记 SourceHealth.failed
   → 曲库静默降级回本地源 → 设置页红色提示「网易云登录已失效，请重新登录」
```

### 4.3 关键实现要点

#### (1) Cookie 抓取（步骤 ②③）

- **推荐主路径：WebView**。理由：兼容全部登录方式；我们不经手用户密码（合规与安全上都更干净）；用户认知成本最低（就是官方登录页）。
- 需新增 WebView 依赖（`pubspec.lock` 实测当前无任何 webview 包）。选型时**必须核对**：Android minSdk ≤ 21（本项目 `build.gradle:37`）、支持读取 CookieManager、Windows 桌面端行为（`just_audio_windows` 说明项目有桌面诉求）。
- **兜底路径必须做**：手工粘贴 `MUSIC_U`。用于 WebView 不可用的平台（Web / 部分精简 Android，参考 `local_music_scanner.dart` 为 Wear OS 做 fallback 的同款思路）以及 WebView 抓取失败时的自救。
- **禁止**：自建登录 UI 收集用户账号密码后直连登录接口。

#### (2) 请求客户端（`netease_client.dart`）

| 关注点 | 设计 |
|---|---|
| 协议加密 | weapi（AES-128-CBC + RSA 包裹 secretKey）/ eapi（AES-128-ECB + MD5 摘要）。**注意：协议层用的是 AES-128，这是网易云协议规定的，不是我们的安全等级选择**；用户拍板的 AES-256 作用于凭证落盘 |
| Cookie 注入 | 每次请求注入 `MUSIC_U`；需要 csrf 的接口从 cookie 取 `__csrf` 拼进 query |
| 必备请求头 | `User-Agent`（桌面浏览器 UA）、`Referer: https://music.163.com`。播放 CDN URL 同样需要 |
| **节流** | 全局串行队列 + 最小间隔（建议 ≥300ms）+ 并发上限（建议 ≤3）。**反爬第一道防线** |
| **重试** | 指数退避（1s/2s/4s，上限 3 次），仅对网络错误与 5xx 重试；对"未登录/风控"错误码**立即失败不重试**（重试只会加剧封禁） |
| 超时 | 单请求 10s，与 §3.4 聚合层 8s 超时配合 |
| **日志脱敏** | 见 §4.5，**强制要求** |

#### (3) 数据映射（`Track` 填充约定）

| Track 字段 | 来源 | 说明 |
|---|---|---|
| `id`（新增） | 网易云 songId | **稳定主键**，`key = 'netease::123456'` |
| `title` / `artist` / `album` | 接口字段 | 多歌手用 ` / ` 连接 |
| `uri` | **懒解析** | `getTracks` 阶段填占位（如 `netease://song/123456`）；播放前由 resolver 换成真实 URL。⚠️ 占位符不得以 `http` 开头，避免被 `isRemote`(`track.dart:50`) 误判后直接送进 `setUrl` |
| `source` | `TrackSource.stream` | 复用现有枚举，**不新增枚举值**（`track.dart:2` 改动会牵动全项目） |
| `sourceId` | `'netease'` | resolver 靠它在 registry 里找回 Source |
| `coverUrl` | 专辑图 URL | 锁屏封面已支持 `coverUrl`（`audio_handler.dart:86-87`） |
| `duration` | 接口字段 ms | 曲库列表直接可显示时长 |
| `extras` | `{songId, vip, fee, maxBr, expireAt, needHeaders}` | 复用现有逃生舱（`track.dart:33`），**零模型改动** |

#### (4) 播放 URL 解析（`resolveStreamUrl`）

- 入参 `Track` → 取 `extras['songId']` → 请求播放 URL 接口（带音质档位）。
- **三种失败必须区分并给出人话提示**（否则用户只会看到"播不出来"）：
  1. 返回 `url == null` → **无版权 / 已下架**（"该歌曲在你的账号下无法播放"）
  2. 返回试听片段 / `fee` 标记付费 → **需要会员**（"需要网易云会员，可试听 xx 秒"）
  3. HTTP 401/302 到登录页 / 风控错误码 → **登录失效**（触发重登流程）
- 成功后写 `extras['expireAt']`，resolver 据此复用缓存，避免每次切歌都打接口（同时也是反爬保护）。

#### (5) 歌词（对接 `TODO_分派方案.md` F-1）

- 按 songId 拉取 LRC 文本（含逐字/翻译版本时优先"原文 + 翻译"双行）。
- **建议**：歌词解析器写成**与音源无关**的独立模块（`services/lyrics/`），本地 `.lrc` 与网易云共用；网易云侧只负责"给出 LRC 字符串"。这样 F-1 与 F-2 不互相阻塞。
- 缓存：`<appSupport>/lyrics/netease_<songId>.lrc`，**歌词非敏感，无需加密**。

### 4.4 ★ Cookie 加密落盘设计（AES-256，用户拍板项）

> **威胁模型先说清楚**：本设计防的是 —— ① 手机被 root / 被物理接触时，凭证不以明文躺在磁盘上；② 应用数据被云备份或被 `adb backup` 导出时不泄露；③ 日志、崩溃报告、缓存文件不意外带出凭证；④ 应用被卸载重装或换设备时凭证自然失效。
> 本设计**不能**防：设备已被完全攻陷且应用运行时内存被 dump（此为客户端加密的理论上限，任何方案都一样）。诚实写明这一点，比声称"绝对安全"更专业。

#### (1) 算法选型

| 项 | 选择 | 理由 |
|---|---|---|
| 对称算法 | **AES-256-GCM** | 用户拍板 AES-256；GCM 是 AEAD，**自带完整性校验**，能识别密文被篡改。**明确禁止 ECB**（模式泄露明文结构）、**禁止无 MAC 的 CBC**（可被篡改而不可察觉） |
| 密钥长度 | 256 bit（32 字节） | 拍板项 |
| IV / Nonce | **12 字节，每次加密由 `Random.secure()` 全新生成** | GCM 的 12 字节是标准长度；**IV 绝对不可重用**——同密钥下 nonce 重用会彻底摧毁 GCM 安全性。项目已有 `Random.secure()` 使用先例（`subsonic_source.dart:32-33`） |
| Tag | 128 bit | GCM 标准 |
| AAD | `magic + version + kdfId` | 让文件头也纳入完整性保护，防止降级攻击（例如把 kdfId 改成弱 KDF） |

#### (2) 主密钥（MK）托管——三级策略

**这是整个设计里最关键的一环。密钥若与密文放在一起，AES-256 等于零。**

```
Tier 1（首选）：系统安全区托管
  MK = 32 字节随机数（Random.secure()），生成后立即存入平台安全存储：
    · Android → Keystore 支撑的 EncryptedSharedPreferences
    · iOS     → Keychain，可访问性 kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly
                （关键：ThisDeviceOnly = 不随 iCloud 钥匙串同步到其它设备）
    · Windows → DPAPI（用户级）
  依赖：flutter_secure_storage（项目当前无此依赖，见 §1.8）

Tier 2（降级）：KDF 派生
  触发条件：Tier 1 不可用。
  ⚠️ 这不是假设——server_config_provider.dart:11-12 明确记录过
     「若日后需要系统级加密存储，可换 flutter_secure_storage（需 VS 安装 ATL 组件）」，
     说明 Windows 侧曾遇到该插件的构建门槛。此降级路径必须真实存在。
  MK = PBKDF2-HMAC-SHA256(
         password = 设备指纹 + 应用内固定盐 + 首次运行生成的随机 appSalt,
         salt     = 随文件保存的 16 字节随机盐,
         iterations = 200_000,  dkLen = 32 )
  安全等级低于 Tier 1（设备指纹可被同设备上的其它应用近似推测），
  必须在设置页明示：「当前设备不支持系统级密钥保护，凭证以降级模式加密」。

Tier 3（最强，可选）：用户口令加固
  用户自设一个应用锁口令：MK = PBKDF2(用户口令, salt, 200k)。
  优点：即使设备被攻陷，无口令也解不开。
  缺点：每次冷启动需输入。建议做成「高级设置」开关，默认关闭。
```

**铁律**：
- MK **绝不硬编码在源码里**（反编译 5 分钟就能拿到，等于没加密）。
- MK **绝不写进 SharedPreferences / 日志 / 崩溃上报**。
- MK 只在内存中以 `Uint8List` 短暂持有，用完后**主动清零**（`fillRange(0, len, 0)`）。

#### (3) 密文文件格式

存放位置：`<getApplicationSupportDirectory()>/secure/cred_<provider>.bin`
（**不放 SharedPreferences**：SP 是明文 XML/plist，且易被备份工具整体导出。项目日志已用 `getApplicationSupportDirectory()`，见 `log_service.dart:31`，路径习惯一致。）

```
偏移  长度   字段        说明
0     4     magic       "XLSC"（XingLi Secure Credential）
4     1     version     格式版本，当前 0x01，用于未来平滑升级
5     1     kdfId       0x00 = Tier1 系统安全区直存 MK
                        0x01 = Tier2 PBKDF2 设备指纹派生
                        0x02 = Tier3 PBKDF2 用户口令派生
6     2     reserved    对齐保留，置 0
8     16    salt        Tier2/3 的 KDF 盐；Tier1 置随机值（不参与运算）
24    12    iv          GCM nonce，★每次写入全新随机
36    N     ciphertext  AES-256-GCM 密文
36+N  16    tag         GCM 认证标签
```

AAD = 前 8 字节（magic + version + kdfId + reserved）。

#### (4) 明文结构（加密前的 JSON）

```json
{
  "v": 1,
  "provider": "netease",
  "cookies": { "MUSIC_U": "...", "__csrf": "...", "NMTID": "..." },
  "uid": 123456789,
  "nickname": "星璃用户",
  "savedAt": "2026-08-10T12:00:00Z",
  "expireHint": "2026-11-10T12:00:00Z",
  "deviceBinding": "<设备指纹哈希>"
}
```

- `deviceBinding`：解密后校验，与当前设备不符则**直接判定失效并擦除**——防止密文文件被整体复制到另一台设备使用。
- `expireHint` 只是提示，**真正的有效性以接口返回为准**（服务端可能提前失效）。

#### (5) 读写与生命周期

| 操作 | 行为 |
|---|---|
| **写入** | 全新 IV → 加密 → **原子写**（先写 `.tmp` → `rename` 覆盖），避免掉电产生半截文件 |
| **读取** | 冷启动**不主动解密**；首次真正需要用（拉曲库/播放）时才解密，解密结果只在内存 Session 对象里持有 |
| **内存** | `NeteaseSession` 单例持有明文 cookie；应用退到后台超过阈值（如 30 分钟）可主动丢弃，下次用时重新解密 |
| **失效** | 接口返回未登录 → 立即擦除文件 + 清内存 + `SourceHealth.failed` + UI 提示重登 |
| **登出/解绑** | **先用随机字节覆写同长度，再删除文件**（尽力而为的抗恢复；注意在 SSD/闪存 wear-leveling 下不能保证物理擦除，此为已知局限） |
| **格式升级** | 靠 `version` 字段：读到旧版本 → 用旧规则解密 → 用新规则重新加密写回 |
| **解密失败** | 一律当作"凭证损坏"处理：擦除 + 要求重新登录。**绝不吞掉异常继续用空 cookie 发请求**（会被风控记账） |

#### (6) 平台侧配套（易漏，必须做）

- **Android**：`android:allowBackup="false"`，或配置 backup rules 显式排除 `secure/` 与 `logs/` 目录。否则 AES 加密的努力会被"云备份把整个 app 数据搬走 + 换设备恢复"绕过一层（虽然 deviceBinding 能兜住，但不应依赖单点）。
- **iOS**：Keychain 项使用 `...ThisDeviceOnly`；密文文件目录设置"不参与 iCloud 备份"标记。
- **Windows**：DPAPI 为用户级加密，同一 Windows 账户下的其它程序理论可解——需在文档中标注为已知局限。
- **Web**：**不支持安全存储，直接禁用云音源登录功能**（`kIsWeb` 短路），不要用 localStorage 存任何凭证。

### 4.5 ★ 日志脱敏（真实泄露点，必须与加密同批修）

**这是本次代码通读发现的最严重的实际问题：**

```dart
// lib/services/audio/audio_service.dart:150-151
LogService.instance.i(
    'audio', '播放: ${track.title} [${track.sourceId}] uri=${track.uri}');
```

而 `LogService`：
- 明文追加写入 `<appSupport>/logs/app.log`（`log_service.dart:31-39`）
- 保留 **7 天**（`log_service.dart:20`）
- 同时 `debugPrint` 到控制台（`log_service.dart:111`）

**后果**：网易云带鉴权签名的播放 URL（以及未来 SMB 代理 URL 里可能携带的 token）会被**逐条明文写进磁盘并保留一周**。凭证文件加密到 AES-256，日志里却躺着可直接播放的签名 URL —— **整套加密的实际防护效果被绕过**。

**要求（与 §4.4 同批次交付，不可拆分）**：
1. 新增统一脱敏函数（如 `LogService` 内的 `redactUri`）：只保留 scheme + host + path 末段，**query 全部替换为 `?<redacted>`**。
2. `audio_service.dart:150`、`local_music_scanner.dart` 等所有打印 uri/path 的位置统一改走脱敏函数。
3. 云音源客户端**禁止**打印请求头、cookie、响应体原文；只打印"接口名 + 状态码 + 错误码 + 耗时"。
4. 建立一条硬约定并写进 `docs/API_CONTRACT_FROZEN.md` 类的契约文档：**任何 `LogService` 调用不得直接内插完整 URL**。

### 4.7 网易云 PC Web 登录取源（2026-08-10 调研）

> 本节为 2026-08-10 追加的可行性调研结论，聚焦"能否复用网易云官方 PC Web（music.163.com）的登录态 + 播放接口直接取音源"，供 §4.1~§4.6 落地时选型参考。不涉及实现代码（仅给出伪代码草图与常量）。

#### 4.7.1 可行性结论

**有条件能 ⚠️**

理由：网易云 PC Web 的登录态（cookie `MUSIC_U`）与播放地址接口（`/api/song/enhance/player/url`）均依赖一套已被社区完整逆向的私有加密协议（weapi / eapi）。其登录与取源**可以**在 App 内复现（WebView 拿 cookie + Dart 自实现加密直连），但本质是逆向私有接口、处于灰色地带，且接口随时可能因风控/版权而变更或加强校验，**稳定性与长期可用性不可保证**。

核心可行点：
- 登录可走 WebView 注入官方页面、或直接复刻二维码登录接口拿 `MUSIC_U`；
- 播放地址接口返回**可直接播放的 HTTPS URL**，且最高支持无损/Hi-Res（需登录态 + 会员）；
- 加密协议完全公开（常量固定），纯 Dart 即可实现，无需服务端。

核心不确定点（见 §4.7.6 风险）：
- 网易云对异常请求的反爬/风控强度不可控；
- 接口随时可能升级加密或加签名校验；
- 版权与 ToS 风险（见 §4.7.7）。

#### 4.7.2 推荐路线

**路线 A：自实现 Dart weapi/eapi 直连（推荐，与本项目风格一致）**

- 在 App 内用纯 Dart 复刻 weapi（两次 AES-128-CBC + RSA 无填充）与 eapi（AES-128-ECB + MD5 签名），直接用 `http` 调用网易云接口；
- 登录走 WebView（复用 §4.1 已规划方案）或二维码登录拿 `MUSIC_U`，cookie 文件经 `SecureBox` 加密落盘；
- 参考实现：`hcanyz/flutter-netease-music-api`（纯 Dart，依赖 `encrypt` + `pointycastle`）、社区 `netease_music_cipher`（Flutter 插件，原生实现）、`enten0103/music_sdk`（Dart SDK）。
- **需新增依赖**：`encrypt: ^5.0.3`、`pointycastle: ^3.9.1`（`pubspec.yaml` 当前仅有 `crypto`、`http`、`shared_preferences`，无加密库）。这与本项目"纯 Dart 自实现加密"的技术取向一致（§4.4 已自实现 AES-256 落盘）。

**路线 B：本地/自托管代理中间件（NeteaseCloudMusicApi 类）**

- 在本地或自有服务器跑一个 Node/Go 中间件，App 只跟中间件交互，由中间件完成加密与登录态托管；
- 优点：协议升级只需改服务端、App 零改动；缺点：**引入长期部署/维护/可用性负担**，且 Node 中间件在移动端常驻违背轻量原则。
- 现状注意：原 Binaryify/NeteaseCloudMusicApi（~30k star）已于 **2024-01 因版权法务通知删库停更**，社区仅存 fork（bigleek、yanranxiaoxi、hcanyz 等）。选型前须评估 fork 的活跃度与维护风险。

**结论**：采用路线 A。项目已用纯 Dart 自实现 AES-256 凭证加密，延续自实现风格、避免新增代理服务的部署维护成本最为契合；但需接受"协议变更时 App 需发版升级"的代价。

#### 4.7.3 所需步骤清单

1. `pubspec.yaml` 新增 `encrypt`、`pointycastle` 依赖（或评估用现有 `crypto` 自写 AES-128/RSA 以零新增依赖）。
2. 实现 weapi / eapi 加密模块（见 §4.7.4 伪代码），含请求体加密与响应体解密。
3. 实现登录态获取：
   - 方案 a：WebView 加载官方登录页，登录成功后从 cookie 提取 `MUSIC_U` / `__csrf`；
   - 方案 b（可选）：复刻二维码登录三步（见下文备注）。
4. 登录态经 `SecureBox` 加密落盘（见 §4.7.5），登出时 `deleteSecret` 擦除。
5. 调用播放地址接口（旧版 `/api/song/enhance/player/url` 带 `br`，或新版 v1 `/api/song/enhance/player/url/v1` 带 `level`）获取直链。
6. 将直链交给 `audio_service` / `just_audio` 播放，并按 §4.1 的 `extras['expireAt']` 机制处理 URL 过期重解析。
7. 接入 §4.6 验收（日志脱敏、篡改检测、设备绑定、失效降级）。

> 备注：二维码登录三步接口（均为 weapi）
> - 取 unikey：`POST /weapi/login/qrcode/unikey`，body `{"type":1}` → 返回 `unikey`；
> - 二维码内容：`https://music.163.com/login?codekey={unikey}`；
> - 轮询 `POST /weapi/login/qrcode/client/login`，body `{"key":unikey,"type":1}`；
> - 状态码：`800`=过期、`801`=待扫描、`802`=待确认、`803`=成功（此时 `Set-Cookie` 含 `MUSIC_U`）。
> - 登录态校验：`POST /weapi/w/nuser/account/get` 返回 uid/昵称/头像。

#### 4.7.4 Dart weapi / eapi 加密伪代码草图

```dart
// ===== 关键常量（来自社区逆向，固定值）=====
const iv            = '0102030405060708';              // 16 字节 IV
const presetKey     = '0CoJUm6Qyw8W8jud';              // 第一次 AES 的预设密钥
const pubKeyExp     = '010001';                         // RSA 指数
const pubKeyMod     = '00e0b509f6259df8642dbc3566290147'
                      '7df22677ec152b5ff68ace615bb7b72'
                      '5152b3ab17a876aea8a5aa76d2e4176'
                      '29ec4ee341f56135fccf695280104e0'
                      '312ecbda92557c93870114af6c9d05c'
                      '4f7f0c3685b7a46bee255932575cce1'
                      '0b424d813cfe4875d3e82047b97ddef'
                      '52741d546b8e289dc6935b3ece0462'
                      'db0a22b8e7';                      // RSA 模数（2048 bit）
const base62        = 'abcdefghijklmnopqrstuvwxyzABC'
                      'DEFGHIJKLMNOPQRSTUVWXYZ0123456789';
const eapiKey       = 'e82ckenh8dichen8';              // eapi AES-128-ECB 密钥（无 IV）
const eapiSalt      = '36cd479b6b5';                   // eapi MD5 盐值

// ===== weapi：请求体加密（返回 form 字段）=====
Map<String,String> weapiEncrypt(Map<String,Object> raw) {
  final text = jsonEncode(raw);
  // 1) AES-128-CBC(presetKey, iv) 加密 text → base64
  final step1 = aes128CbcEncrypt(text, presetKey, iv).toBase64();
  // 2) 随机 16 字节 secretKey（取自 base62 字符集）
  final secret = List.generate(16, (_) => base62[randInt(62)]).join();
  // 3) AES-128-CBC(secret, iv) 加密 step1 → base64  => params
  final params = aes128CbcEncrypt(step1, secret, iv).toBase64();
  // 4) RSA 无填充加密 secret.reverse() => encSecKey（转 hex）
  final encSecKey = rsaNoPaddingEncrypt(secret.split('').reversed.join(),
                                        pubKeyMod, pubKeyExp).toHex();
  return {'params': params, 'encSecKey': encSecKey};
}

// ===== eapi：请求体加密（URL 把 /api/ 换成 /eapi/）=====
String eapiEncrypt(String url, Map<String,Object> raw) {
  final body     = jsonEncode(raw);
  final digest   = md5('nobody${url}use${body}md5forencrypt'); // + eapiSalt 视版本
  final plain    = '${url}-36cd479b6b5-${digest}-${body}';
  return aes128EcbEncrypt(plain, eapiKey).toHex();   // 响应体同样需 AES-128-ECB 解密
}

// ===== 调用示例：取播放地址（旧版 eapi）=====
Future<String> fetchPlayerUrl(int songId, int br) async {
  const api = '/api/song/enhance/player/url';
  final data = {'ids': jsonEncode([songId]), 'br': br}; // br=999000 为无损
  final enc  = eapiEncrypt(api, data);
  final resp = await http.post(
    Uri.parse('https://interface3.music.163.com/eapi/song/enhance/player/url'),
    headers: {'Cookie': cookieLine, 'Referer': 'https://music.163.com/'},
    body: enc,
  );
  return eapiDecrypt(resp.body)['data'][0]['url'];
}
```

> 注：`rsaNoPaddingEncrypt` 须用 RSA **NoPadding**（即 PKCS1 但无填充），Dart 侧可参考 `hcanyz/flutter-netease-music-api` 的 `encrypt_ext.dart`（子类化 `PKCS1Encoding` 覆写填充）。`csrf_token` 取自已登录 cookie 的 `__csrf` 字段，weapi 请求时随 body 附带。

#### 4.7.5 Cookie 处理（复用现有 SecureBox）

登录成功拿到 `MUSIC_U` / `__csrf` 等字段后，**不要**直接 `shared_preferences.setString`，统一走项目已有的 `SecureBox` 保险箱（AES-256-CBC + HMAC-SHA256，PBKDF2 派生，详见 §4.4 与 `lib/services/security/secure_store.dart`）：

## 五、其余音源接入路径

### 5.1 SMB 本地网络共享（A 类，第二顺位）

**目标**：把 NAS / Windows 共享文件夹当成一个"远程本地目录"，体验对齐现有 `LocalDirMusicSource`。

**核心难点**：`just_audio` 不认 `smb://`。两条路线：

| 路线 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **A. 本地 HTTP 代理**（推荐） | 应用内起 `HttpServer`（`dart:io`，**无需新依赖**）监听 `127.0.0.1:<随机端口>`；收到请求后用 SMB 客户端按 `Range` 读取字节流并转发 | 支持流式播放与拖动进度；`just_audio` 完全无感 | 需正确实现 HTTP `Range`（206 Partial Content）；多一次内存拷贝 | ✅ 采用 |
| B. 先下载到临时文件再播 | 整曲下载到 cache 后 `setFilePath` | 实现最简单 | 大文件首播延迟高、占磁盘、拖动前需下完 | 仅作为 A 失败时的兜底 |

**代理安全要求**（易被忽视，必须做）：
- 只监听 `127.0.0.1`（**绝不** `0.0.0.0`，否则同局域网任何设备都能读你的 NAS 文件）；
- URL 路径带一次性随机 token，非法请求返回 404；
- 播放结束/切源后及时关闭 server，避免端口常驻。

**实现要点**：
- SMB 协议栈：需引入 Dart 侧 SMB2/3 客户端库（**pub.dev 生态较薄，选型时须实测**：SMB2/3 支持度、大文件随机读性能、Android/Windows 双平台可用性、维护活跃度）。若纯 Dart 方案不达标，退路是 Android 侧用原生库 + Platform Channel（成本翻倍，需谨慎评估）。
- 凭证：SMB 密码**复用 §4.4 的 `SecureVault`**（这正是把安全层做成通用模块而非塞进 netease 目录的原因）。
- 扫描：递归列目录 + 扩展名过滤，可直接复用 `LocalDirMusicSource` 的既有规则（扩展名白名单 `:20-22`、同名优先 `.mp3` `:54-58`、标题美化 `:95-106`）。
- `Track` 填充：`source: TrackSource.local`（语义上是用户自有文件），`sourceId: 'smb:<host>/<share>'`，`uri` 用 `resolveStreamUrl` 换成代理 URL，`extras` 存原始 SMB 路径。
- **缓存**：建议对已播放曲目做本地 LRU 文件缓存（可配上限，如 2GB），弱网 NAS 体验会天差地别。
- **平台配置**：Android 需 `networkSecurityConfig` 放行 `127.0.0.1` 明文 HTTP（§1.8）。
- UI：设置页新增"网络共享（SMB）"卡片，交互范式照抄现有"本地目录"（`server_settings_page.dart:108-118`），健康状态复用 `SourceHealth`。

### 5.2 DLNA 投送（C 类，第三顺位）

**定位澄清**：这是**输出端**，不是音源。建议入口放在播放页"输出到设备"，而非音源设置页。

**技术路径**：

```
① 发现：SSDP UDP 组播 M-SEARCH → 239.255.255.250:1900
        ST: urn:schemas-upnp-org:device:MediaRenderer:1
   收集响应中的 LOCATION → GET device description XML
   → 解析出 AVTransport / RenderingControl 的 controlURL
② 投送：SOAP POST 到 controlURL
        SetAVTransportURI(CurrentURI = 音频地址)
        Play / Pause / Stop / Seek
        RenderingControl: SetVolume / SetMute
③ 状态：轮询 GetTransportInfo / GetPositionInfo（多数设备不支持事件订阅，轮询更稳）
        建议 1~2s 一次
```

**内容源两种情况**：
- 投**本地文件**：必须在手机上起 HTTP 服务，且这次要监听**局域网 IP**（电视要能访问到），与 §5.1 的 127.0.0.1 代理是**不同实例、不同安全策略**。需限制只暴露当前投送的那一个文件 + 随机 token。
- 投**网络 URL**（如网易云已解析地址）：直接把 URL 交给设备。**风险**：带签名的 URL 可能因设备 UA/Referer 不同而被拒；且 URL 过期后设备端会中断。**建议一期只支持投送本地/SMB 文件**，云音源投送标为"实验性"。

**与星璃引擎的关系（必须在 UI 讲清楚）**：
进入投送态后，`AudioService` 应暂停本机播放并进入"遥控模式"；EQ / 场景音景 / 空间音效 / 音量均衡**全部失效**。建议在播放页显示明确的"投送中 · 音效由设备接管"状态条。

**平台**：Android/Windows 可行；iOS 需 `NSLocalNetworkUsageDescription` + Bonjour services 声明，且首次会弹本地网络权限；Web 不可用。

### 5.3 Spotify（B 类，建议只做 L1）

**L1 · 元数据 + 30 秒试听（推荐先做，可完全走星璃引擎）**

```
授权：OAuth 2.0 Authorization Code + PKCE
  ① 生成 code_verifier / code_challenge
  ② 系统浏览器（非 WebView，Spotify 要求且更安全）打开 authorize 页
  ③ 回调走自定义 scheme / App Links → 拿 code
  ④ code + code_verifier 换 access_token + refresh_token
```

- 合规：需展示 Spotify 品牌标识与"Powered by Spotify"，禁止缓存/下载音频。

**L2 · 完整播放（App Remote SDK）**——需设备装官方 App + Premium 订阅 + 新增 B 类抽象 `RemotePlaybackAdapter`（播放/暂停/切歌/进度全部代理给官方 App，星璃只做 UI 与曲库）。**建议暂不排期**，除非有明确用户诉求。

### 6.1 关于"统一 MusicTrack 模型"的建议

任务书提到"统一 MusicTrack 模型建议"。**明确建议：不要新建 `MusicTrack`，而是增强现有 `Track`。**

理由：
1. `Track` 已被全项目消费——`AudioService`、`PlaybackController`、`StelarithAudioHandler`、6 个 Source、曲库页、播放页、`nowPlayingProvider`、`favoriteProvider`、持久化层。新建平行模型会造成**双模型转换地狱**，且必然引入不一致 bug。

### 6.4 错误处理与降级（必须遵守的既有风格）

现有代码的降级哲学非常一致，新音源必须沿用：
- `AudioService._safe()`（`:129-136`）：引擎异常吞掉记日志，绝不上抛 → **保持**。
- `musicLibraryProvider`（`:96-103`）：单源异常 → 空列表，不影响其它源 → **保持**。
- `LocalMusicScanner`（`:34-46`）：主路径失败 → fallback 路径 → **云音源照做**（网易云失败 → 本地源；SMB 失败 → 提示但不阻塞）。
- `RadioSource`（`:14-19`）：多镜像轮询 → **云音源可用于多 API 端点容灾**。

**新增要求**：`_safe()` 会把失败变静默，云音源必须**在 Source 层就把失败原因写进 `SourceHealth`**（`sourceHealthProvider`），否则用户只会看到"转圈不动"，无从排查。

### 实施顺序建议（一句话版）

> **先把地基（Track.key / resolveStreamUrl 接线 / headers / SecureVault / 日志脱敏）夯实，再上网易云；网易云跑通后立刻做 SMB 对冲云音源被封的风险；DLNA 作为输出能力独立排期；Spotify 只做 L1 试听；Apple Music 与 QQ 音乐本轮不投入。**

**三个关键卡点（Go / No-Go）**：
1. **P0 完成后**：必须确认 5 类既有播放零回归，才能进 P1。
2. **P1-1/P1-2 完成后**（约投入 6 人天）：若网易云协议或 cookie 抓取被证明不可行，**及时止损转 P2**，沉没成本可控。
3. **P2-1 spike 后**（0.5~1 人天）：若 Dart 侧 SMB 库不达标，需重新决策"原生 Channel（成本翻倍）"还是"放弃 SMB"。
