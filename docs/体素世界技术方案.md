## 0. 现状核对（先纠正三个容易踩空的前提）

在动手前，必须承认代码里的四个**事实**，方案全部围绕它们展开：

| # | 事实（已核对源码） | 对方案的影响 |
|---|---|---|
| F1 | `VoxelCanvasView` / `VoxelCanvasController` 依赖的是 `lib/models/voxel.dart` 的 `VoxelBlockType` + `VoxelSoundScene`，**完全没用到 `VoxelWorld`**。三处共用（`voxel_canvas_page` / `voxel_sound_editor_page` / `voxel_minigame_page`）走的是另一条数据链。 | 3D 世界与 2.5D 画布是**两套互不相干的数据模型**。替换 `voxel_canvas_page` 只是移除 `VoxelCanvasView` 的第 3 个调用点，编辑器与小游戏零影响。兼容风险远低于预期。 |
| F2 | `VoxelWorld` 构造函数吃 `int seed`，但**没有把 seed 存成字段**（`_generate(seed)` 后即丢弃）。 | 拍照要能"复现同一个世界"，必须先给 `VoxelWorld` 补一个 `final int seed;`（唯一需要改动既有文件的地方，纯增字段、不改行为）。 |
| F3 | `kVoxelSpecs[Voxel.water]!.solid == true`（只有 `air` 是 `solid: false`）。所以 `VoxelWorld.isSolid()` 认为水是实心的，`surfaceHeight()` 会把水面算成地表。 | 面剔除、碰撞、贴地三处都**不能直接用 `isSolid`**，需要在渲染/物理层自己判定 `occludes`（实心且不透明）与 `walkable`。不要去改 `VoxelSpec.solid` 的语义（会连带影响 `surfaceHeight` 的既有含义）。 |
| F4 | `Scenes.decodePack` 是**严格相等**判断：`if (schema != packSchemaVersion) throw FormatException`。`ScenePacker.decode` 则完全不校验 schema。 | schema 升到 2 后，v1 老包会被 `decodePack` 直接拒收。必须把判断改成"区间兼容"（见 §5.3）。 |

另外两条环境事实：

- **音频素材**：`D:/Stellara/Music/audio_material/` 有 10 个 m4a（共 ~566MB，最大 145MB），**未打进 assets**（`pubspec.yaml` 的 `assets:` 只有 `assets/icons/`、`assets/figma/`）。现有 `SoundBlockMixer._sfxBaseDir()` 的做法是**运行时探测外部目录**（Windows 硬编码 `d:\Stellara\Music\minecraft_music`，Android 探 `/storage/emulated/0/Music|Download`）。世界音效沿用同一策略，不改打包体积。

## 2. 渲染器设计

### 2.1 为什么不用 GPU 三角形管线 / 第三方 3D 库

工程既有裁决 Q3：**零第三方 3D 依赖，纯 `CustomPaint`**。继续遵守，理由成立：

- 世界规模极小：24×24×20 = 11520 格，实心格约 4000~5000，剔除后暴露面**约 1200~2500 个四边形**。这个量级 CPU 投影完全吃得住。
- `Canvas.drawVertices` 走的是 Skia/Impeller 的 GPU 批绘制，一次调用可提交上千三角形，不是逐 path 的软件光栅。真正的软件开销只在**投影 + 排序**（纯 Dart 数学）。
- 不引 `vector_math`：自写 `Vec3` + `ViewBasis` 只有 ~80 行，能内联优化，避免为 6 个方法拉一个包。

### 2.2 坐标系与投影

**约定**：右手系，X 向东、Y 向上、Z 向南；方块 `(x,y,z)` 占据 `[x,x+1]×[y,y+1]×[z,z+1]`。

视图变换用**基向量点乘**而非 4×4 矩阵乘（省一半乘法，且只需 3×4）：

```
forward = (sin(yaw)·cos(pitch),  sin(pitch),  cos(yaw)·cos(pitch))
right   = (cos(yaw),             0,          -sin(yaw))
up      = right × forward

d     = world - eye
viewX = d·right
viewY = d·up
viewZ = d·forward        // > 0 表示在相机前方
```

透视投影（viewport = W×H）：

```
f      = 1 / tan(fovY / 2)
aspect = W / H
screenX = W/2 + (viewX · f / aspect) / viewZ · (W/2)
screenY = H/2 - (viewY · f)          / viewZ · (H/2)
depth   = viewZ
```

**近平面裁剪**：面的 4 个顶点里只要有任一 `viewZ < near`，整面丢弃（不做多边形裁剪）。代价是相机贴脸时面会突然消失——用 §3.4 的碰撞把相机挡在方块外 0.3 格以上即可掩盖，比实现 Sutherland–Hodgman 划算得多。

### 2.3 面剔除（三级）

按开销从低到高依次过滤，早退优先。

**① 相邻遮挡剔除（收益最大）**

面朝向的邻格若"遮挡"，则该面永不可见：

```dart
bool occludes(Voxel v) => kVoxelSpecs[v]!.solid && !kVoxelSpecs[v]!.transparent;
```

注意：**不能用 `VoxelWorld.isSolid()`**（F3：水的 `solid == true`），否则水体下方与侧面的地形面会被错误剔除，水里会露出空洞。规则细化：

| 当前块 | 邻块 | 是否绘制该面 |
|---|---|---|
| 不透明 | 不透明 | 否 |
| 不透明 | 空气 / 水 / 叶 | 是 |
| 水 | 水 | 否（同型内部面剔除，水体只留外壳） |
| 水 | 空气 | 是 |
| 水 | 不透明 | 否（被地形挡住，看不见） |
| 叶 | 叶 | **是**（叶片同型不剔除，保留树冠体积感——这是与水的关键差异） |

叶不做同型剔除会让树冠面数上升，但一棵树叶团只有 ~40 格，24×24 世界树不超过 20 棵，总量可控。若超预算，用 §2.7 的 LOD 把远处树冠退化为只画外壳。

**② 背面剔除**

面法线与视线同向即背面：`faceNormal · (faceCenter - eye) >= 0` → 丢弃。轴对齐面的法线是 6 个常量，判断只需一次减法一次比较。可再砍掉约 45% 的面。

**③ 视锥 + 距离剔除**

先做**列级**（column-level）粗剔除：对每个 `(x,z)` 列算一次到相机的水平距离与方位角，超出 `renderDistance` 或明显在 fov 外（留 15° 余量）的整列跳过，不进入逐方块循环。这一步把 576 列砍到通常 150~250 列，是循环开销的主控项。

### 2.4 深度排序

**不用 Z-buffer**（`CustomPaint` 没有），用**画家算法 + 面中心深度降序**：

```dart
faces.sort((a, b) => b.depth.compareTo(a.depth));  // 远 → 近
```

轴对齐立方体的画家算法在"凸物体不相交"时是正确的，体素世界天然满足（方块不重叠）。已知瑕疵与对策：

| 瑕疵 | 场景 | 对策 |
|---|---|---|
| 同深度面 z-fighting | 共面的相邻方块顶面 | 稳定排序，同深度按 `x+y+z` 次序做 tie-break |
| 大面穿插小面 | 体素世界不会出现 | 无需处理 |
| 半透明穿透 | 水 / 叶叠在一起 | 见 §2.6：两趟绘制，不透明先画完再画半透明 |

排序成本：2500 个面 `sort` 约 0.15ms，可接受。**进一步优化**：按 `depth` 分 128 个桶做**桶排序**（步长 `renderDistance/128`），桶内不排序，O(n) 且视觉无差异，省约 60% 排序时间。建议 Phase 1 先用 `sort`，不达标再换桶排。

### 2.5 分面着色

复用既有 `shade(Color base, double brightness, {double alpha})`（`voxel_world_types.dart` 已提供），不造轮子。亮度表：

| 面 | 亮度 | 说明 |
|---|---|---|
| `top` | 1.00 | 直接受光 |
| `south` (+Z) | 0.86 | 主侧光 |
| `east` (+X) | 0.78 | |
| `north` (−Z) | 0.70 | |
| `west` (−X) | 0.62 | 背光侧 |
| `bottom` | 0.48 | 环境光 |

取色优先级：`spec.top != null && face == top ? spec.top! : spec.base`（草 / 雪的顶面色 `kVoxelSpecs` 已定义好）。

**日夜微调**：把 `timePhase` 映射为全局光照系数 `dayLight ∈ [0.55, 1.0]`（正午 1.0 / 黄昏 0.7 / 夜 0.55）与暖色偏移（黄昏叠 `Color(0xFFFFB07A)` 8%），乘到 brightness 上。几乎零成本，但对"画面表现"提升极大。

**AO 近似（强烈建议做，Phase 1.5）**：对每个面的 4 个角检查相邻 3 格是否 occludes，命中数 0~3 → 顶点亮度再乘 `[1.0, 0.88, 0.76, 0.66]`，通过 `drawVertices` 的 per-vertex color 传入，GPU 免费插值。这是"像不像我的世界"的关键观感。成本：每面 12 次数组访问，2500 面约 0.2ms。

### 2.6 天空、雾、半透明

**天空**（`voxel_sky.dart`）：不画方块，在 `paint()` 最开始铺一层竖直 `LinearGradient` 矩形，颜色由 `timePhase` 插值。

```dart
class SkyPalette {
  final Color zenith, horizon, fog, sun;
  static SkyPalette at(double timePhase); // 黎明/白天/黄昏/夜 四关键帧 lerp
}
```

- 太阳 / 月亮：一个 `drawCircle` + 径向光晕，位置由 `timePhase` 决定的方位角投影到屏幕；在视锥外就不画。
- 星星（夜间）：叠 60 个确定性随机点（复用 `VoxelWorld` 同款 hash，保证不闪烁），alpha 随夜深渐入。
- 云：**不做**。体素云要么面数翻倍要么很假，收益低。

**雾**：让远处面的颜色向 `SkyPalette.fog` 线性混合，这是让 24×24 小世界"有纵深"的最廉价手段。

```
fogT  = clamp((depth - fogStart) / (fogEnd - fogStart), 0, 1)   // fogStart = 0.55 × far
color = Color.lerp(shadedColor, palette.fog, fogT * 0.85)
```

在 CPU 端算完直接写进 `RenderFace.color`，GPU 端零开销。`powerSave` 下 `fogEnabled = false`。

**半透明两趟绘制**：

```
Pass A：不透明面（grass / dirt / stone / sand / wood / snow）—— 深度降序
Pass B：半透明面（water alpha 0.62 / leaves alpha 0.80）—— 深度降序
```

两趟之间不混排，避免"水面盖住了它前面的树"这类错误；同一趟内部仍按深度降序。

**水面动画**：**不做世界空间顶点位移**（会破坏面剔除前提且成本高）。改用三个廉价手段叠加：

1. 只对**水的顶面**（数量少，通常 < 300 个）做 Y 偏移
   `y = 0.9 + 0.06·sin(2π·timePhase·1.5 + 0.7x + 0.5z)`，四顶点各算一次 sin，形成波纹起伏。
2. 顶面颜色按同一相位在 `base` 与 `lighten(base, 0.12)` 间插值 → 粼光。
3. 每 12 个水面确定性地挑 1 个画一条 2px 高光短线（确定性挑选，不闪烁）。

**叶片动画**：对叶面做**屏幕空间** ±0.8px 水平位移 `sin(2π·timePhase·0.8 + 0.3x + 0.4z)`。屏幕空间位移不影响剔除与排序，成本是每面 2 次加法。

### 2.7 性能预算

**面数基线**（24×24×20，seed 20260810，相机位于世界中心高 12、俯视 −25°）：

| 阶段 | 面数 |
|---|---|
| 全部方块 × 6 | ~28000 |
| ① 相邻遮挡剔除后 | ~4200 |
| ② 背面剔除后 | ~2300 |
| ③ 视锥 / 距离剔除后 | **~1400** |

**每帧预算（60fps → 16.6ms）**：

| 环节 | 目标 | 说明 |
|---|---|---|
| 列级粗剔除 | 0.3ms | 576 次距离 / 角度判断 |
| 逐方块面收集 + 剔除 | 2.5ms | ~250 列 × 平均 8 实心格 |
| 投影（4 顶点 × 1400 面） | 1.8ms | 5600 次点乘 |
| AO + 着色 + 雾 | 1.0ms | |
| 排序 | 0.2ms | 桶排 |
| `drawVertices` 提交 | 1.5ms | 2~4 次批调用 |
| **合计** | **~7.3ms** | 留一倍余量给 UI 与 GC |

**批绘制策略（决定性优化）**：把同一趟的所有面拍成**一个** `Vertices` 对象（`VertexMode.triangles`，每面 2 三角 6 顶点，per-vertex color），一次 `canvas.drawVertices(v, BlendMode.srcOver, Paint())` 提交。draw call 从 1400 次降到 2 次。

> 限制：Web CanvasKit 支持 `drawVertices` 的 per-vertex color，**HTML renderer 不支持**。Web 端需检测并降级为 `drawPath` 循环 + `renderDistance` 降到 16（见 §7）。

**LOD（`lodBias > 1` 时启用）**：距离 > `0.6 × far` 的区域按 2×2 合并列——取 4 列最高地表画一个加宽面。轮廓保留，面数再降约 35%。仅 `powerSave` 与 Web 启用。

**三档降级表**：

| 项 | powerSave | balanced | smooth |
|---|---|---|---|
| 目标帧率 | 30fps（`Ticker` 隔帧跳过） | 60 | 60 |
| `renderDistance` | 18 | 28 | 40 |
| 面数上限 | 1200 | 3000 | 5000 |
| 雾 | 关 | 开 | 开 |
| AO | 关 | 开 | 开 |
| 水面波纹 | 关（纯色水） | 开 | 开 |
| 叶片摆动 | 关 | 关 | 开 |
| 星星 / 太阳光晕 | 关（纯渐变天空） | 太阳开 | 全开 |
| LOD 合批 | 开 | 关 | 关 |
| 自动巡航 | 关 | 关 | 可开 |

超预算兜底：面数超上限时按 `depth` 从远到近丢弃溢出面（远处丢失被雾掩盖，视觉损失最小）。

| 手势 | orbit | walk |
|---|---|---|
| 单指拖拽 | `yaw += dx·0.006`，`pitch -= dy·0.005`（pitch 夹 [−1.45, −0.02]） | 同左，pitch 放宽到 [−1.45, 1.45] |

### 3.3 摇杆（walk 模式）

左下角 96dp **虚拟摇杆**（不用 4 个 D-pad 按钮——摇杆手感明显更好且占地更小）：

- 拇指偏移向量 → 相机**局部** XZ 位移方向，模长映射速度 `0 ~ 4.5 格/秒`。
- 右下角「↑」按钮：短按跳跃（初速 5.2，重力 −18），长按上浮（观景用，脱离重力）。
- 摇杆与按钮均满足 `AppSize.touchMin` 热区，外观沿用 `AppColors.accent` 半透明圆（与现有 `_BackButton` 同语言）。

### 3.4 贴地行走与碰撞

**贴地**：

```dart
double groundHeightAt(double x, double z) {
  // 注意：不能用 world.surfaceHeight()（F3：它会把水面当地表）
  final int xi = x.floor(), zi = z.floor();
  for (int y = world.maxY - 1; y >= 0; y--) {
    if (occludes(world.get(xi, y, zi))) return y + 1.0;
  }
  return 0.0;
}
```

对四个角的 `groundHeightAt` 做双线性插值，让相机在斜坡上平滑升降而非台阶式跳变。眼高 = 插值地面 + 1.7。

**碰撞**：相机视为半径 0.32、高 1.8 的 AABB，**逐轴分离求解**（先 X 后 Z 后 Y）：某轴目标格 `occludes` 则该轴位移归零、其余轴保留 —— 贴墙滑行手感自然，不会卡死。

**水面可过**：水的 `occludes == false`，碰撞天然允许穿过。额外两件事：

1. 相机所在格是 `Voxel.water` 时，眼高改为 `waterLevel + 0.4`（半潜），移动速度 ×0.55。
2. 屏幕叠一层 `Color(0x333A78C2)` 水下滤镜，雾距缩到 8（水下能见度低）。零成本、强表现力。

**边界**：XZ 夹在 `[1.5, sizeX-1.5]`；Y 夹在 `[1.0, maxY+8]`（允许飞到世界上方俯瞰全景，取景常用）。

## 4. 世界内空间音效

### 4.1 复用既有设施，不重写

现有 `lib/services/audio/spatial/` 已经把最难的部分做完了：

- `SpatialSound` / `SpatialTrack`（≤4 轨）+ `SpatialChannel`（center/front/back/left/right）
- `SpatialPlayer.start({int walls})` / `setWalls(int)` —— 材料隔音动态生效
- `transmissionLoss(SoundMaterial, walls)` + `dbToGain(db)` —— dB → 音量倍率
- `SpatialSynth.synthesizeWav(synthId, seed)` —— `water` / `fireplace` / `furnace` / `rain` / `wind` / `cave` 六种 PCM，带 1.5s 淡入淡出的无缝循环包络，写盘缓存
- `SpatialMixer.play/stopById/updateWalls/stopAll`

`WorldAudioEngine` 的职责因此非常收敛：**把"相机 + 世界"翻译成"一组 SpatialSound + walls"，然后调 mixer**。它不碰播放器、不碰声道混音。

### 4.2 声源扫描（世界不变则只做一次）

`scan(VoxelWorld)` 遍历一次世界，把声源方块**聚类**（避免 300 个水方块变成 300 个播放器）：

```
1. 收集候选格：water（且上方是 air，即水面）、leaves、以及未来的 campfire
2. 对每类做 6-邻域 flood fill 聚类（可直接借 spatial_models.dart 已有的
   waterFlow(originX, originY, isBlocked, maxDistance) —— 它就是 BFS，
   把 isBlocked 定义为"不是水/超出该类"即可，maxDistance 用 9 保持与既有语义一致）
3. 每簇产出 1 个 WorldSoundSource：
     center     = 簇内格的质心
     blockCount = 簇大小
     radius     = clamp(4 + sqrt(blockCount) * 1.6, 6, 22)
4. 全局环境源（风）：固定挂在相机头顶，永远 center 声道，音量随相机高度上升
```

结果按 `blockCount` 降序缓存在引擎里。世界 seed 不变就不重扫。24×24 世界扫描一次约 1~3ms，可在页面 `initState` 同步做。

### 4.3 每帧（实为每 250ms）更新

音频参数**不要跟着渲染帧走**（60Hz 改音量会让 `audioplayers` 抖动且徒增开销）。用一个 250ms 的 `Timer.periodic`：

```dart
Future<void> update(VoxelCamera cam) async {
  final list = _sources
      .map((s) => (s, (s.center - cam.position).length))
      .where((e) => e.$2 < e.$1.radius)
      .toList()
    ..sort((a, b) => a.$2.compareTo(b.$2));

  final top = list.take(maxConcurrent);   // 默认 3，powerSave 降到 1

  for (final (src, dist) in top) {
    final channel = channelOf(cam, src.center);
    final volume  = volumeOf(src, dist);
    final walls   = wallsBetween(world, cam.position, src.center);

    if (已在播 && 声道未变) {
      await _mixer.updateWalls(src.id, walls);       // 只更新衰减，不重启
    } else {
      await _mixer.play(_buildSound(src, channel, volume), walls: walls);
    }
  }
  // 淘汰不在 top 里的：await _mixer.stopById(id)
}
```

**方向 → 声道**（用相机基向量判象限，注意 `SpatialChannel` 只有 5 个离散值）：

```dart
static SpatialChannel channelOf(VoxelCamera cam, Vec3 target) {
  final d = (target - cam.position).normalized;
  final f = d.dot(cam.forward);
  final r = d.dot(cam.right);
  if (f.abs() >= r.abs()) {
    return f >= 0 ? SpatialChannel.front : SpatialChannel.back;
  }
  return r >= 0 ? SpatialChannel.right : SpatialChannel.left;
}
```

**声道迟滞**：象限边界会来回抖（左↔前反复切会导致重启播放器）。加 0.12 的迟滞阈值——只有新象限的优势超过旧象限 0.12 才切换。这条不做的话，用户转身时会听到爆音，是**必须**的细节。

**距离 → 音量**：`volume = baseVolume / (1 + dist / (radius * 0.5))`，`baseVolume = clamp(0.18 + blockCount * 0.012, 0.18, 0.85)`。

**遮挡 → walls**：从相机到声源做 3D DDA 体素射线步进，统计路径上 `occludes` 的格数，`walls = min(count, 6)`，直接喂给 `SpatialPlayer.setWalls()`，由既有 `transmissionLoss` 换算衰减。射线步进 24 格量级，250ms 一次，开销可忽略。

**结果**：站在山另一侧听水声会被石头闷掉（`stone` 的 Rw=50dB），绕过山头就清亮起来 —— 这正是既有材料系统的设计意图，终于有了使用场景。

### 4.4 方块 → 声源映射表

`world_sound_sources.dart` 里定义（合成兜底 + 外部素材优先）：

| 世界元素 | `synthId` | `SoundMaterial` | 优先外部素材（`audio_material/`） | 说明 |
|---|---|---|---|---|
| `water`（水面簇） | `water` | `glass`（水导声极好，α=0.025） | `［长］海滩.m4a`（6.8MB，最小最适合） | 簇越大音量越高 |
| `leaves`（树冠簇） | `wind` | `wool`（吸音 0.8，树叶天然吸音） | `［长］树叶窸窸窣窣.m4a` | 风吹叶声 |
| 高处 / 空旷（相机 y > 14） | `wind` | `stone` | `［长］竹林窸窣、风声.m4a` | 全局源，center 声道 |
| `grass` 大片（未来） | — | `dirt` | `［短多采样］鸟叫合集.m4a` | 白天随机触发鸟叫（见下） |
| 篝火（Phase 3+ 可放置） | `fireplace` | `wood` | `［长］篝火燃烧.m4a` | 已有合成器，直接可用 |
| 洞穴 / 地下（相机 y < 4 且头顶被遮） | `cave` | `stone` | — | 已有合成器 |
| 雨（时相 / 天气，Phase 3+） | `rain` | `wool` | `［长］432Hz雨声.m4a` | 已有合成器 |

**鸟叫的特殊处理**：`［短多采样］鸟叫合集.m4a` 是短采样合集，不适合循环播放。做法是**随机点触**——白天（`timePhase ∈ [0.25, 0.7]`）且相机附近 12 格内有 ≥8 个 `leaves` 时，每 8~20 秒随机一次，用 `AudioService.playSfx` 单发（不占 `SpatialMixer` 的并发名额），音量 0.12~0.22。这比循环鸟叫自然得多。

**素材接入策略（关键，别踩打包体积的坑）**：

- `audio_material/` 共 566MB，**绝不能进 assets**（现在 debug APK 已 157MB）。
- 沿用 `SoundBlockMixer._sfxBaseDir()` 的**运行时外部目录探测**模式，新增 `WorldAudioAssets._materialDir()`：
  - Windows/Linux/macOS：探 `d:\Stellara\Music\audio_material`
  - Android：探 `/storage/emulated/0/Music/audio_material`、`/storage/emulated/0/Download/audio_material`
  - Web / 找不到目录：**全部回落到 `SpatialSynth` 合成**（合成器已覆盖 6 种，功能完整不降级）
- 探测命中时把路径填进 `SpatialTrack.audioPath`——`SpatialPlayer._ensureTrackFile()` 已经写好了"有 audioPath 且文件存在就优先用"的逻辑，**零改动接入**。
- 长期方案（记入 `TODO_分派方案.md` 已有条目）：把 10 个 m4a 裁剪成 20~30s 无缝循环片段、转 64kbps ogg，总量可压到 ~8MB，届时可考虑进 assets。本方案不依赖该前置。

### 4.5 与既有音频通道的关系

| 通道 | 归属 | 与世界音效的关系 |
|---|---|---|
| 音乐（`just_audio` / `AudioService`） | 全局播放器 | **完全不干扰**。`SpatialPlayer` 已设 `AudioContextConfigFocus.mixWithOthers`，不抢焦点 |
| 场景音景（`switchSoundscape`） | 场景页 | **互斥**：进入世界页时暂停场景音景，退出时恢复。否则两层环境音会糊在一起 |
| SFX（`playSfx`） | 一次性 | 共存（鸟叫走这条） |
| 世界空间音效（新） | 世界页生命周期 | 页面 `dispose` 必须 `stopAll()`；`AppLifecycleState.paused` 也要停（省电，且避免后台被系统杀播放器） |

`worldAudioEnabledProvider` 默认跟随既有白噪音总开关（R4），HUD 上的 🔊 只是它的快捷开关。

### 4.6 并发上限

`SpatialMixer` 每个 `SpatialSound` 会为每条 track 起一个 `AudioPlayer`。若一个 sound 用 2 轨、同时 3 个 sound，就是 6 个播放器实例——低端机（手表 412×502）扛不住。约束：

| 档位 | `maxConcurrent` | 每源轨数 |
|---|---|---|
| powerSave | 1 | 1 |
| balanced | 2 | 1 |
| smooth | 3 | 2（近处水源可用 2 轨做宽度） |

即最多 6 个播放器实例，和现有 `SoundBlockMixer` 试听时的量级相当。

## 5. 拍照 / 取景（核心新需求）

### 5.1 设计立意：存"机位"而不是存"图片"

这是整个方案最重要的一个决策。

用户要的是"**在体素世界里拍照，作为播放器场景背景，且背景里的水流树叶天空要实时动**"。如果拍照产出的是一张 PNG，第二个需求就死了。所以：

> **`VoxelSceneCapture` 不存像素，只存"能复现这一画面的参数"**：世界 seed + 世界尺寸 + 相机位姿 + fov + 画幅 + 时间相位。
> 播放器背景拿到它，重新构造 `VoxelWorld` 与 `VoxelCamera`，用同一个 `VoxelRenderer` 低帧率重绘 —— 于是水在流、叶在摆、天在变，而"照片"本身只有 ~200 字节 JSON。

PNG 快照仍然要生成，但它的角色是**降级兜底**（powerSave / Web / 渲染失败），不是主路径。

### 5.2 取景交互流程

```
世界页（orbit 或 walk）
  │  点「📷取景」或长按画面
  ▼
【取景模式】mode = frozen
  ├─ 相机冻结：世界手势全部失效（防止误触毁掉构图）
  ├─ 画面外围压暗（取景框外 Color(0xCC000000) 遮罩），只留取景区亮着
  ├─ 取景框内叠三分线（半透明白，构图辅助），可开关
  ├─ 底部工具条：
  │     [画幅 4:3 | 16:9 | 全屏]   ← 切换即改遮罩比例，画面不重渲
  │     [🕐时相滑条]               ← 实时改天色，这一步是"调色"
  │     [微调：↑↓ 抬降机位 · ⟲⟳ 微转 yaw]  ← 冻结下唯一允许的相机动作，步长很小
  │     [🔀换个世界]               ← 换 seed 重新生成地形（不满意就换）
  │     [✕ 取消]        [⦿ 快门]
  ▼
按快门
  ├─ 生成 VoxelSceneCapture（纯参数）
  ├─ 同步渲染一张 PNG 兜底快照 → 落盘 <docs>/voxel_captures/<sceneId>_<ts>.png
  ├─ 触觉反馈 + 快门白闪 120ms（motionScale 缩放）
  ▼
【确认页】（底部 sheet，不离开世界页）
  ├─ 缩略图预览（就是刚才那张 PNG）
  ├─ "用作哪个场景的背景？" → 场景选择器（默认当前 activeScene）
  ├─ [背景实时动] 开关 → capture.animate
  ├─ [重拍]  [保存并应用]
  ▼
保存 → scene.copyWith(voxelCapture: capture) → 走既有场景持久化
       → 弹 SnackBar「已设为『雪原』的背景」+ [去看看] 跳场景页
```

**关键交互原则**：

1. **冻结优先**：取景模式下绝不允许自由旋转。用户好不容易构好的图，一次误触全毁 —— 这是"可用好用"的分水岭。微调只给极小步长（yaw ±0.02 rad / y ±0.25 格）。
2. **画幅只改遮罩不改渲染**：切 4:3 / 16:9 只是改遮罩矩形，相机 fov 与投影不变。这样切换零延迟，且用户看到的就是"从同一个画面里裁一块"。真正的画幅信息存进 `capture.aspect`，背景渲染时按它决定 `BoxFit`。
3. **换世界要保机位**：点「🔀换个世界」只换 seed 重新生成地形，`yaw/pitch/fov/timePhase` 全保留 —— 用户在同一视角下连续刷地形，直到刷到满意的，效率极高。相机 y 需要按新地形重新贴地。

### 5.3 数据模型与 Scene 集成

#### `VoxelSceneCapture` JSON

```json
{
  "v": 1,
  "seed": 20260810,
  "sx": 24, "sz": 24, "my": 20, "wl": 5,
  "cx": 12.4, "cy": 14.2, "cz": 3.8,
  "yaw": 0.72, "pitch": -0.31, "fov": 1.0472,
  "aspect": "r16x9",
  "phase": 0.68,
  "animate": true,
  "snap": "/data/.../voxel_captures/snow_1754800000.png"
}
```

约 200 字节。字段名刻意缩短，因为它会被塞进每个 Scene 的 JSON 里、随场景包分享。

**`buildWorld()` 的正确性依赖 F2**：`VoxelWorld` 目前没存 seed，必须先加：

```dart
// voxel_world.dart 的唯一改动
class VoxelWorld {
  VoxelWorld({
    this.sizeX = 24, this.sizeZ = 24, this.maxY = 20,
    this.seed = 20260810,          // ← 改成字段
    this.waterLevel = 5,
  }) : _blocks = ... { _generate(seed); }

  final int seed;                   // ← 新增
  ...
}
```

生成算法本身已经是**完全确定性**的（`_hash` 是整数位运算，`_Rng` 是 LCG，无 `DateTime`、无 `Random()` 无种子构造），所以同 seed + 同尺寸 → 逐格相同的世界。这一点是整个"存参数不存图"方案成立的**技术前提**，已验证成立。

> 单测必做：`VoxelWorld(seed: 42)` 连造两次，逐格比对 11520 个 `get()` 全等。

#### 并入 `Scene`

沿用工程里已经验证过的**可空字段向后兼容**模式（`bgmUri` / `visible` 就是这么加的）：

```dart
class Scene {
  ...
  /// v3：体素世界取景（非空时场景背景改用 3D 实时渲染）。
  /// 向后兼容：旧 JSON 缺失该字段即 null，走原渐变背景。
  final VoxelSceneCapture? voxelCapture;

  Map<String, dynamic> toJson() => {
    ...,
    'voxelCapture': voxelCapture?.toJson(),   // null 就写 null，与既有风格一致
  };

  factory Scene.fromJson(Map<String, dynamic> json) => Scene(
    ...,
    voxelCapture: VoxelSceneCapture.tryFromJson(
      json['voxelCapture'] as Map<String, dynamic>?,
    ),   // 容错：字段缺失 / 类型不对 / 版本不认识 → null，绝不抛异常
  );

  Scene copyWith({..., VoxelSceneCapture? voxelCapture,
                  bool clearVoxelCapture = false}) => Scene(
    ...,
    voxelCapture: clearVoxelCapture ? null : (voxelCapture ?? this.voxelCapture),
  );
}
```

`tryFromJson` 而不是 `fromJson`：场景包可能来自更高版本的 App（分享场景），遇到不认识的 `"v": 2` 直接返回 null 退化成渐变背景，**不能让整个场景解析失败**。

#### schema v1 → v2 兼容策略

现状（F4）：

```dart
// scene_api.dart —— 严格相等，v1 包在 v2 App 上会被拒收
if (schema != packSchemaVersion) throw FormatException(...);
```

改为**区间兼容 + 上限拒收**：

```dart
class Scenes {
  static const int packSchemaVersion = 2;      // 1 → 2
  static const int minSupportedSchema = 1;     // 新增

  static Scene decodePack(String pack) {
    final root = jsonDecode(pack) as Map<String, dynamic>;
    final schema = root['schema'] as int? ?? 0;
    if (schema < minSupportedSchema || schema > packSchemaVersion) {
      throw FormatException(
        '场景包 schema=$schema 不受支持（当前支持 $minSupportedSchema~$packSchemaVersion）',
      );
    }
    // v1 包没有 voxelCapture 字段 → Scene.fromJson 里 tryFromJson 返回 null，自动兼容
    return Scene.fromJson(root['scene'] as Map<String, dynamic>);
  }
}
```

兼容矩阵：

| 包 schema | 旧 App（v1） | 新 App（v2） |
|---|---|---|
| 1（旧包） | ✅ 正常 | ✅ 正常，`voxelCapture = null` → 渐变背景 |
| 2（新包，无 capture） | ❌ 抛 FormatException | ✅ 正常 |
| 2（新包，有 capture） | ❌ 抛 FormatException | ✅ 正常，3D 背景 |

"旧 App 读不了新包"是可接受的（用户升级即可），但**必须保证错误信息可读**，别让用户看到裸异常。`ScenePacker.decode` 目前**完全不校验 schema**，也补上同样的检查（否则同一份数据两条解析路径行为不一致，是个隐藏 bug）。

### 5.4 实时背景渲染（`VoxelSceneBackdrop`）

#### 渲染树位置

```
ScenePage
└─ PageScaffold
   └─ Stack
      ├─ Positioned.fill → RepaintBoundary
      │                    └─ VoxelSceneBackdrop(capture)   ← 新增，最底层
      ├─ Positioned.fill → 半透明可读性遮罩（见下）
      └─ Column[ SceneCardStack, UnifiedPlayer ]            ← 原有内容不动
```

`VoxelSceneBackdrop` 只在 `scene.voxelCapture != null` 时插入；为 null 时整棵子树不存在，**旧场景零开销**。

#### 低帧率驱动

不用 `AnimationController`（它跟 vsync 走 60Hz），用一个显式的低频 `Timer.periodic`：

```dart
class _VoxelSceneBackdropState extends ConsumerState<VoxelSceneBackdrop> {
  late final VoxelWorld _world   = widget.capture.buildWorld();   // 构造一次
  late final VoxelCamera _camera = widget.capture.buildCamera();  // 永不改变
  List<RenderFace>? _staticFaces;    // 不透明面：只算一次，永久复用
  List<RenderFace> _animFaces = [];  // 水/叶面：每 tick 重算
  double _phase = 0;
  Timer? _timer;

  void _start(int fps) {
    _timer?.cancel();
    if (fps <= 0) return;                     // powerSave → 静态快照，不起 timer
    _timer = Timer.periodic(Duration(milliseconds: 1000 ~/ fps), (_) {
      if (!mounted) return;
      _phase = (_phase + 1 / (fps * 40)) % 1; // 40s 一个完整循环
      setState(() => _animFaces = VoxelRenderer.refreshAnimated(
        lastFrame: _staticFaces!, world: _world, camera: _camera,
        viewport: _size, config: _config, timePhase: _phase,
      ));
    });
  }
}
```

**这里的核心优化：相机是固定的，所以几何、剔除、排序全部只需算一次。**

| 数据 | 频率 | 成本 |
|---|---|---|
| 世界构造 | 1 次 / 首次挂载 | ~5ms（`_generate` 的 fbm 循环） |
| 不透明面收集 + 投影 + 排序 | 1 次 | ~5ms |
| 水 / 叶面重算 | 每 tick | **~0.4ms**（通常 < 400 个面，只重算 sin 与颜色） |
| 天空渐变 | 每 tick | ~0.05ms（一个 `drawRect`） |
| `drawVertices` 提交 | 每 tick | ~1.2ms |

即稳定态每帧 **< 2ms**，18fps 下 CPU 占用约 3.6%。这个数字是方案可行性的关键 —— 它让"播放器背景实时动"从"听起来很贵"变成"比现有粒子系统还便宜"。

**帧率**（由 `voxelBackdropFpsProvider` 给出）：

| 档位 | fps | 行为 |
|---|---|---|
| powerSave | 0 | 不起 timer，直接 `Image.file(capture.snapshotPath)` 静态图 |
| balanced | 18 | 水波与天色可见地动，功耗可忽略 |
| smooth | 24 | 更顺滑，叶片摆动也开 |

用户在 `capture.animate = false` 时，无论档位都走静态快照。

#### RepaintBoundary 策略（三层隔离）

这是"背景动但不拖累整页"的关键，必须做对：

1. **背景自身包 `RepaintBoundary`** —— 背景重绘不会向上冒泡触发 `SceneCardStack` / `UnifiedPlayer` 重绘。
2. **`SceneCardStack` 也包一层 `RepaintBoundary`** —— 卡片有 `LiquidGlass`（`BackdropFilter`），它是全树最贵的节点，绝不能被背景的 18fps 带着跑。**这一条如果漏了，整个方案的性能就崩了。**
3. **`setState` 范围收到最小** —— `_animFaces` 变更只影响 `CustomPaint`，用 `ValueNotifier<List<RenderFace>> + RepaintBoundary + CustomPaint(repaint: notifier)` 甚至可以完全绕开 `setState`（`CustomPainter` 的 `repaint` 参数直接触发 paint 而不 rebuild widget 树）。**推荐这个写法**，比 `setState` 省一整轮 build/layout。

```dart
CustomPaint(
  painter: VoxelWorldPainter(
    faces: _facesNotifier,       // ValueListenable<List<RenderFace>>
    repaint: _facesNotifier,     // ← 只触发 paint，不 rebuild
    sky: _skyNotifier,
  ),
)
```

#### 与 `LiquidGlassCapture` 的关系：**必须互斥，且已有天然隔离**

读过 `liquid_glass_capture_provider.dart` 后可以确认这是本方案**最大的一个坑**：

```dart
// 现状：它在 initState 的 postFrameCallback 里 toImage() 抓一次背景，
// 注释明确写着「背景是静态的（渐变+噪点），捕获一次即可」
WidgetsBinding.instance.addPostFrameCallback((_) => _capture());
```

冲突分析：

| 问题 | 说明 | 结论 |
|---|---|---|
| 快照会过期 | 3D 背景每 55ms 变一次，`LiquidGlassCapture` 的快照停在第一帧 | 玻璃折射采样到的是"世界的第一帧"，与实际背景对不上 |
| 不能提高捕获频率 | `toImage()` 是**同步 GPU→CPU 回读**，全屏一次 5~15ms，18fps 下光这一项就吃满 | 绝对不能每帧捕获 |
| 层级问题 | `LiquidGlassCapture` 在 `app_shell.dart` 里包的是 **Shell 级背景**，`ScenePage` 是它的 child | 3D 背景在 Shell 背景**之上**，本来就不在捕获范围内 |

**裁决：`VoxelSceneBackdrop` 放在 `LiquidGlassCapture` 的捕获边界之外（即作为 ScenePage 内部的一层），玻璃继续折射 Shell 的静态渐变背景。**

理由：

- 零改动、零额外成本，`LiquidGlassCapture` 一行不用动。
- 视觉上完全说得通：玻璃卡片折射的是"环境底色"，本来就不需要精确反映 3D 世界的每一帧。
- 若强行让玻璃折射 3D 背景，代价是每帧 `toImage()`（15ms）+ shader 采样，功耗翻 3 倍，换来的视觉差异用户几乎察觉不到。**性价比极低，明确不做。**

补充：为保证卡片文字可读性（3D 世界可能很亮，如雪原正午），在背景与卡堆之间插一层自适应遮罩：

```dart
// 遮罩强度按 capture 的时相与主色亮度估算，或直接用固定值
Container(color: Colors.black.withValues(alpha: 0.28))
```

`_SceneCard` 内部已经用 `lightText = Color(0xFFF5F5FA)` 强制浅色文字（见 `card_stack.dart`），配 0.28 黑遮罩后对比度足够。

### 5.5 性能兜底与平台差异

| 场景 | 行为 |
|---|---|
| `powerSave` | 不起 timer，`Image.file(snapshotPath)`；快照缺失则回落渐变背景 |
| `capture.animate == false` | 同上（用户主动选静态） |
| Web | `kIsWeb` 时**强制静态快照**。理由：CanvasKit 的 `drawVertices` 可用但 wasm 数学慢 3~5 倍，HTML renderer 更是不支持 per-vertex color；且 Web 没有稳定的本地文件路径。Web 上 `snapshotPath` 改存 base64 dataURL 或直接退化为渐变 |
| 快照文件丢失 | `File.exists()` 失败 → 尝试实时渲染 → 再失败 → `scene.visual.gradientColors` 渐变（三级兜底，绝不白屏） |
| 页面不可见 | `AppLifecycleState.paused` / 路由被覆盖 → `_timer.cancel()`。**必做**，否则后台 18fps 持续烧电 |
| 低电量 | 可选：`Battery` 低于 20% 自动降级为静态（不引新依赖的话跳过） |
| 世界构造耗时 | `buildWorld()` 约 5ms，在 `initState` 同步做会掉 1 帧。改为首帧后 `postFrameCallback` 异步构造，构造完成前显示 `snapshotPath` 或渐变，构造完 crossfade 200ms 切到实时 |

**快照生成**（`voxel_backdrop_cache.dart`）：

```dart
Future<String> renderSnapshot(VoxelSceneCapture c, {Size size = const Size(720, 1280)}) async {
  final recorder = ui.PictureRecorder();
  final canvas = Canvas(recorder);
  VoxelWorldPainter(faces: VoxelRenderer.buildFrame(...)).paint(canvas, size);
  final img = await recorder.endRecording().toImage(size.width.toInt(), size.height.toInt());
  final bytes = await img.toByteData(format: ui.ImageByteFormat.png);
  // 落盘 <appDocs>/voxel_captures/<sceneId>_<ts>.png（与 SpatialPlayer 缓存同目录风格）
}
```

按快门时同步生成一次；场景删除时清理对应文件（挂到既有场景删除逻辑）。单张 720×1280 PNG 约 150~400KB，10 个场景不超过 4MB，可接受。

每个 Phase 都以"可独立验收、可独立回滚"为标准切分。Phase 1~4 期间 `voxel_canvas_page.dart` **原封不动**继续服役，直到 Phase 5 才切换 —— 任何一个 Phase 出问题都不影响现有功能。

### Phase 1 · 渲染器可用（地基）

**产出**：`voxel_camera.dart` / `voxel_renderer.dart` / `voxel_sky.dart` / `voxel_world_painter.dart`

**验收标准**：
1. 调试页能画出一个可辨认的地形：草地、水面、沙滩、树、雪顶山峰，六个面亮度分明。
2. 固定相机下 `buildFrame()` 返回的面数在 1000~2500 之间（打日志验证剔除生效）。

### Phase 2 · 交互（手感）

**产出**：`voxel_controller.dart` / `voxel_world_view.dart` / `voxel_hud.dart`

**验收标准**：
1. 拖拽旋转跟手，松手有惯性且自然停下（不是硬停也不是滑太久）。
2. 双指缩放平滑，到边界（r=10/34）时有阻尼感而非硬卡。
3. walk 模式下摇杆行走贴地，上下坡平滑无台阶跳变；撞墙滑行不卡死；能走进水里且有半潜 + 蓝色滤镜。

5. 真机（一加 Pad PA2353）balanced 档持续操作 3 分钟稳定 55fps+；手表（412×502）powerSave 档稳定 28fps+ 且机身不明显发烫。

### Phase 3 · 世界音效

**产出**：`world_audio_engine.dart` / `world_sound_sources.dart`

**验收标准**：
1. 走近水边水声渐强、走远渐弱；转身面向 / 背向水，左右声道有可听辨的变化。
2. 站在山体另一侧，水声明显被闷掉；绕过山头恢复清亮（验证 `wallsBetween` + `transmissionLoss` 生效）。

4. `audio_material/` 存在时用真实素材，删掉目录后自动回落合成音，功能不缺失。
5. 页面 dispose / App 切后台，所有 `AudioPlayer` 实例归零（用日志或 DevTools 内存视图确认无泄漏）。
6. 世界音效与正在播放的音乐同时存在，音乐**不被打断、不被 duck**。
7. 并发播放器实例数不超过 §4.6 的上限。

## 7. 风险与权衡

### R1 · CustomPaint 软件投影的性能天花板 —— 中等风险，已缓解

**风险**：所有几何变换在 Dart 主 isolate 上跑，世界一旦变大（比如 64×64）就会线性劣化。

**缓解**：
- 世界规模锁死在 24×24×20（既有 `VoxelWorld` 默认值），不提供"大世界"选项。这是产品约束，不是技术妥协 —— 24×24 对"取一张好看的景"完全够用。
- 用 `drawVertices` 批提交，把 GPU 侧成本压到 2~4 个 draw call。
- 背景渲染场景下相机固定，静态几何只算一次（§5.4），这是最大的一笔省。

**未来演进（明确不在本期做）**：Flutter 的 `FragmentShader` 已在本工程用于 `liquid_glass.frag`，理论上可以写一个体素 ray-marching shader 把整个渲染搬到 GPU。但那意味着：世界数据要传成纹理、调试成本极高、Web/低端 GL 兼容性未知。**投入产出比在当前阶段不成立**，记为 backlog。

### R2 · 水面动画成本 —— 低风险

**风险**：水面每帧重算 sin 是背景渲染的主要开销。

**权衡**：
- 只动**顶面**（水的侧面看不出波动，省 4/5 的面）。
- `sin` 用查表（1024 项预计算表 + 线性插值）替代 `math.sin`，Dart 里能快 3~4 倍。若 profile 显示 sin 是热点就换，否则不做（避免过早优化）。
- powerSave 直接关波纹用纯色水 —— 静态水面配上天空渐变依然好看，不是"残废版"。

### R3 · 与既有 2.5D 三处共用代码的兼容 —— **低风险（比预期低很多）**

这一条在需求里被列为重点风险，但读完代码后可以明确：**风险很小**。

依据（F1）：`VoxelCanvasView` / `VoxelCanvasController` 依赖的是 `lib/models/voxel.dart` 的 `VoxelBlockType` + `VoxelSoundScene`，与 `VoxelWorld` / `Voxel` 枚举**完全没有交集**。三个调用点各自 `new` 一个独立的 `VoxelCanvasController`，无共享状态。

因此：
- 3D 世界全部新增在 `lib/widgets/voxel3d/`，与 `lib/widgets/voxel/` 并存，**互不 import**。
- 删除 `voxel_canvas_page.dart` 只减少一个调用点，编辑器与小游戏零感知。
- 唯一触碰既有 voxel 文件的是 `voxel_world.dart` 加 `seed` 字段和 `voxel_world_types.dart` 加 extension —— 而 `VoxelWorld` **当前在全工程无任何引用**（grep 确认只有自身定义），改它的风险为零。

**仍需注意**：`lib/widgets/voxel/` 与 `lib/widgets/voxel3d/` 两个目录名字太像，容易 import 错。缓解：3D 侧所有类名统一带 `Voxel*3D` 前缀？—— 不，会很丑。改为在 `voxel3d/` 下加一个 `voxel3d.dart` barrel 文件统一导出，调用方只 import barrel，从源头避免混淆。

### R4 · Scene JSON 向后兼容 —— 中等风险，需单测护住

**风险点有两个，都在 §5.3 处理了**：
1. `Scenes.decodePack` 的严格相等判断（F4）—— 改区间兼容。
2. `voxelCapture` 解析失败拖垮整个 Scene —— 用 `tryFromJson` 全程吞异常返回 null。

**额外注意**：`ScenePacker.decode` 目前**完全不校验 schema**（`root['schema'] as int` 拿了但没用），与 `Scenes.decodePack` 行为不一致。这本身就是既有的隐藏 bug，本次一并修（两处用同一个校验函数）。

**必须有的单测**（列在 Phase 4 验收第 6 条）：v1 包解析、损坏 capture 容错、往返一致性。没有这三条测试就不合入。

### R5 · 世界与场景的耦合语义 —— 产品层风险

**问题**：`VoxelSceneCapture` 存了 seed，意味着"这个场景的背景 = 那个世界的那个机位"。但用户在世界页里换了 seed 再取景，就会产生多个场景各自绑不同世界。这是**特性还是混乱**？

**裁决：是特性**。每个场景配一个独立世界完全说得通（"雪原"场景配雪山世界，"海边"配沙滩世界）。但要给用户明确反馈：
- 世界页顶部显示当前 seed 的短哈希（如 `#A3F1`），让用户知道"我在哪个世界"。
- 场景背景长按 → 「回到这个背景的世界」，直接用该场景的 capture 打开世界页并定位到机位（`applyCapture`）。这个功能几乎免费（`applyCapture` 已在 controller 接口里），但对"可用好用"的体感提升很大。

### R6 · 音频并发与低端设备 —— 中等风险

**风险**：`SpatialPlayer` 每轨一个 `AudioPlayer` 实例，手表设备（Android 11，蓝牙音频曾触发闪退，见 `_draft_code_facts.md` 九）可能扛不住。

**缓解**：
- §4.6 的并发上限表，powerSave 压到 1 源 1 轨。
- 世界音效默认**跟随白噪音总开关**，用户关了就一个播放器都不起。
- 手表设备（屏幕 < 480px）默认强制 powerSave 音频策略，不管用户选了什么档位。
- 音效启动全部 `try/catch`（`SpatialPlayer.start` 已有），单轨失败不影响其它轨。

### R7 · 后台耗电 —— 低风险但必须处理

18fps 的背景 timer 如果在 App 切后台后继续跑，会持续烧 CPU。**必做**：`WidgetsBindingObserver` 监听 `AppLifecycleState`，`paused`/`inactive`/`hidden` 一律 cancel timer，`resumed` 恢复。这条漏了会被用户投诉耗电，属于"可用好用"的底线。

### R8 · Web 端 —— 已明确降级，不是风险

Web 上：世界页可用但强制 LOD + `renderDistance=16`；场景背景强制静态。工程本来就以 Android 为主（`build/web` 只是调试用途），不为 Web 做额外投入。

## 8. 决策摘要（一页速查）

| 议题 | 决策 | 依据 |
|---|---|---|
| 3D 方案 | 纯 `CustomPaint` + `drawVertices` 批提交，零新依赖 | 沿用 Q3 裁决；世界仅 24×24×20，CPU 投影够用 |
| 深度处理 | 画家算法 + 深度降序（体素凸体不相交，成立） | 无 Z-buffer 可用 |
| 半透明 | 两趟绘制（不透明 → 半透明） | 避免水盖树 |
| 水面动画 | 只动顶面 + 屏幕空间近似，不做世界空间形变 | 保住面剔除前提 |
| 拍照存什么 | **存参数（seed + 位姿 + 时相），不存像素**；PNG 仅作降级兜底 | 唯一能让背景"实时动"的方案 |
| 世界可复现性 | `VoxelWorld` 生成已完全确定性，只需补 `seed` 字段 | 已核对 `_hash` / `_Rng` 无随机源 |
| Scene 集成 | 加可空 `voxelCapture`，`tryFromJson` 容错 | 复刻 `bgmUri` 已验证的兼容模式 |
| schema | 1 → 2，`decodePack` 改区间兼容（min 1, max 2） | 现状严格相等会拒收老包 |
| 背景帧率 | powerSave 0（静态）/ balanced 18 / smooth 24 | 用户裁决：只有低性能档才能减效果 |
| 背景性能关键 | 相机固定 → 静态几何只算一次；三层 RepaintBoundary 隔离 | 稳定态 < 2ms/帧 |
| LiquidGlass | **互斥**：3D 背景放在捕获边界外，玻璃继续折射 Shell 静态背景 | 每帧 `toImage()` 成本 15ms，性价比极低 |
| 空间音效 | 复用 `SpatialMixer`/`SpatialSynth` 全套，只新增"世界→声源"翻译层 | 既有设施已完备 |
| 音频素材 | 运行时探测外部目录，找不到回落合成；**不进 assets** | 566MB，APK 已 157MB |
| 2.5D 兼容 | 新代码放 `widgets/voxel3d/`，与 `widgets/voxel/` 零 import | F1：两套数据模型本就无交集 |
| 世界规模 | 锁死 24×24×20，不提供大世界 | 产品约束，保住性能天花板 |
